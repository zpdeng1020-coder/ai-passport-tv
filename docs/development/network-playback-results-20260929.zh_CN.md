# 网络播放实测结果与当前瓶颈（2026-09-29）

本文记录按[网络验证交接文档](handoff-network-validation-20260929.zh_CN.md)在板子上做的测量，以及仍未解决的瓶颈。除非特别说明，每个数字都是**单次运行**，除 3.12 节外都**不含音频**。数字来自 demo 自己每 5 秒一行的输出和服务端日志；每个字段的含义见第 2 节。

## 1. 摘要

- 此前产品路径上的"9 fps 天花板"是仪器问题加上 TCP 的行为，不是设备极限。一个与产品会话毫无共用的最小接收程序，在 UDP 下 **30 fps 输入画出 26–27 fps**，但那是合成片段 `demo_clip.bin`（平均 10.7 KB/帧）。真实频道素材（13.4 KB/帧）在同一路径上 25 fps 输入只画出 20–21 fps（3.11、3.14 节）；26–27 不能当作真实电视能达到的水平引用。
- **TCP 是第一堵墙。**同一条无线链路上，TCP 只有约 100 KB/s（逐秒在 5–280 KB/s 间跳），UDP 超过 1 MB/s。TCP 送帧只到约 16 fps。
- **换成 UDP 之后，墙是"成团到达"，不是设备。**数据报一团一团到，团与团之间有 100–480 ms 的空档。服务端发得很均匀，24–30 fps 时 CPU 约一半空闲。
- **接收内存吸收不了一团。**demo 分配完缓冲后，内部堆只剩约 49 KB；30 fps 下一团 150 ms 约是 4.5 帧，正好是整个缓冲。到达时没有空位的帧记为 `nobuf` 并丢失。
- 80 MHz 下面板不再是限制（见 3.6），30 fps 下 CPU 也不是限制。**它们都不是没到 30 fps 的原因。**
- **空档在无线电处就已经存在**（3.7）：在 PHY 层取的时间戳显示出与应用层一样的 60–120 ms 空档。设备的驱动、lwIP、调度和内存都没有制造它们，接收侧 A-MPDU 的设置也改变不了它们（3.8）。
- **用 ROM 里的解码器，JPEG 走不通**（3.10）：解一帧 320×180 约 82 ms，约 12 fps，而预算是 33 ms。
- **只发变化了的条带能把字节减半**（每帧 7.6 对 13.4 KB），同一片段内画出帧率从 19.9 升到 25.5 fps（3.11 节）。30 fps 片段含重复帧，所以这些 fps 偏高；素材本身是 25 fps。
- **音频不影响图像，但内存是墙**（3.12 节）：加大音频队列会让 Wi-Fi 分配不到缓冲，两者都变差。
- **空档不是电脑的网卡、不是信标周期、也不是别的站点**（3.13 节），仍然没有解释。
- **没有稳住 25 或 30 fps。**条带槽模式从计数器看更好，但有可见、可听的撕裂（3.14 节）。
- **80 MHz 下扫过输入帧率，没有零丢帧的档位**（3.15 节）：16 fps 就丢 9–12%，30 fps 丢 17–26%；`nobuf` 是丢帧的大头，校验数据报最多只能补三成。
- **UDP 传输改造暂时搁置，产品继续走 TCP。**delta 在产品的 TCP 路径上没有带来稳定的帧率提升（3.18 节）；TCP 方向的进度和问题记在 [tcp-delta-progress-20260930.zh_CN.md](tcp-delta-progress-20260930.zh_CN.md)。

## 2. 仪器

一个最小的网络基准，刻意不基于产品的会话、接收任务和封包协议（那些正是被对比的对象）：设备侧 `main/net_demo.c`，电脑侧 `tools/net_demo_server.py`。用 `tools/sdkconfig.net-demo` 开启；该选项关闭时产品镜像不变。

| 步骤 | 运行的内容 | 测的是什么 |
|---|---|---|
| 1 | 面板上画彩条，信息写在黑边栏 | 面板是否工作，别无其他 |
| 2 `bulk` | 服务端发 TCP 零字节，设备只计数 | TCP 接收速率 |
| 3 `frames` | 服务端发 `demo_clip.bin` 的帧（TCP），不限速，靠 TCP 背压 | TCP 下接收 + 解压 + 展开 + 绘制的天花板 |
| 4 `udp` | 服务端以阶梯速率发 1400 字节带序号的数据报 | UDP 接收速率、丢包、乱序 |
| 5 `udpframes` | 服务端按固定或阶梯 fps 把帧拆成数据报发送 | UDP 帧率，以及帧为何丢失 |

设备端日志字段（每 5 秒窗口）：

| 字段 | 含义 |
|---|---|
| `fps_x10` | 每秒画出的帧数 ×10 |
| `rx_frames` | 窗口内完整收到的帧数 |
| `nobuf`（累计） | 某帧的第一个数据报到达时没有空闲缓冲，该帧被丢弃 |
| `inc`（累计） | 某帧在下一帧开始时仍不完整 |
| `inf/exp/sub_x100` | 每帧平均解压 / 调色板展开 / 送屏耗时，单位为 10 微秒 |
| `net_wait_ms` | 绘制任务没有帧可画而空等的时间 |
| `JITTER arr_min/max_ms` | 相邻两帧首个数据报之间的最短与最长间隔 |
| `JITTER burst` | 相隔不到 15 ms 到达的帧对数 |
| `CPU%` | FreeRTOS 运行时统计得到的各任务 CPU 占比（低于 1% 的不显示） |

服务端每档会打印 `max_late`（相对自己计划迟到多久）、`late>20ms` 和 `max_sendto`，用来区分"发送端自己晚了"和"网络送晚了"。

途中纠正过两处仪器错误，因为它们都产生过看似合理的数字：

- 曾有两个探针副本同时监听 8096 端口，设备连到了旧的那个，一轮读数作废。
- 第一版 UDP 设计让设备先向服务端发一个招呼数据报。在 Windows 热点上这个入站数据报到不了（防火墙），读起来像"没有数据"。现在改为服务端主动推送，不再需要招呼。

此前"6 和 9 fps 通过产品播放器与 `tools/transport_probe.py` 是稳定的"这一说法**撤回**：探针日志显示只有 6 fps 那一档跑完，9 fps 那一档中会话就被重置了。

## 3. 结果

3.1–3.10 节用的是合成片段 `demo_clip.bin`（平均 10.7 KB/帧，三档复杂度）；3.11 节起用真实频道素材，每帧更大（全帧 13.4 KB），所以两组的 fps **不能直接比较**。

### 3.1 TCP

| 测试 | 结果 |
|---|---|
| `bulk`（设备只数字节） | 平均约 100 KB/s，逐秒 5–280 KB/s |
| `frames`（接收、解压、绘制） | 平均约 16 fps，逐秒 9–23 fps |
| `frames`，TCP 窗口 65535 加深队列 | 约 9 fps、91 KB/s；**没有改善**（单次运行，只能说"没有更好"，不能说"更差"） |

这些运行里绘制任务每秒有 50%–100% 的时间是空闲的，也就是被 TCP 饿着。`sdkconfig.defaults` 里的注释记录过：窗口从 5.7 KB 调到 32 KB 才是起作用的那一步，64 KB 没有再带来什么。

### 3.2 UDP 裸数据报（设备只计数）

| 服务端发送（KB/s） | 设备收到（KB/s） | 逐秒丢包 |
|---|---|---|
| 100 | 约 100 | 0–2% |
| 200 | 约 200 | 0–1%，某一秒 9% |
| 300 | 约 290 | 0–1%，某一秒 14% |
| 400 | 约 390 | 1–3%，某一秒 11% |
| 600 | 约 570 | 3–5%，最高 19% |
| 800 | 约 750 | 3–6%，最高 12% |
| 1200 | 约 1100 | 3–22% |

全程乱序为零。20–30 fps 的视频约需要 200–300 KB/s，UDP 有余量，TCP 没有。

### 3.3 UDP 送帧，阶梯速率（当时面板时钟为 40 MHz）

产品的面板时钟现在是 80 MHz；这里的 40 MHz 是测量当时板子跑的时钟。

电脑走以太网，设备连办公室 Wi-Fi。每档 8 秒。

| 输入 fps | 画出 fps | 丢帧（累计） |
|---|---|---|
| 8 | 约 7.5–8.9 | 无 |
| 12 | 约 12 | `nobuf` 1 |
| 16 | 约 15–17 | `inc` 2，`nobuf` 4 |
| 20 | 约 20（个别秒 15–18） | `nobuf` 最高 13 |
| 24 | 约 21–23 | `nobuf` 最高 23 |
| 30 | 约 22–31 | `inc` 最高 16，`nobuf` 最高 38 |
| 40 | 约 24–38，很不均匀 | `inc` 最高 28，`nobuf` 最高 92 |

### 3.4 24 fps 下时间花在哪（当时面板时钟为 40 MHz）

同 3.3，下面与面板有关的数字（每帧等面板 8–10 ms）属于旧时钟；80 MHz 下同一步约 1.9 ms（3.6 节）。

| 项目 | 实测 |
|---|---|
| 服务端迟到 | `max_late` 0–1 ms，`max_sendto` 0.2–0.8 ms：发送端是准时的 |
| 绘制任务 CPU | 30%–45% |
| 空闲 | 50%–65% |
| Wi-Fi 任务 | 约 2% |
| lwIP `tiT` 任务 | 约 1% |
| 接收任务 | 2%–3% |
| 每帧解压 | 12–14 ms（本机 demo 为 10–15 ms） |
| 每帧展开 | 约 2.7 ms |
| 每帧等面板 | 8–10 ms |
| 最长单帧 | 26 ms（偶发 35–46 ms） |

所以整条收包路径（Wi-Fi、lwIP、接收任务）只占约 6% 的 CPU。此前"收包抢走了解压的 CPU"的怀疑**没有得到支持**：它花得很少。

同一轮里帧到达设备的间隔：`arr_min` 4–5 ms，`arr_max` 130–480 ms，每 5 秒窗口 `burst` 4–12 对。帧先停一阵，然后几帧在几毫秒内涌来。填满三个缓冲的是这个，不是绘制耗时。

### 3.5 网络路径对比（24 fps，单次运行）

| 路径 | 最长到达间隔 | `inc`（累计） | 每 5 秒 `nobuf` |
|---|---|---|---|
| 电脑走以太网，设备走办公室 Wi-Fi | 140–480 ms | 最高 38 | 约 5–20 |
| 电脑走同一办公室 Wi-Fi（WLAN） | 130–405 ms | 0 | 约 3–12 |
| Windows 移动热点，近距离，2.4 GHz | 105–320 ms（多数 110–160） | 0 | 约 3–11 |

以太网到 Wi-Fi 那一跳造成了不完整帧，但不是空档的来源。办公室的 AP 和信道占了空档的一部分（约 300–480 ms 降到热点上约 110–160 ms），而**在干净、近距离的链路上仍剩约 100–150 ms 的残余**。残余来自哪里尚未确定。

### 3.6 80 MHz 面板时钟、接收环形缓冲、30 fps 输入

面板时钟改为 80 MHz（上游提交 `20668230`，以及 `main/av_player.c` 里对应的断言；画面已用肉眼确认正常）。UDP 接收路径用一块 48 KB 的环形缓冲，整帧首尾相接存放，替代固定的 22 KB 槽。

| 项目 | 实测 |
|---|---|
| 每帧送屏 | 约 1.9 ms（40 MHz 下为 8–10 ms） |
| 每帧解压 / 展开 | 约 13.3 ms / 2.9 ms |
| 绘制任务 CPU | 43%–45%，空闲 48%–50% |
| 30 fps 输入时画出 | 25–28，多数 26–27 |
| `nobuf` | 每 5 秒窗口约 15–20 |

其中 1.9 ms 只是把条带提交给面板驱动的耗时，不是总线占用的时间。启动时的自测（`PANEL_BENCH`）提交整幅画面并等 DMA 完成、不做任何 CPU 工作，实测**每帧 13.9 ms（约 72 fps）**，接近 80 MHz 下 320×180×16 位的理论下限 11.5 ms。总线与 CPU 工作是重叠的，所以流水线约每帧 16–18 ms，30 fps 下仍有余量，但之前的"约 55 fps"是由提交耗时估出来的，不应当作实测天花板引用。设备实际只画了 26–27，是因为每秒约有 3–4 帧找不到空位。环形缓冲的深度计数打印出来是乱码（我的格式与参数不匹配），所以**环形缓冲实际用到多深没有观察到**。48 KB 大约装 4.5 个平均帧，比它替换掉的三个固定 22 KB 槽（66 KB）还小，所以 `nobuf` 没有改善并不意外。

### 3.7 空档出现在哪一层（分层探针）

设备端混杂模式回调，30 fps 输入，Windows 热点，信道 11（20 MHz）。每 5 秒窗口，相邻两个发给设备的帧之间的间隔分桶为 <2、<10、<30、<60、<120、>=120 ms。

| 层 | 典型窗口 |
|---|---|
| 空口（PHY 接收时间戳） | 958 / 146 / 36 / 15 / **35** / 0 |
| 驱动回调 | 968 / 137 / 35 / 15 / **35** / 0 |
| 应用 `recv()` 返回 | 970 / 131 / 39 / 15 / **35** / 0 |

每窗口约 30–37 个 60–120 ms 的空档，在 PHY 时间戳里就已存在，三层一致。所以停顿发生在帧到达无线电之前：空口、AP 或发送端网卡。约 15% 的帧带重传位，所有帧都是聚合发送。该统计覆盖所有发给设备的下行数据帧，这里几乎只有视频。

### 3.8 接收块确认窗口与聚合（每个变体单次运行）

同一份固件，只改 `CONFIG_ESP_WIFI_RX_BA_WIN` 和 AMPDU RX。启动日志（`rx ba win`）确认了实际生效值；日志里的 `winSize:64` 是 AP 协商的，不是这个设置。

| 变体 | 每 5 秒 60–120 ms 空档数 | 画出 fps | 备注 |
|---|---|---|---|
| BA 4（基线），两次 | 23–31 | 约 26–27 | |
| BA 8 | 28–34 | 约 26–27 | |
| BA 12 | 20–31 | 约 26–27 | |
| 关闭 AMPDU RX | 20–31 | 约 25–27 | `agg=0` 确认聚合已关 |

没有任何变体改变空档数量或帧率，所以聚合窗口里的接收端重排序不是原因。

### 3.9 办公室 Wi-Fi 加有线电脑，以及发送端摊开（30 fps）

电脑走以太网，设备连办公室网络（办公室内网地址）。`--spread` 是发送端把一帧的数据报摊开到多少个帧周期内；每个设置各跑两次，交替进行。

| 摊开 | 平均画出 fps | 最低 5 秒窗口 | 每 5 秒 `inc` | 每 5 秒 `nobuf` |
|---|---|---|---|---|
| 0.4（此前默认） | 27.1 与 27.0 | 24.7–24.9 | 1.3 与 2.1 | 9.7 与 8.8 |
| 0.9 | 23.8 与 23.7 | 18.9–21.1 | 9.1 与 8.7 | 5.8 与 7.9 |

**摊得更开反而更差**，两组重复一致：一帧花掉几乎整个周期才发完，下一帧开始时它更常还没收全。这里把一帧紧凑地发成一团更好。

同一设置的运行间波动很大：此前在同一路径上 30 fps、摊开 0.4 的一次运行画出约 24–26 fps、`inc` 每 5 秒约 9，而这次是 27 fps、`inc` 约 1.3–2.1。所以单次运行之间零点几 fps 或几个 `inc` 的差别不能当作证据。

### 3.10 JPEG 在 C3 上的解码速度（单次运行）

基线 4:2:0 JPEG，320×180，按内容档位搜索质量使平均每帧约 5.5 KB，用 ROM 里的 TJpgDec（`esp_rom/tjpgd.h`）在 160 MHz、`-O2` 下解码，写入 320×16 的 RGB565 条带缓冲（解码器输出 RGB888，转换在我的输出回调里，没有单独计时）。每行是 80 次解码（8 帧重复 10 遍）。此外什么都不运行：没有音频，没有网络。

| 内容（平均字节） | 只解码 | 解码加送屏 DMA | 最长一帧 |
|---|---|---|---|
| 测试图（5458） | 81.4 ms | 83.7 ms | 82 ms |
| 曼德博一（5451） | 81.5 ms | 84.0 ms | 84 ms |
| 曼德博二（5456） | 81.8 ms | 84.1 ms | 95 ms |

- 约 12 fps，且基本与内容无关：时间花在固定的反量化、IDCT 和颜色转换上，不在熵编码数据上。
- 约 226 个 CPU 周期/像素。30 fps 下一帧总共约 92 周期/像素，所以这个解码器在还没算音频和收包之前就慢了约 2.4 倍。zlib 路径（解压加展开，约 16 ms）比它快约 5 倍。
- 送屏 DMA 重叠得很好，只多了约 2 ms。
- 这是**一个简单的老解码器**，不等于"C3 上的 JPEG"。优化过的库（例如 JPEGDEC、`esp_new_jpeg`）可能快好几倍，都没有测。要到 33 ms，它至少要快 2.5 倍，且没有给音频和收包留余量。查到的公开先例：C3 上 JPEGDEC 做到 160×128、15 fps；双核原版 ESP32 在 320×240 上做到 28 fps。
- 每帧 5.5 KB 时的画质没有评估；丢包后的局部恢复也没有评估（一帧 JPEG 是一条熵编码流，要把损坏限制在帧的一部分内需要重启标记）。

### 3.11 把帧做小：只发变化了的条带（单次运行）

用真实频道素材（本地素材目录，CCTV1），两个变体的帧和 3-3-2 量化完全相同，只有每帧字节数不同，片段由 `tools/make_real_clip.py` 生成。`delta` 变体里，编码后的像素与面板当前显示几乎一样的条带，长度记为 0 不发；每帧另外轮换刷新一个条带，所以丢了的条带最迟 15 帧内修复。设备端只改了两行：长度为 0 的条带直接跳过（不解压、不展开、不占总线）。

| 整帧 UDP，无音频，30 fps 片段 | full | delta |
|---|---|---|
| 平均每帧 | 13.4 KB | 7.6 KB |
| 画出 fps（平均，最低） | 19.9（14.0） | 25.5（22.0） |
| 每 5 秒 `nobuf` | 46.5 | 17.8 |
| 每帧解压 | 15.1 ms | 7.4 ms |

- delta 相对全帧编码的画质：平均 PSNR 72 dB，最差帧 40.5 dB。**没有人把它当静止画面看过。**
- 收益依赖内容：CCTV1 平均 15 个条带只发 8.3 个。快速摇镜头会退回接近整帧（p95 仍约 19 KB）。
- **对上面 fps 的更正。**素材本身是 25 fps（CCTV6 是 30，HEBEI 平均 25）。30 fps 片段是把 25 fps 重采样成 30，其中 34% 的帧几乎为空（至多一个条带），一到就算“画出”；25 fps 片段这类帧只有 17%。老实算，30 fps 片段的 25.5 更接近每秒约 17 个真实帧。**同一片段内部的对比是公平的，30 fps 与 25 fps 片段之间的对比不公平。**

只在电脑上离线试过、没有上板（`tools/frame_size_lab.py`，CCTV1 与 CCTV13，各 192 帧；PSNR 以完整 320×180 的 3-3-2 帧为参照）：

| 编码 | CCTV1 平均 | CCTV13 平均 | PSNR 平均（最差） |
|---|---|---|---|
| 完整 320×180 3-3-2 | 14.7 KB | 21.5 KB | 参照 |
| 每帧 16 色调色板，每像素 4 位 | 9.2 KB（全帧 12.5） | 12.9 KB（全帧 20.6） | 比 3-3-2 好：27.0 对 24.0 dB（CCTV1） |
| “扫描线”：320×90，行加倍 | 8.4 KB | 11.5 KB | 24.4（22.4）/ 22.3（21.5）dB |
| 条带隔行（奇偶条带隔帧交替） | 7.3 KB | 10.8 KB | 最差帧 14.0 / 10.0 dB |

隔行不可用：有运动时一半条带是旧的，最差帧掉到 10–14 dB。扫描线只省 43%，不是 50%，且永久丢垂直细节。16 色调色板需要改设备端，没有上板。

### 3.12 加上音频（单次运行）

用产品的音频参数：16 kHz、s16、单声道，每 40 ms 一块 1280 字节（32 KB/s），与图像走**同一个 UDP socket、由同一个任务读取**；I2S DMA 无论网络如何都每 40 ms 消耗一块，队列空了就播静音。设备端队列 8 块（320 ms）；产品是 24 块。

| 30 fps 片段 | full | delta |
|---|---|---|
| 无音频时画出 fps | 19.9 | 25.5 |
| 有音频时画出 fps | 20.0 | 25.5 |
| 音频块丢失 | 3% | 3% |
| 播放静音的时间占比 | 10% | 4% |
| 100 秒内静音次数 | 98 | 43 |

音频没有改变图像帧率，但听感并不干净：100 秒内 43–98 次断续；delta 让次数减半，只是因为它让 CPU 更空闲。

**内存是硬约束。**48 KB 接收环形缓冲加 8 块音频队列时，空闲堆约 13 KB，`heap_min` 掉到几十字节。之后的运行都用 32 KB 环（空闲堆约 30 KB）。25 fps、整帧 delta 片段：

| 音频队列 | 画出 fps | 音频丢失 | 最低空闲堆 |
|---|---|---|---|
| 16 块（640 ms） | 17.4 | 15% | 172 B |
| 12 块 | 20.3 | 8% | 68 B（环应为 28 KB，编译参数没有核实） |
| 8 块（对照） | 21.3 | 7% | 652 B |

音频队列加大反而更差：Wi-Fi 接收缓冲分配不到。**产品的 24 块队列会比 demo 跑过的任何配置都更紧。**

注意事项：早先一次服务端音频泵有 bug（开头一秒突发），该次数据作废。尝试用 `AUD_QUEUE=6` 构建没有生效（只有 `RING_BYTES` 传到了编译器），那个变体实际是 8。

### 3.13 空档从哪来（追加探针，单次运行）

`pktmon` 用不了（没有管理员权限，驱动缺失），改用设备端和发送端的三种探针。

| 探针 | 结果 |
|---|---|
| 发送端强制走有线以太网（`--ifindex`），网卡字节计数器确认流量确实从以太网出去 | 每 5 秒 ≥120 ms 的空档 9.1 个，Wi-Fi 发送时是 9.0–9.8。空口重传降到 8%（Wi-Fi 发送时 14–17%），但空档没变 |
| 结束 60 ms 空档的那一帧落在 AP 信标周期的哪个位置（908 个信标） | 每个 10 ms 桶都是 0.6–1.6%，没有集中：与信标/DTIM/省电无关。省电已关（`WIFI_PS_NONE`），BSSID 已固定 |
| 空档期间，我们两帧之间别的站点的数据帧 | 多数空档里一个都没有（例如一个窗口 11 个空档里 10 个）：信道是安静的，AP 不是在忙着服务别人 |
| 空档长度 | 多为 60–130 ms，偶有 300–634 ms |

- full、delta、带音频三种运行里，120 ms 以上空档的数量一样（每 5 秒约 7–10 个），与发什么无关。
- 每窗口空档数与每窗口 `nobuf` 的相关系数：整帧 0.13（那时 CPU 和缓冲大小是主因），delta 0.61–0.68。每次只有 16–19 个窗口，只能说提示，不能算证明。
- 剩下的是办公室 AP 自己的排队或聚合。没有第二台 AP 或第二台接收设备来确认。

### 3.14 条带最新者胜，以及用户看到的（单次运行）

demo 的模式 5。设备上没有“帧”：15 个条带各有一个槽，存它最新的完整压缩版本，新版本替换没画的旧版本。一个数据报只装一个条带（或其分片），丢一个数据报只损失一个条带；内存固定为 15 个槽，与空档多长无关。

| CCTV1 delta，30 fps 片段 | 结果 |
|---|---|
| 数据报丢失（按序号） | 3.0%（全帧片段 3.5%） |
| 完整条带占应发 | 每 5 秒 1197/1245（96%）；全帧片段 2084/2250（93%） |
| 带音频 | 每 5 秒 1194 个条带；音频丢 3%，静音占 5% |
| 单次绘制最长 | 2.7 ms |
| 未画的最旧条带落后最新帧 | 2–3 帧 |

从计数器看它更好。**但用户实际观看时，画面和声音都有可感知的撕裂。**随后看整帧模式，用户认为与我预期的描述相符：没有条带错位，但会丢帧、卡顿，连稳 30 fps 都显得困难。所以条带槽模式**不是**看起来更稳的那个，它的计数器测的不是眼睛在意的东西。

整帧 delta 按素材帧率、无音频（25 fps 片段）：画出 21.1 fps（最低 14.3），输入 25 fps。带音频时，输入 20 fps 画出 17.6，输入 25 fps 画出 21.3，所以降帧率并没有降低丢帧比例（约 12–15%）。

一个估算，不是测量：3% 数据报丢失、每帧约 7 个数据报，则整帧至少丢一个包的概率是 1 − 0.97^7 = 19%，与实测画出 85–88% 吻合。真实丢包是成团的，所以只是粗略吻合。每帧加一个异或校验数据报（丢一个可恢复，多 14% 字节）已提出，**没有实现**。

### 3.15 80 MHz 下的帧率扫描：整帧对 delta（单次运行）

UDP，无音频，CCTV1 的 25 fps 片段，只改服务端输入帧率，每档 40 秒有效窗口，设备为 `build-small`。`nobuf`、`inc` 为每 5 秒的平均增量。

| 输入 fps | delta 画出（最低） | 画出/输入 | `inc`+`nobuf` | 整帧画出（最低） | 画出/输入 | `inc`+`nobuf` |
|---|---|---|---|---|---|---|
| 16 | 14.5（12.5） | 91% | 4.6 | 14.1（12.6） | 88% | 6.2 |
| 20 | 18.5（16.9） | 92% | 4.7 | 16.7（14.4） | 84% | 12.9 |
| 24 | 21.0（18.7） | 88% | 11.0 | 19.5（16.8） | 81% | 16.8 |
| 28 | 23.6（18.3） | 84% | 14.3 | 20.9（16.9） | 75% | 24.5 |
| 30 | 25.0（21.9） | 83% | 17.1 | 22.2（19.1） | 74% | 28.0 |

- **没有零丢帧的档位。**丢帧比例从 16 fps 的约 9–12% 平滑涨到 30 fps 的约 17–26%，没有拐点。此前从 3.3 节（40 MHz）推出的"16 fps 几乎不丢帧"**不成立**。
- **delta 每一档都更好，差距随帧率拉大**（16 fps 时 91% 对 88%，30 fps 时 83% 对 74%）。
- **`nobuf` 是丢帧的大头**：delta 30 fps 为 12.1 对 5.0（`inc`），整帧 30 fps 为 21.3 对 6.7。所以每帧加一个异或校验数据报（只能补 `inc`）最多补掉总丢帧的约三成，不值得为它改协议。
- 该片段约 17% 的帧几乎为空，一到就算"画出"，绝对帧率偏乐观；档位之间的对比是公平的。
- 同一片段同一路径，delta 30 fps 画出 25.0，与 3.11 节的 25.5 吻合。

### 3.16 关闭 IPv6（单次运行，板子上）

`tools/sdkconfig.no-ipv6` 只关 `CONFIG_LWIP_IPV6`；代码里只用 `AF_INET`。同一 demo、同一服务端参数：

| | 基线 | 关 IPv6 | 差 |
|---|---|---|---|
| 静态 DRAM | 164048 | 162456 | −1.6 KB |
| 启动时 `allocated; heap` | 60432 | 62372 | +1.9 KB |
| 联网收帧稳态 `heap_free` | 27360 | 29432 | +2.1 KB |
| Flash 镜像 | 1554402 | 1519230 | −35 KB |

官方说运行时约省 7 KB，实测只有约 2 KB，帧率没有可见变化。这一项收益太小，**不采用**。`heap_min` 两次不可比（18840 对 192/420），原因没查。

### 3.17 静态内存账本（`build-small`）

静态 DRAM 共 164 KB：IRAM 里的代码 102.6 KB、`.bss` 47.8 KB、`.data` 13.6 KB。`.bss` 里最大的一项是应用自己的：`av_player.c` 的 `static player_t s`，17.5 KB，其中 `channel_t list[128]` 占 8 KB。网络 demo 构建里播放器从不启动，但 `av_player.c` 仍被链接，这 17.5 KB 被白占；让 demo 不链接它就能还给堆（**没有做**）。产品里它是真占用。

### 3.18 产品路径上的 delta（单次运行）

服务端 `TV_DELTA=1`、设备固件跳过长度为 0 的条带，在产品的 TCP 路径上测得约 7–11 fps，基线约 7.8 fps，没有稳定提升；每十几秒一次的半秒以上写入停顿会让会话重置。细节、改动清单和后续候选见 [tcp-delta-progress-20260930.zh_CN.md](tcp-delta-progress-20260930.zh_CN.md)。

## 4. 仍然存在的瓶颈

按对稳定帧率的制约程度排序。目标应是素材帧率，多数频道是 25 fps（3.11 节），而不是 30；此前的 30 是重采样造成的。"实测"指上文有数字，"推测"指尚未验证的推断。

1. **每秒约 6–7 次的 60–120 ms 空档，试过的每个 AP 和路径上都有**（实测）。它在 PHY 时间戳里就存在（3.7），所以不是设备制造的，也不受接收 BA 窗口或聚合影响（3.8）。剩下的是空口、AP 或发送端网卡。办公室 Wi-Fi、办公室 WLAN 发送端和 Windows 热点都出现了，只是形状不同；没有试过别的 AP 或发送端硬件，链路层重传（约 8%–20% 的帧带重传位）是一个没有被单独隔离的候选。
2. **接收内存吸收不了一团**（实测）。demo 的缓冲之后内部堆约剩 49 KB；30 fps 下一团约 4.5 帧。平均每帧 10.7 KB，最大 22 KB。没有 PSRAM，Wi-Fi、lwIP、显示和编解码共用同一块内部 RAM。想把环形缓冲加大就得从这些里让出内存，**它们哪个能让出多少，没有调查过**。
3. **这条链路上 TCP 在这个速率下不可用**（**已被后续实测推翻**）。此处的约 100 KB/s 来自最小 demo 的单次运行，与产品路径上的结论相反：产品路径里 120–150 KB/s 的平台是服务端限速器的预算，去掉限速器后真实直播画出 24.3 fps、约 349 KB/s，见 [tcp-delta-progress-20260930.zh_CN.md](tcp-delta-progress-20260930.zh_CN.md)。
4. **一帧约八个数据报，丢任何一个整帧作废**（实测为 `inc`；这些运行里数量不大，0–38）。网络好时代价低，弱网下代价高。按条带对齐数据报（模式 5，3.14 节）只会丢帧的一部分，但有可见撕裂；校验数据报已提出，没有实现。
5. **解压是 CPU 上最大的一项**（实测，约 18 ms 中占 12–14 ms）。30 fps 下它今天不是墙（CPU 约 44%），但加上音频和丢包处理之后，余量要从这里来。基线 JPEG 用 ROM 解码器实测更慢（3.10）；更便宜的无损索引编码只是估算。
6. **产品仍走 TCP，帧率上限仍是 `server/rate.py` 里默认的 12 fps。**UDP 方案搁置；产品侧只加了默认关闭的 `TV_DELTA`（3.18 节），demo 的 UDP 结果没有带进产品。

## 6. 没做的事

- 音频只从 3.12 节起测过，用 demo 的 8 块队列而不是产品的 24 块；之前各节都没有音频。

- 环形缓冲深度现在日志里有 `ring_high`（有 delta 片段时多次读到 13，槽位上限 15），但**含义没有核实**：帧很小时先满的可能是槽位数而不是字节，没有分开测。

## 7. 其他可能有用的信息

**外部资料怎么说**（检索所得，没有在这块板子上复现）：

- Wi-Fi modem 省电是接收延迟长达一个信标周期的常见原因（`esp_wifi_set_ps(WIFI_PS_NONE)`）。这里不适用：设备日志显示 `Set ps type: 0`。也有人建议用 HT20 代替 HT40；热点那几轮本来就是 20 MHz，空档依然存在。调大 Wi-Fi RX 缓冲数、BA 窗口和 UDP 邮箱是文档给出的抗突发手段，这些都试过（3.8），没有效果。有一个论坛帖子描述了 C3 上约每 200 ms 一团的突发 UDP，用纯 ESP-IDF 也一样，没有给出解决办法。**没有找到能解决 60–120 ms 空档的现成办法。**
- atomic14 的 `esp32-tv` 播放器（读了源码，没有运行）：HTTP，设备主动拉取，一个下载任务加长连接，图像只有一帧缓冲，总是请求当前音频时间对应的那一帧，所以卡顿是被跳过而不是被补播；音频按 1 秒一块、8 位 PCM 拉取。在双核芯片上 280×240 约 15 fps，没有预取队列。里面没有任何东西能超过现有数字。它与本项目共有的两个思路是：以音频为时钟、跳过过期帧而不是补播；产品播放器已经会丢弃比音频时钟落后超过 100 ms 的帧，而网络 demo 没有，因为它没有音频。

**考虑过但没有测的想法：**

- 在服务端把帧做小。zlib 条带格式在降低画质后可以做到每帧 5–6 KB，设备不用改。这是找到的唯一一个不碰链路、又作用于内存瓶颈的杠杆，画质没有评估。
- 给接收路径腾内存：找出 Wi-Fi、lwIP、显示和编解码各自能让出多少（内存账本，瓶颈 2）。`tinfl_decompressor` 的大小在启动时有打印，但为 3840 字节的条带使用更小的解压窗口能否省出内存，没有核实。
- 换 AP、换发送端网卡，或用有线连接 AP 的发送端，看 60–120 ms 空档会不会移动（瓶颈 1）。链路层重传计数没有读。
- 像 esp32-tv 那样由音频时钟驱动的拉取模型，永远不会收到装不下的一团；代价是每次请求一次往返，60–120 ms 的空档会把它暴露出来，所以需要同时有多个请求在途。
- 数据报按条带对齐（每个数据报装完整条带），这样丢包只损失帧的一部分（瓶颈 4）。没有实现。
- 同理的带重启标记的 JPEG，只有在更快的解码器让 JPEG 可行时才有意义。
- UDP 传输、产品的 12 fps 上限（瓶颈 6）：UDP 已搁置，demo 的 UDP 结果没有带进产品。TCP 方向的进展见 [tcp-delta-progress-20260930.zh_CN.md](tcp-delta-progress-20260930.zh_CN.md)。

**途中做的选择，读者可能想重新审视：**

- UDP 是单播，一个数据报载荷 1384 字节加 16 字节头，服务端直接推送，不需要设备向服务端发任何数据报（热点上入站数据报被挡了）。
- 下一帧开始时某帧仍缺任何数据报，就整帧丢弃；接收端从不阻塞，所以设备慢会表现为 `nobuf`。
- 接收环形缓冲 48 KB，整帧首尾相接存放；为了放下它，TCP 模式的槽位减到了一个。它的深度计数是错的，所以它在成团时的表现没有被确认。

## 8. 复现

```text
# 固件（公开构建），加 demo 叠加文件和你要的实验叠加文件
idf.py -B build-net -D AV_PUBLIC_BUILD=ON "-DSDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.av-prototype;tools/sdkconfig.net-demo;tools/sdkconfig.net-udp;tools/sdkconfig.net-stats" -D SDKCONFIG=build-net/sdkconfig build
# 在这台机器上通过 tools/idf-run.ps1 运行；只用分段刷写，不要 erase-flash

# 服务端（一次只跑一个；先确认没有旧副本在监听 8096）
```
