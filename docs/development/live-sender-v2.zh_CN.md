# 直播发送引擎 v2 候选版

本候选版重写直播媒体调度与 socket 写入，保留共同 FFmpeg 输入、源时间戳映射、FAV1 协议、原生 320x240 索引画面和 16 kHz 单声道 PCM。已在主机验证，尚未在 ESP32-C3 测试。普通入口仍选择旧发送器，请通过下文的候选版专用入口启动。

## 为什么要改发送器

回传的真实频道记录中，设备 39.324 秒完成 79 帧，约 2.01 fps；软件补静音 208000 个采样，即 13 秒。已经转码好的音频从 92 块积压到 394 块，同时 socket 写入出现长时间阻塞。这支持检查下游拥塞与调度，不能证明解码器太慢是唯一原因。

此前固定 12 fps 的试播参数用于受控基线，不能保证所有直播源都能持续达到该速率。本候选版改变发送调度，保留画面分辨率。

## 运行边界

- 单个非阻塞写入者最多持有一个未写完的包，按已写偏移继续；半包超时就关闭连接，不在残缺载荷后拼接新包。
- 按条带边界将视频重新分组为最大 6144 字节的载荷，压缩条带内容与全部 15 条带保持完整。音频只在完整包之间优先发送，不插进视频载荷。
- 本地音频预送量为 280 ms，恢复追赶最多约八个 40 ms 块。重置本地发送计划不改媒体时间戳，也不表示设备已经播放。分片到达的 END 控制头会被保留，不阻塞媒体写入。
- 视频同时按字节和帧配速：从 3 fps、64000 B/s 视频预算开始，在 1–12 fps 间自适应，预算最高 120000 B/s。这是保守试用配置，不是已测得的硬件上限。最低帧率仅用于拥塞退让，不能作为验收标准。
- 主机 PCM 积压超过 8 秒时，在完整帧之间保留约 4 秒音频，并按同一内容边界丢弃更旧画面。线上 PCM 时间戳仍连续。这会在过载时跳过节目内容；反复裁剪属于故障迹象，不能算通过。
- 连续 3 秒没有可取音频则关闭会话、等待重连。这种有界回退不等于源恢复已经无缝。

发送器依据本地写入耗时推测压力，没有设备缓冲反馈。每条带 5 ms 的配速与每包 1 秒的超时仍需真机验证。单靠小包不能修复持续吞吐或渲染能力不足的接收端。

## 启动与测量

在现有仓库根目录，使用真实的本机频道表：

```bash
python3 tools/run_live_v2.py --repo . --channels /absolute/path/channels.txt --channel ch000 --dry-run
python3 tools/run_live_v2.py --repo . --channels /absolute/path/channels.txt --channel ch000 --output-dir /absolute/path/new-run
```

入口清除继承的 `TV_*` 实验变量，载入候选参数，检查实际导入配置，记录源码哈希及新的服务端日志。它不采集串口，不自动宣布真机 PASS。真实 IPTV 不要加 `--loop`。使用旧端口前停止已有服务。需要受控对照时，在同一命令后加 `--engine legacy`，使用独立输出目录；这比较同源同配置下的两种发送器，不使用旧的固定帧率入口。

在真实主机上，测真实源的独立生产能力，不连接设备、不运行发送器：

```bash
TV_GEOMETRY=320x240 TV_FPS=12 TV_PACKET_TARGET=6144 TV_STREAM_LOOP=0 python3 tools/probe_live_source.py --channels /absolute/path/channels.txt --channel ch000 --seconds 20 --output /absolute/path/new-source-result.json
```

必须使用新输出文件名。音频接近 25 块/秒、视频接近 12 帧/秒，说明该配置可实时产出。探针按实时输入配速，不是 CPU 峰值测试；`pack_wall_s` 是打包路径耗时，不是 CPU 占用率。生产足够而设备卡顿时检查发送、网络和接收；生产不足时先量源断供与 FFmpeg CPU/进度，再归因硬件。

`LIVE2` 分开报告 `frames_tx`、`video_packets`、音频包速率和生产队列。即使 `frames_tx` 也只代表主机写完的帧，不是屏幕实际显示帧。必须配合串口完整帧计数及屏幕、扬声器录像。

## 固件与验收

本包不改固件源码及线协议。试播前核对运行应用身份和 CONFIG 兼容性；如果证实接收端缺陷，仍可能需要修改固件并刷机。回传快照的根 `sdkconfig` 与 `sdkconfig.defaults` 存在 TCP 缓冲（5760 与 32768 字节）和接收邮箱（6 与 16）差异，任何一份都不能证明真机正在使用什么。必须检查实际构建配置及内部 RAM 预算，无 PSRAM 的设备不要盲目增大缓冲。

先对故障真实频道试播 60 秒并保留原始串口。如果正常，再以同一版本连续播放 30 分钟并切台。如果失败，先保留首个失败和独立源测试，再改变下一项变量。算帧率时不能用重连后的好窗口替换失败区间；不能因为声音连续就接受幻灯片式画面。下一次试用版判定采用真实频道的 30 分钟观察，保持原生分辨率及现阶段约 11–12 个完整显示帧/秒的目标，随后检查切台和重连。重复受控素材耐久测试不再作为本次试用的前置条件。精密输出音画同步和完整重复故障矩阵在测量前继续标为未验证，试用就绪不代表这些要求已关闭。

默认视频预算无法让每帧 20000 字节的频道跑到 12 fps：即使不计额外开销，预算相除也只有 6 fps。不能把这称为硬件上限或任务完成。设备音频与队列稳定后，可用 `--video-budget BYTES_PER_SECOND` 按实测帧成本做一次留档的容量试验，给缓慢升速留出时间；设备断音、丢帧或慢写再次出现时停止加预算。

## 验证范围

`python3 -m unittest discover -s tests -p 'test_live_sender_v2.py' -v` 覆盖包完整性、部分 I/O、有界音频追赶、共同时间轴裁剪、分片控制输入和真实主机限速 TCP。本地 720p25 HLS 素材也已通过真实 FFmpeg 和候选启动入口。这些都不模拟 ESP32 内存压力、Wi-Fi、LCD 或扬声器输出。

Build: NOT RUN（复核环境没有 ESP-IDF）。
Host tests: 详见候选包证据，未执行项独立列出。
Device tests: 本候选版 NOT RUN。
Unverified: 真实频道可持续帧率、目视与听感连续性、实际输出同步、长时恢复、真机固件配置及 macOS 行为。

回传快照缺少 Git 元数据，标准仓库检查停在 `git ls-files`。执行机应在真实仓库运行 `./tools/validate.sh --static`。固件编译与设备结果分开报告。

## 设备采集与修正后的汇总

`tools/run_live_v2_trial.py` 在同一发送器外增加串口采集。指定 `--repo`、`--channels`、`--channel`、`--serial-port`、`--output-dir` 及选定的 `--video-budget`。`--seconds` 现在从媒体开始且 `--warmup-seconds` 结束后计正式观察时间；30 分钟测试使用 1800 秒正式观察。只有有限时长的基线文件加 `--loop`。工具需要 pyserial，每次创建新目录，保留会话结束计数，在 `capture_events.jsonl` 记录单调时钟的开始、观察、停止标记。

采集完成不是播放验收通过。缺失串口数据、启动失败及读取失败返回非零。主动停止后的重置单列；没有停止标记的旧日志保留为未分类。`tools/summarize_live_trial.py --run-dir RUN --output NEW_JSON` 也可以审计旧日志：空重连会话不会抹掉前一会话的补静音，累计 `dropped` 不逐窗口求和，`nobuf` 仍按窗口累加。缺少末尾计数就是未知，不能填零。静音总数是所捕获会话的软件计数，不是声学测量，也不能定位到暖机或正式观察阶段。周期采样的空闲堆与固件开机以来的最低值分开报告。新增 13 项汇总/采集测试使用构造夹具，真机验收仍单独进行。
