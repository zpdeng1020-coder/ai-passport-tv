# Task state, 2026-09-16

**Read this before starting work, and check it against the code.** Every claim
below names where it can be verified. If the code and this table disagree, the
code is right and this table is stale — fix it.

The point of this file is that a session working on this project had its context
compacted and came back to the work with a wrong picture of what had already been
done: it proposed building a mechanism that already existed, and it reported
defects as unfixed that had been fixed. Both are cheap to cause and expensive to
discover.

**Use only these states, and do not blur them:**

| State | Means |
|---|---|
| Suspected | A worry, with no evidence yet |
| Located in source | Found the exact place, not reproduced |
| Reproduced offline | Reproduced on the host with controlled input, repeatable |
| Modified | Code changed, not yet well verified |
| Local tests pass | Host tests pass **and were shown to fail on the old code** |
| Verified on device | Measured on the hardware |

**A finding from a review is never promoted straight to "fixed".**

### How the timeline work has to go

Sharing one source read and demux is the direction: keep each output's PTS and
time base, then map both onto a common session basis. **Changing two epochs to
the same wall-clock instant is not the fix.**

The current ffmpeg outputs `rawvideo` and bare PCM, and Python reads only the
payload — **and raw formats carry no timestamps**, so adding `-copyts` while still
reading bare payloads cannot work. Either an interface that carries time, or an
explicit metadata mechanism, and the filter's resampling and live timestamp jumps
have to be considered.

**A constraint from the device side**: `main/av_protocol.c:48` requires audio to
start at 0 and advance strictly in 40 ms steps. Upstream PTS cannot be put
straight into the existing header. How upstream content time maps to session
playback time, and what happens on a jump, a gap or a rebuffer, has to be decided
and changed on both ends together.

### Regression cases that must exist

Same content 600 ms late; a source that stops producing; a blocked video send;
short audio starvation and recovery; audio queue overflow; a source PTS jump; a
frame split across packets.

**They must check content ID and PTS and the recovery result**, not that the
connection stayed open or that some function was called.
