# 画面通路改造开发日志（2026-09-14）

本文记录把画面从「160×120 JPEG 在设备上放大两倍」换成「320×240 索引色整帧」的
全过程，重点是**动手之前不知道、动手之后才知道的事**。结论写在 CHANGELOG 里，
过程写在这里，因为下次改这条通路的人需要的正是这些。

## 一、起因

设备屏幕 240×320，而已发布的画面是 160×120 的 JPEG 在设备上按 2 倍最近邻放大，
屏幕上四分之三的像素是复制出来的。用户的要求只有一句：画面不流畅、画质不好，
借鉴社区项目重做，两条都要改善。

社区项目 L33Z22L11/pocket-tv 的做法是整帧调色板索引 + zlib 压缩。JPEG 解码要算
霍夫曼表和反余弦变换，inflate 只做查表和拷贝，每像素成本低得多——所以清晰度和
帧率有机会同时改善，而不是二选一。

## 二、动手前的测量

这些数字决定了方案形状，都是实测而非估计：

| 项 | 数值 | 怎么得到的 |
| --- | --- | --- |
| 索引色整帧 | 76800 字节 | 320×240，一字节一像素 |
| 分 16 行条压缩 vs 整帧 | 只差 2.2% | 四个频道各 10 秒 |
| 30 秒采样的最坏帧 | 29275 字节 | 10 秒采样只看得到 23167，会漏 |
| 自适应调色板 RMSE | 10.1（固定 332 是 28.2） | 同帧对比 |
| `-sws_dither none` | 最坏帧 31KB → 23KB | 抖动是噪声，压缩不掉 |
| `tinfl_decompress` | 在 C3 ROM 里，`0x400000f4` | `esp32c3.rom.ld:81` |
| 每帧 SPI 下限 | 153600 ÷ 5MB/s ≈ 30.7ms | 计算 |

最坏帧 29275 字节直接否掉了「一帧一个包」的简单做法，于是有了 3 条一包、一帧
5 包的格式，以及「同帧续包」标志位。

## 三、动手之后才发现的四件事

前两件是 ffmpeg 的行为，后两件是我们自己代码里的错。

### 1. `-pix_fmt rgb8` 会摧毁自适应调色板

`rgb8` 看起来就是「8 位色」，实际不是：它是 ffmpeg 自己固定的 3-3-2 栅格。要它
就意味着每个像素被重新量化到那个栅格上，**选定的调色板整个被丢掉**。设备拿到的
索引会去查一张它们从来没被选出来的表。

这条特别危险，因为它不会报错：画面仍然会出来，只是自适应调色板白做了——本质上
退回成 3-3-2，还多绕了一圈。发现方式是在白色测试卡上量边框，`rgb8` 在画面下方
第一行吐出了三种近黑，而同一路信号的 `pal8` 输出是干净的黑。

正确做法是 `pal8`，索引原样透传。验证方式是把这个怀疑彻底钉死：同一帧同时输出
`pal8`（索引）和 `rgb24`（颜色），把索引经调色板还原成颜色后逐像素比对，
307200 像素零差异。

### 2. `pal8` 每帧带 1024 字节调色板，且在**像素之后**

rawvideo 复用器每帧写一次调色板块。实测步长 77824 = 76800 索引 + 1024 调色板，
**像素在前、调色板在后**——不是通常以为的头在前。这 1024 字节必须读掉再丢，
不能 seek 过去（管道不能 seek）。若读错步长，下一帧会提前 1024 字节开始，
整条流剪切错位，表现出来像缓慢的画面撕裂而不是错误。

### 3. 调色板采样与画面映射用的不是同一套几何

`palette_command()` 采样时用的是 `fps,FIT`，而 `import_video()` 映射画面时用的是
`scale=iw*sar:ih,setsar=1,FIT`。**非方形像素的源**因此是「按满屏采样的调色板，
去映射一个加了黑边的画面」——调色板里根本没有黑色。于是上下黑边被映射到最近的
可用颜色，也就是白色，整个面板看起来是亮的。

修法是让两者由同一个字符串派生，而不是靠两处写法保持一致。这是本次改动里
唯一一处「同类错误可能重演」的地方，所以用派生而不是注释来防。

### 4. 设备离线的计数取决于哪条代码路径先发现

`_device_left()` 原本把「连接断开但没收到 END」当成正常离开返回 True。这条判断
与 `_wait_until()` 的异常路径互相竞争：一个已经通过鉴权、然后消失的设备，
可能被计成一次正常完成，也可能被计成一次故障，**取决于哪条路径先看到 FIN**。

实测约十次里错一次。而这个数字恰恰是程序退出时给操作者看的唯一一行统计——
十次对九次就是错。设计分界应该是**握手**而不是 FIN：没鉴权就断开是观众改了主意，
鉴权之后断开是真故障。改法是让异常照常抛出，落到 `session_id != 0` 那一支。

## 四、顺带修掉的两个小问题

- `tools/install-actionlint.sh` 用 `command -v sha256sum` 判断校验工具是否可用。
  macOS 的 `/sbin/sha256sum` 存在、`command -v` 也答「在」，但不接受任何选项，
  `--check` 更不行——于是脚本在这台机器上必然失败。改为优先用 `shasum`。
- `import_video()` 只关了 stdout，stderr 管道留着。一次导入漏一个描述符，
  长期运行的服务上是**每个片段漏一个**。

## 五、没验证的部分

**真机解码耗时与内存占用尚未测量。** 代码在本机编译通过、主机测试全绿、固件
构建通过，但 `tinfl` 在 160MHz RISC-V 上的实际吞吐只是按 miniz 常见量级推的。
判断流畅度是否真的改善，唯一硬证据是刷机后串口日志里的实测值。在拿到那个数字
之前，任何关于「更流畅」的说法都只是设计意图。

调色板带来的实际观感同理：自适应调色板 RMSE 10.1 是主机上的量化数字，
在 240×320 的屏上好不好看，要眼睛看了才算。
