# 数据字典：每个计数器到底在数什么

记错含义的数字比没有数字更糟。本项目已经有三轮被这件事误导过：`panel_frames` 被当成帧数、`in_bps` 被当成链路吞吐、`rx_bps` 被当成总吞吐。这份文件的存在，是为了让下一个读到它的人不再重复。

**用下面任何一个数字之前，先读"但它不是"那一列。**

## 设备端计数器

来自串口的 `CLOCK_ESTIMATED` 行，每十秒一行。

| 字段 | 数的是什么 | 在哪里累加 | **但它不是** |
|---|---|---|---|
| `interval_frames` | 区间内**画完的完整画面**数 | `s.decoded`，一帧的 15 条带全部画完才加一 | 画面被物理看见的时刻。这个数在最后一条带提交之后才加，而那一条带的 DMA 可能还在跑 |
| `interval_ms` | 这个区间的墙钟长度 | — | 恰好 10000。它是实测的，通常略多 |
| `panel_frames` | 处理掉的**视频包**数 | `push_stripe()` 各调用点 | 帧数。一帧拆成两个包就算两次 |
| `panel_ms` | 这些包从解码前到传输等完的墙钟总耗时 | `video_task` 里解码与绘制那一段 | CPU 占用。它包含了等显示 DMA 的时间；也不是最后一条带物理完成的时刻 |
| `panel_wait_ms` | 阻塞在 `bsp_display_raw_wait()` 里的时间 | `push_stripe()` 末尾 | SPI 总时间。它量的是 CPU **被挡住**的时间，而双缓冲之下这个数接近零，因为传输被重叠掉了 |
| `inflate_ms` | 各条带的 zlib 解压 | `tinfl_decompress` 前后 | — |
| `expand_ms` | 索引字节展开成 RGB565 | `av_expand_indexed` 前后 | — |
| `enlarge_ms` | 条带放大 | `enlarge_stripe` 前后 | — |
| `overlay_ms` | 菜单与横幅画进条带 | `overlay_stripe` 前后 | — |
| `submit_ms` | 启动一次显示传输 | `bsp_display_raw_submit_nowait` 前后 | 传输本身。它排进队列就返回了 |
| `parts_ms` | 解压、展开、放大、叠加、提交、等待六项之和 | 打印时算出来 | 一个测量值。它就是那六项相加，只是替读者先加了 |
| `decode_max_ms` | 区间内**最慢那个包**的耗时 | `video_task` | 均值。它用来留余量，不用来定持续速率 |
| `dropped` | 设备放弃的画面数，**两个来源合计** | 接收任务：拿不到包缓冲的首包（`av_player.c:1131`、`:1172`，与 `nobuf` 同时发生）；绘制任务判定迟到（`:2305`） | 单一来源。它**包含**缓冲满造成的丢帧，与 `nobuf` 有重叠，而两者单位不同（一个是帧，一个是包） |
| `nobuf` | 因为两个包缓冲都被绘制任务占着而丢掉的包数 | `receive_task` | 任何关于链路的信息 |
| `starts` | 开启一帧的视频包数 | `receive_task` | — |
| `late` | 因 `estimated_pts() - v.pts > 100` 而丢掉的帧 | `video_task` | 专指网络迟到。它是相对播放时钟的迟到 |
| `stray` | 一帧里**每一个非首包** | `receive_task` | 异常计数。正常的续包也被算进去，所以一个健康的多包帧会把它推高 |
| `rx_pkts` / `rx_bps` | 从 socket 上读到的**视频载荷**字节与包数 | `receive_task`，读取成功之后 | 整条 socket 的总吞吐。它完全不含音频、不含 FAV1 包头，而缓冲满时的丢弃读取另算 |
| `rx_audio` | 读到的音频包数 | `receive_task` | — |
| `io_ms` / `wait_ms` / `iters` / `per_iter_us` | socket 读耗时 / 音频流控等待 / 循环次数 / 平均一次读 | `receive_task` | — |
| `in_bps` | 交给解压器的压缩条带字节率 | `av_player.c:1786` 累加，**位置早于** `:1789` 那三处成功校验（解压状态、消费字节数、产出长度） | **不是「只统计解压成功的字节」**。正常解码时两者相同，失败路径上累加发生在前。它永远看不见被丢弃的包，也永远看不见音频 |
| `hdrgap_max` | 接收循环两次收到包头的最大间隔 | `receive_task` | — |

### 三个真的被读错过三次的

**`panel_ms ÷ interval_frames` 才是每帧成本。**除以 `panel_frames` 得到的是每包成本，那是另一个数，曾经被用错过一次，让设备看起来比实际快一倍。

**`rx_bps` 不是总吞吐。**某一行显示 `rx_bps=106269`、`rx_audio=250`，它承载的载荷是 `106269 + 250×1280÷10 = 138269` 字节每秒，还没算包头。从 `rx_bps` 里再扣一次音频，是把它本来就不含的那部分扣了两次。

**`parts_ms` 要和同一行的 `panel_ms` 比。**两个数都打在每一行里，就是为了这个。它们的相对差最大到约 1.3%，并不需要在 1% 以内：其中一部分是逐字段整除 1000 的截断（六项加起来最多 5 毫秒），另一部分是真实的、没有计时的循环开销（每窗口 4 到 18 毫秒）。两者都不是故障。**但把「`parts_ms` 超过 `panel_ms`」直接判为计时器被算了两次，也是错的**：分段在处理过程中陆续入账，总时间在包处理结束时才入账，而统计又分别读取各个原子计数，没有取同一完成边界的快照，因此跨窗口出现反向差值是可能的。

**所以这里承认：计数窗口之间可能不严格对齐。**要让它们对齐，需要在一个包处理完之后统一发布累计统计，或者给快照加一致性机制。在那之前，任何逐字段的差都不该被单独当作计时故障的证据。

## 服务端计数器

| 字段 | 数的是什么 | **但它不是** |
|---|---|---|
| `video_sent` / `video_pps` | **视频包**数 / 每秒视频包数 | 每秒帧数。一帧可能不止一个包 |
| `prod_drop` | 视频队列淘汰的帧数，**两个原因合计**：队列溢出，以及在配对时被更新的帧顶掉 | 单一原因造成的故障帧数 |
| `late_video` | 服务端选中画面后、因该轮 socket 不可写而放弃发送的次数 | 设备端的迟到。**名字不等于条件**：递增发生在 `writable` 为假处，不是「槽位过期」 |
| 传给 `RateController` 的 `dropped` | **这个发送端**在窗口里放弃的帧数 | 设备反馈。没有反向通路，设备什么都不报 |
| `RATE` 行里的 `frame=` | 平滑值与瞬时值，来自 `video_bytes ÷ frames` | 两次测量。它们是对同一个量的两个估计 |
| `ceiling=` | 预算除以每帧字节，夹在 `MIN_FPS` 与 `MAX_FPS` 之间 | 一个实测速率。它是从实测每帧成本算出来的，但被除的那个预算是假定的工作点（见 `rate.py`） |
| `worst_write` | 窗口内最慢的**单次 4096 字节切片**写入 | 发完一整个包的耗时 |
| `prod_drop` 与 `video_pps` | 生产跑在 `media.FPS`（跟随 `rate.MAX_FPS`），发送跑在控制器的速率 | 同一个速率。实测：生产 12，承载约 5.5，差额在队列里被丢掉 |

## 完全没有被测量的东西

这些是缺口，列出来是为了不让人误以为量过：

- **设备自己的播放位置**没有回传服务端。服务端知道自己发了什么、什么时候写出去的，仅此而已。
- **设备的音频缓冲深度**也没有回传。
- **画面出现的物理时刻**没有测量。`interval_frames` 数的是提交完成的次数，不是光子。
- **显示 DMA 真正忙了多久**在改用双缓冲之前没有测量过；`panel_wait_ms` 量的是等待，不是传输。
- **内容时间戳没有从 ffmpeg 一路保留到播放。**对齐用的是到达时间。见 `state-20260916.md` 的 D4。
