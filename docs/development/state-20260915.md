# What is known and what is not (2026-09-15)

This list exists to end a cycle of repeated work. After the working context was
compacted, several conclusions that already had measurements behind them were
lost, and the same questions were measured again from scratch -- once changing
the code back to an arrangement that a development log had already rejected.
Writing down what is settled and what is still open is meant to stop that
happening a third time.

> **Two things to know before reading. ** This list was written in the afternoon,
> and both the picture geometry and the link measurement advanced afterwards.
> `docs/development/handoff-20260915.md` is the later document; where the two
> disagree, it wins. Concretely: the picture described here is a 320x240 indexed
> frame, and it is **now 200x150 in, enlarged 8/5 on the device**; and the
> successive reversals in this document settle on the link's ~175 kB/s ceiling,
> which is a **separate** finding from "the receiver task outranked the video
> task" -- both hold, each explains its own layer. The line "`TV_FPS` now
> defaults to 8" has since been replaced by 12.

## 1. Measured, and not to be measured again

### The picture format

| Item | Value | How it was obtained |
| --- | --- | --- |
| One indexed frame | 76800 bytes (320x240, one byte a pixel) | calculation |
| Compressed frame, per-channel | 29.8 to 42.6 KB | measured on four live channels |
| Compressed frame, re-measured | 11 to 16 KB, and about 2.4 KB on a flat test card | 2026-09-15, `packet` sizes at the sender |
| Splitting into 16-row stripes | costs 2.2% over one stream | 4 channels x 10 s |
| Adaptive palette vs fixed 3-3-2 | RMSE 10.1 against 28.2 | same frames; **only for the frame it was sampled from**, see section 2 |
| `-sws_dither none` | worst frame 31 KB to 23 KB | measured |

The figure of 15-22 KB per frame that earlier notes carried is wrong. Nothing
measured lands in that range, and reasoning built on it came out about half of
what it should have been.

### The receive path

| Item | Value | Note |
| --- | --- | --- |
| Packet ceiling | about 72 a second, of any size | measured on the device |
| Sound alone | 50 packets a second, indefinitely | zero underruns |
| Old design (160x120 JPEG) | 12 picture packets a second, about 73 kB/s | runs on this device |
| Device decode | 3 to 46 ms a frame | not the constraint |
| Device decode, re-measured | 64 to 146 ms a frame, worst frame in the interval | 4 frames a second, 13:50 build |
| `hdrgap_max`, steady state | 93 to 163 ms at 4 fps, 72 to 87 ms at 8 fps | added 13:50; the 2500 ms reading is the opening prebuffer |
| Server capability | 120 packets a second, 510 kB/s | not the constraint |
| pocket-tv transport | USB serial at 115200 | its flow control does not transfer |

The two decode figures do not agree, and the later one is the one taken with
the picture actually flowing: `decode_max_ms` is the worst single frame in a
ten-second interval, so it is a peak and not an average, and at 4 frames a
second the peak sits well above the earlier 3-to-46 ms range. The device spends
about 0.5 seconds of every ten inflating at 4 frames a second, so decoding is
still not what limits the frame rate, but the margin is smaller than the first
figure suggests.

This table used to end by saying the constraint is the number of packets and not
the number of bytes. Section 5 measures the opposite and supersedes it: at 8
frames a second the device keeps up perfectly well when the picture is small,
and falls over when it is large. The packet budget is real -- one task reads the
socket, so a picture packet delays the sound, and the sound queue holds about
600 ms -- but it is not what is being hit. Bytes are.

### Device structure

- Video queue and free-buffer queue are both 2 deep
- The audio and video paths were designed around one packet per frame
- Task priorities: **receiver 6, video 5**, audio 7 (changed 2026-09-15; was video 6, receiver 5)

## 2. The colour fault: a frozen palette. Fixed.

This is the fault the viewer reported as "sometimes normal, sometimes grey,
sometimes green, sometimes brown", and the reason it survived every check made
against a still test card: a static card contains all its colours in its first
frame, so a palette sampled from the opening seconds of a stream is exactly
right for it. Only moving content shows the fault.

**The cause.** Every live picture is drawn from a 256-entry palette, and the
palette was chosen adaptively -- by sampling about a second and a half of the
source when the channel opened, then frozen for the rest of the session. It
cannot be changed afterwards without re-indexing every picture and telling the
device. So whatever is on screen later is drawn in the colours of whatever was
on screen in those first seconds: a fade, a title card, a studio caption.

Measured on a clip that opens dim and brown and then cuts to colour bars:

| frame at 2.5 s drawn with | error against its true colours |
| --- | --- |
| the palette sampled from the opening scene | RMSE 275 (of 255) |
| a palette sampled from that frame itself | RMSE 0.00 |
| the fixed 3-3-2 grid | RMSE 57 |

A stale adaptive palette is not a tint. It is a different picture.

Two smaller faults sat inside the same code. `palettegen` was given
`stats_mode=single` with `-frames:v 1`, and `single` computes its histogram per
frame rather than accumulating -- so the "sample a second and a half so that one
outlier frame cannot decide the palette" that the function's own comment
promised was, in the code, "use the first frame". And the rawvideo reader still
skipped a 1024-byte palette block per frame, which `rgb8` does not write.

**The fix.** The palette is now a constant: ffmpeg's own 3-3-2 grid, which the
device already implements in `av_palette_rgb565`. Nothing is sampled, so nothing
can be stale. The grid's bit order was checked by encoding pure red, green and
blue and reading the indices back -- 0xE0, 0x1C, 0x03, which is RRR GGG BB and
matches the device's table on all 256 entries.

**It is also smaller, which was not expected.** The adaptive palette was assumed
to be worth about 2x on easy content, and the fixed grid to give that up. On the
same 20 seconds of a live channel:

| | median frame | worst frame |
| --- | --- | --- |
| fixed 3-3-2 | 21087 B | 28643 B |
| adaptive, sampled from that same clip | 24604 B | 36765 B |

A regular grid is more temporally consistent -- flat areas land on the same
index from frame to frame -- and deflate finds more to point at. So the fix
costs nothing and buys a picture that is always the right colour.

On hardware, same channel, fixed palette: 6 fps for 180 s gave one reset against
three in 300 s before, and a single 240-second run at 8 fps gave none at all.
That run was luck and is recorded here only because it was later contradicted:
nine minutes at 8 fps gave 5 resets. The palette fix makes frames about 15%
smaller, which helps, and it does not by itself make 8 frames a second hold. See
section 6 for what does.

## 3. The panel's rendering is correct. Measured, not inferred.

This is the first thing this list said was unknown, and it is now settled. The
screen capture facility existed in the source but had never been compiled: the
`AV_SCREEN_CAPTURE` macro it is guarded by was not defined anywhere in the
repository, in any configuration. "The device can now take a picture of it" was
written into an earlier version of this document without that having been
checked. It is a `Kconfig` option now, off by default.

With a controlled source -- grey steps of 0, 36, 73, 109, 146, 182, 219 and 255
across the width, the same ramp in the lower half tinted towards red -- the
panel's own input was read back and compared:

| step | source | panel | ratio |
| --- | --- | --- | --- |
| 36 | 36 | 32 | 0.89 |
| 73 | 73 | 74 | 0.99 |
| 109 | 109 | 106 | 1.00 |
| 146 | 146 | 148 | 0.99 |
| 182 | 182 | 180 | 1.00 |
| 219 | 219 | 222 | 1.00 |
| 255 | 255 | 255 | 1.00 |

and on the tinted half, where the source asks for (36, 9, 9) the panel has
(32, 8, 8), and for (182, 45, 45) it has (180, 44, 41). The residues are not a
fault: they are exactly what quantising to RGB565 does, 36 to 32 and 9 to 8
being the 5-bit and 6-bit steps. Colours are also not permuted -- a green, red,
blue pattern arrives green, red, blue.

**The device's rendering is not where the colour fault was.** The protocol, the
index expansion and the panel timing are all correct as measured. The fault was
upstream of it, in which palette the server sent -- section 2.

A warning this measurement carries, and the reason the fault survived it: a
still test card cannot detect a palette fault. It contains every colour it will
ever show in its first frame, so a palette sampled from the opening second of a
stream is exactly right for it. The card was useful -- it proved expansion and
panel timing -- and it was answered as though it covered colour. It did not.

An earlier reading suggested the panel was about 0.70 times too dark. It is not:
that figure came from comparing a panel capture against a source sampled at a
different instant, and it is not usable.

## 4. State as of 2026-09-15, 14:00

The device runs the prototype firmware built at 13:50, from `sdkconfig.av-prototype`
with `CONFIG_AV_SCREEN_CAPTURE=y`.

**Receiving is healthy at 4 frames a second.** Over a 63-second run against a
local test stream: 40 frames every 10 seconds against a target of 40, 500 to 502
audio packets every 10 seconds against 500, `dropped=0`, `nobuf=0`, `late=0`.
That run ended because the test file itself ends at 60 seconds, not because
anything failed.

Two services changes are in place and confirmed on hardware: the picture is
scheduled by timeline slot rather than by a due time, and a frame is packed to
the protocol ceiling rather than to 4 KB.

**One destructive operation**: a merged image was written from offset 0, which
overwrote the NVS partition at 0x9000 and erased the device's stored Wi-Fi
credentials and server address. The partition was restored from the 2026-09-14
full reading and the device rejoined the network. `docs/local-tv-prototype.zh_CN.md`
forbids writing a merged image, and only the application partition at 0x10000 is
written since.

## 5. The ceiling is bytes, not frames. Measured.

This is the session's main result and it replaces the guess that the device runs
out of packets. The same test card -- large flat areas, so a frame compresses to
about 2.4 kB -- plays at 8 frames a second indefinitely: eleven consecutive ten
-second intervals at 80 frames each, 500 to 504 audio packets each, no resets at
all in 150 seconds. That is 8 frames a second with the sound running, which the
engine had never done.

The picture stops being reliable when the bytes go up:

| source | frame rate | bytes a second | outcome |
| --- | --- | --- | --- |
| test card | 8 | about 18 kB | no faults in 150 s |
| live channel | 4 | about 65 kB | 1 reset in 200 s |
| live channel | 6 | about 123 kB | 3 resets in 300 s, 8 of 18 intervals degraded |
| live channel | 8 | about 210 kB | 6 resets in 240 s |

A live 320x240 frame measures 11 to 16 kB compressed, so the frame rate is really
a bytes-a-second dial. The failure is always the same: the server sends 50 audio
packets a second and the device counts 317 to 361 of them arriving over the same
ten seconds. **The missing packets are lost between the two**, and the picture's
bytes are what make them lost.

Three explanations were tested and rejected:

- *The sender stops.* Rejected. The server's longest gap between writes is 123 to
  388 ms and it is never blocked for longer; over a ten-second interval it is
  occupied for 0.0 to 1.1 s.
- *The device stalls between packets.* Rejected. The counter added for this
  (`hdrgap_max`) reads 72 to 109 ms in steady state at 8 frames a second. The
  2500 ms figure that appears once per session, at the start, is the sender's
  deliberate three-second audio prebuffer.
- *The sender's audio catch-up burst overflows the device.* Rejected, and the
  test is worth recording because the reasoning was plausible and wrong. Cutting
  the catch-up from 32 chunks to 6 should have reduced the burst to below the
  device's receive pool; it made things distinctly worse -- eighteen failed
  sessions in two and a half minutes, against a handful before. A shallow
  catch-up cannot repay the audio the picture withheld, so the deficit grows and
  the sound underruns for want of sending. It is back at 32.

**This table was measured with the adaptive palette**, which is gone. With the
fixed grid frames are smaller (section 2: median 24604 B down to 21087 B) and the
same channel ran 8 frames a second for 240 seconds with no resets at all. The
"four is the ceiling" conclusion therefore belongs to the old palette and is
superseded; the new ceiling is still being measured.

## 6. The frame rate ceiling was a task priority. Fixed.

Section 5 concluded that the ceiling was bytes a second and left the mechanism
unexplained. The mechanism is in `main/av_player.c`: the task that reads the
socket was created at priority 5, below the video task at 6, on one core. While
the video task inflated a stripe -- measured at up to 146 ms, and 1.6 seconds of
every ten at 8 frames a second -- nothing read the socket at all. The server's
writes went undrained for that long, its audio fell behind by exactly that much,
and the session ended on an audio underrun the link had nothing to do with.

The ordering was deliberate and the comment defending it was about a real
hazard: the receiver hands out the buffers the video task returns, so a receiver
that can *wait* for a buffer while outranking that task deadlocks. But the wait
here has a zero timeout -- `xQueueReceive(s.free_video,&v.jpeg,0)` -- and a
receiver that finds none discards the packet and reads on. It never blocks, so
it can never hold the video task off the processor. The hazard did not apply and
the cost of guarding against it was the whole frame rate.

**Receiver 6, video 5.** Audio stays at 7.

| | healthy intervals | median frames / 10 s | server failures |
| --- | --- | --- | --- |
| before, live channel at 8 fps | 7 of 26 | 43 | 25 |
| after, same channel, same source | 30 of 37 | 79 | 9 |

The ceiling moves with it. Live channel at 8 frames a second holds 79 of 80 and
`dropped` stays at 0 or 1 with every frame complete (`maxstripes=15/15`); at 10
the median falls to 88 of 100 and half the intervals degrade. **`TV_FPS` is now
8.**

Two other things were tried against the same symptom and both were wrong, which
is why the note above is worth its length:

- **Enlarging the Wi-Fi receive pool** from 6+16 buffers to 6+32, on the theory
  that the arriving bytes had nowhere to go while nothing drained the socket.
  No effect whatever: 7 healthy intervals of 25, against 11 of 33 before.
- **Testing a different source.** The viewer pointed out that only one channel
  had been used and it might itself be unstable. The official broadcaster's
  stream was substituted -- verified to deliver exactly 8 frames a second -- and
  behaved identically, 7 of 26 with 25 failures. The source was never the
  problem, and the suggestion was still worth following because it ruled out a
  whole class of explanation.

## 7. Not yet known

**Why the link drops at these rates.** The counters establish *that* packets are
lost, not why. The candidates are the shared 2.4 GHz channel, the Mac's own Wi-Fi
queue, or the device's receive path, and separating them needs either the
platform's TCP counters or a capture of the air -- see below.

**How many packets the device can really take.** 72 is inferred from one set of
runs, not established by a sweep. It is no longer the operative figure: the
ceiling measured above is bytes a second, and it is reached well before the
packet count is.

## 8. What is not measurable on this machine

`netstat -s -p tcp` on macOS reports every TCP counter as zero -- it is
documented as unavailable there rather than genuinely idle. A reading of "zero
retransmits" was taken from it during this session and is void; it was used to
rule out packet loss, and packet loss has therefore not been ruled out by it.
The platform's counters are in `sysctl net.inet.tcp.stats`, which is not writable
without root, and `tcpdump` needs `sudo`. Measuring retransmissions here needs
one of those, or a wired link.

The loss itself is nonetheless established, and without either: the sender's own
count of audio packets written and the receiver's own count of audio packets
read are both taken on the device's clock, over the same interval, and they
disagree by 140 to 180 packets in ten seconds. No platform counter is needed for
that.

## 9. Faults introduced during this session, and fixed

Recorded because each cost hardware time and each was found by reading back a
measurement rather than by reasoning:

- **A format string with one more conversion than arguments.** Adding
  `hdrgap_max=%u` to the interval log without adding the argument made `printf`
  read a pointer from the stack and dereference it. The device panicked every
  session with `Load access fault` and the log ended mid-line. Resolved by
  `riscv32-esp-elf-addr2line` to `shot_print`, which was the first suspect only
  because the crash arrived with a capture build; the counter was the real
  cause.
- **The capture buffer starved the channel list.** Allocated when the capture
  was armed -- before the first CONFIG arrived -- its 9600 bytes took the free
  heap below what parsing the channel list needs, and every session ended at
  `config-validation` with "No memory to parse the channel list". It is now
  taken and given back inside the frame that is kept.
- **The capture printed from a null pointer.** After moving the allocation
  later, it was taken one frame after the counter that printed it, so the print
  ran against a null buffer and faulted. The allocate, fill and print now all
  happen within one frame.
- **A firmware flash that was not the prototype.** `idf.py build` with the
  default `sdkconfig` produced the demonstration application, and flashing it
  replaced the player. The prototype needs
  `-D SDKCONFIG=...` pointing at a build directory; the `SDKCONFIG_DEFAULTS`
  environment variable alone is not read by `idf.py`.

## 10. Working rules

Three repetitions happened in one day: reading a playback rate as link
throughput (twice), and restoring an arrangement a log had already rejected
(once). All three came from acting before reading.

Before changing anything, read `docs/development/`, `docs/CHANGELOG*.md`, and
the memory entries tagged `ai-passport-tv`, and check whether the question has
already been answered.
