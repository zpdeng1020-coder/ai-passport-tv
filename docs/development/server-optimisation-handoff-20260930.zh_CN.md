# 服务端优化方向交接（2026-09-30）

**做服务端或画质相关工作前先读这一份。**它记录设备端冻结之后的状态：服务端现在做什么、什么还没有确认、按顺序接下来该做什么。它的来源传输改造见 [tcp-delta-progress-20260930.zh_CN.md](tcp-delta-progress-20260930.zh_CN.md)；那份文档里设备端的部分仍然有效，服务端的部分已经过期。

这些改动已提交在 `feature/cjpjxjx` 分支上。

**本文有意不记录任何按频道或按链路的数字。**一个频道每帧花多少字节、一条链路能承载多少、某一次运行测到的帧率，都随内容和网络变化，不是关于这个项目的事实。请在手头的频道和链路上重新测；工具见第 6 节。

## 1. 定下来的取舍

帧率**固定**，字节速率**固定**，放不下的时候牺牲画面的**细节**。

帧率变动是观看者最容易察觉的，而画面短暂变粗基本不会。所以一个频道整个会话都用源自身的帧率播放，每帧都被压到「目标字节速率除以帧率」以内（默认目标是每帧 20000 字节，即 `TV_FRAME_BYTES`，所以字节速率随帧率走：25 fps 为 500 kB/s，30 fps 为 600 kB/s）。放不下就变粗直到放得下。为了达到目标，画面可以变粗到什么程度是没有上限的。

**固定模式是默认，也是要先做好的那个。**自适应字节速率控制器（`rate.ByteRate`）仍然存在，用 `TV_ADAPTIVE=1` 开启，同时要把 `TV_RATE_MAX` 抬到起步值以上。固定模式做好之前不要考虑它：控制器挪动目标，画质也跟着挪，之后对画面的任何判断都变成对控制器的判断。

它取代的是：一个依据写入耗时和丢帧在 3 到 12 之间调帧率的控制器，每个频道的上限由 `预算 / 每帧字节数` 推出。它的预算从未作为链路上限测量过，并且把帧率压得远低于同一条链路、同一份固件在控制器不动时能承载的水平。见进度文档第 1 节。

## 2. 服务端现在做什么

| 位置 | 做什么 |
|---|---|
| `server/live.py` `probe_source_fps` | 启动时用 `ffprobe` 问频道帧率：优先 `avg_frame_rate`（25 fps 的节目以 50 场传输时，`r_frame_rate` 是 50 而 `avg_frame_rate` 是 25），超过 30 就对半折算——30 是设备自身的上限（`main/av_player.c` 里的 `json_between(j,"fps",1,30)`）。按 URL 缓存。显式设置 `TV_FPS` 就跳过探测；源不回应时按名义 25 |
| `server/live.py` `LiveChannel.fps`、`source_graph`、`source_command` | 探测到的帧率同时进入 ffmpeg 滤镜图、内容时间轴和发送侧节拍，三者从构造上就一致 |
| `server/rate.py` `ByteRate` | 默认把字节速率固定在 `TV_FRAME_BYTES` × 帧率（`TV_ADAPTIVE` 关闭，原因显示 `fixed`）。`TV_ADAPTIVE=1` 时才调速率：写入超过 250 ms 或连续两个窗口有丢帧就立刻降；连续两个窗口写入低于 120 ms **并且**用掉了至少 80% 的速率才涨 5%。第二个条件才是关键：静止画面因为字节少所以写得快，靠这个涨速率等于给下一次场景切换放开闸门 |
| `server/frames.py` `encode_within` | 逐帧：先按当前画质压缩，再逐级放粗颜色（红绿 8→4→3→1 级，蓝 4→1 级），取第一个放得进「速率 ÷ 帧率」的，帧与帧之间不保留状态。发出的每个条带都来自当前帧。只有最粗一档仍放不下时才丢条带，按变化量从大到小 |
| `server/perceptual.py` `encode_within` | **装了 numpy 时默认开启**（`TV_PERCEPTUAL=0` 或没有 numpy 就用上一行的颜色阶梯）。放得进目标的帧原样发出 ffmpeg 生成的画面。放不进的帧不走阶梯：只要调色板里的这个颜色与参照像素的距离在逐帧阈值之内，像素可以沿用设备的值或左邻值（10 档，先试 0 档，再从上一帧的档位开始搜索）。放得下时耗时与之前相同，放不下时约 14–18 ms |
| `server/frames.py` `choose_stripes` | 发哪些条带：每帧轮换刷新一个，其余按与设备当前画面的差异像素数排序，直到花完目标。没轮上的条带下一帧排序只会更高，不需要任何记账 |
| `server/tv_server.py` `_pace_live` | 读取 `channel.fps`，驱动 `ByteRate`，每秒把速率推给频道。时隙算法未变 |
| `server/media.py` | `FPS` 是名义 25，用于 CONFIG 的 `fps` 字段和预生成媒体。设备只检查它的范围，所以可以在看源之前就发出去 |

delta **默认开启**（`TV_DELTA=1`，容差 `TV_DELTA_MAX_DIFF=0.01`）。长度为 0 的条带正是设备会跳过的，所以**旧固件会在第一个这样的条带上结束会话**；要么刷配套固件，要么设 `TV_DELTA=0`。

可选的 v2 发送器（`TV_LIVE_ENGINE=v2`，`server/live_sender.py`）**不受以上任何改动影响**：它仍然驱动旧的 `RateController` 和它自己那套 64 KB/s 字节预算。这是有意不碰，而不是迁移了一半。`media.FPS` 不再等于 `rate.MAX_FPS` 会悄悄改变它的默认上限，所以那一行改为直接读 `rate.MAX_FPS`。

## 3. 学到了什么

这些是关于设计的结论，不是可以拿来依赖的数字。

**每帧硬性大小上限是错的，正是这一点定下了设计。**把每帧硬卡在很小的固定大小时，一帧里每个条带都变了就没办法整帧发出，新场景只能一块一块到达：可见的上一场景横带，最差帧的 PSNR 极低。让切换整幅放行、之后几帧还债（早先的令牌桶规则）消除了横带。现在的规则改成让画面变粗，这样每个条带都是当前帧的。

**用颜色阶梯变粗不是对字节最划算的用法，感知式取舍现在已经实现（`server/perceptual.py`）。**在字节数大致相同时，它比阶梯好 2 到 9 dB（对原始画面的 PSNR，3 个频道，各 100 帧，离线），并且在阶梯会崩成乱码的最紧目标下退化得很平缓。这些是当时正在播出的内容上的静止帧 PSNR，只能说明排序，不是可以引用的数字。阶梯每次跳一整档，会落在目标远下面、浪费剩下的预算，逐帧阈值搜索则不会。

**第一版是错的，错法值得留下。**它把画面当 RGB 处理，把每个像素映射到**最近**的调色板色，按 PSNR 好约 2 dB、字节少 8%–14%。观看者拿它和默认对比，否决了：ffmpeg 的转换偏暗、偏中性，而最近色会让深灰变蓝、在阴影里出现彩色斑块，因为蓝只有 4 级、在误差里权重又小。**PSNR 不是观感的代理指标。**观看者觉得正常的画面就是 ffmpeg 自己的索引帧，所以现在以它为参照，取舍在调色板空间里对它进行。

**多久触发一次取决于目标和内容，目标调低后会变得常见。**繁忙频道的帧大小常常就在目标附近，目标差几 KB，触发的帧占比就能从百分之几变成三分之一以上。不触发的时候，观看者看到的是固定 3-3-2 调色板本身，与字节预算无关。取舍是给突发、切镜和更紧的目标用的；想提升日常颜色，要改的是表示方式（自适应调色板、更多位数），不是预算逻辑。

**编码开销随内容变化。**颜色阶梯每帧最多要压六次，所以在画面繁忙的内容上每帧耗时是单独条带选择的数倍。在最忙的频道上先测过再加每帧的工作；相对帧间隔的余量就是它的预算。

## 4. 尚未确认的事

1. **在每帧 20 KB 的目标下，繁忙内容上的变粗曾经是可见的。**这是观看者自己的报告。这是首要未解问题：机制是对的，画质损失还不能接受。
2. **每帧 20000 字节的目标是操作者的选择，不是测得的链路上限。**某条链路承不承得住，靠写入耗时和丢帧数判断，这是仅有的两个工具——仍然没有设备反馈。固定模式下链路变差时没有任何东西让发送端慢下来；写入卡住的代价是丢帧。
3. **设备的帧率上限还没有找到。**固件拒绝任何高于 30 的帧率（`main/av_player.c` 里的 `json_between(j,"fps",1,30)`），一段纯静止画面在板子上一次运行里守住了这个 30 fps，所以 30 是测试停下的地方，不是设备的极限。要找上限，得先在固件里放宽这个界限。另外，字节目标是**单帧的上限，不是实际发送量**：大多数帧远低于它，所以线上的字节速率通常低于配置的速率。要按配置速率做负载测试，需要每帧真的花那么多字节的内容；用无法压缩的内容测出来的是最坏情况，不是帧率。
4. **压力下的画质还没有在足够多的频道上被人当动态画面看过。**产生过的所有画质数字都是静止帧上的 PSNR。
5. **帧率探测没有对真实 HLS 播放列表验证过。**只用本地文件和打桩的 `ffprobe` 测过。真实 HLS 播放列表经常不报告 `avg_frame_rate`。
6. **改动之后没有重新调参。**`AUDIO_LEAD_MS`、`PREBUFFER_SECONDS`、`VIDEO_QUEUE_SECONDS` 和时隙节拍都是在帧率在 3 到 12 之间变动、画面还很小的年代选的。都没有重新审视过，而且已经能看到一个可疑点：25 fps 下 16 秒的视频队列是 400 帧。
7. **验证缺口。**`python3` 是 Microsoft Store 占位程序、没有原生 C 编译器或 `actionlint` 的机器上，`tools/validate.sh` 跑不了。三个 Python 测试失败——`test_live_transcode.py` 的 `test_live_mode_signal_handler_stops_the_accept_loop`，以及 `test_tv_server.py` 的 `test_environment_and_restricted_token_file` 和 `test_fragmented_and_coalesced_stream`——把改动 stash 掉同样失败。新展开函数的宿主机 C 测试只做了语法检查。
8. **频道地址会失效。**频道表里是公共流，条目会无声地失效（默认的 `ch000` 最近一次试的时候返回 404）。会话停在 `live_palette` 失败，多半是源的问题，不是服务端；先查地址，再怀疑代码。
9. **8096 端口上的旧服务端浪费了将近一天。**上一个会话遗留的服务端一直占着端口，于是设备连的是它，而新服务端什么都没记录。所有症状看起来都像设备或固件故障。先查 `netstat -ano | grep :8096`。
10. **`tools/launch.py` 不传 `--bind`**，而媒体服务器没有显式的回环或 RFC1918 地址就拒绝启动，所以启动器会以「程序没能启动」退出。异常是有意被吞掉的，所以原因看不到。请直接带 `--bind` 启动服务端（第 6 节）。

## 5. 接下来的步骤，按顺序

1. **把感知式取舍当动态画面看一遍。**它已经实现，并在板子上跑过（读取了一个 45 秒的窗口，帧率在目标值、设备无丢帧），但还没有人评判过画面。在同一个频道上对比 `TV_PERCEPTUAL=0` 和默认值。然后判断固定 3-3-2 调色板本身是不是上限，因为字节预算很少吃紧（见第 3 节）。
   还没做：打包（`tools/build_server.py`）没有带上 numpy，所以打包版本走阶梯；编码在发送线程里持频道锁运行，典型耗时可以承受，最坏的 14–18 ms 只剩大约半帧的余量。
2. **按固定 25–30 fps 的画面重新调队列深度和前导量。**最便宜的改动，可能换来延迟下降；那些数字是按 3–12 fps 的发送者选的。
3. **在多个频道和弱网下检验目标能否守住**，要包含剧烈运动的内容，并据此决定 每帧 20000 字节是否该是默认值。
4. **至少三个频道上把画面当动态画面看一遍**，在固定目标下，然后才有资格称这次改动是改进。这是项目一直缺的验收。
5. **考虑 4 位自适应调色板**（早先离线结果：在安静内容上字节更少，而且 PSNR 比 3-3-2 更好）作为字节问题的真正解法，它能减轻变粗的压力。它需要改设备端解码，所以是联合改动，不是快速改动能解决的。
6. **这之后才考虑自适应控制器**（`TV_ADAPTIVE=1`）。

## 6. 复现

```text
# 服务端，默认：固定每帧 20000 字节（字节速率 = 它乘以源的帧率）。--bind 必须是本机的回环或私有地址。
# 选一个当前能播的频道（ch000 可能已失效）。
python -m server.tv_server live --channel <频道 id> --bind <本机地址>
# 换一个固定目标（或用 TV_RATE_START=<字节每秒> 直接设速率）：
TV_FRAME_BYTES=12000 python -m server.tv_server live --channel <频道 id> --bind <本机地址>
# 自适应控制器，需要主动开启（要抬上限，否则涨不上去）：
TV_ADAPTIVE=1 TV_RATE_MAX=600000 python -m server.tv_server live --channel <频道 id> --bind <本机地址>

# 离线：帧大小、条带选择与逐帧颜色阶梯
PYTHONPATH=. python tools/budget_lab.py /path/<频道>.ts --frames 200 --rates 500000
# 离线：以原始画面为参照的画质，四种方法（需要 numpy）
PYTHONPATH=. python tools/quality_lab.py /path/<频道>.ts

# 测试
PYTHONPATH=. python tests/test_rate.py && PYTHONPATH=. python tests/test_delta_encoding.py && PYTHONPATH=. python tests/test_fixed_rate.py
```

