# 服务端优化方向交接（2026-09-30）

**做服务端或画质相关工作前先读这一份。**它记录设备端冻结之后的状态：服务端现在做什么、测到了什么、什么还没有确认、按顺序接下来该做什么。它的来源传输改造见 [tcp-delta-progress-20260930.zh_CN.md](tcp-delta-progress-20260930.zh_CN.md)；那份文档里设备端的部分仍然有效，服务端的部分已经过期。

本文所有内容都**未提交**。工作区里是两天的成果（delta 编码、流式条带接收、固定帧率服务端、固件改动），都叠在提交 `c61b764` 之上。

本文里所有数字要么是**在录制素材上离线测量**，要么是**对设备板的单次运行**。没有任何一项重复测量，画质数字是 PSNR，它只是代理指标，不是观看者的判断。

## 1. 定下来的取舍

帧率**固定**，链路吃紧时牺牲画面的**细节**。

帧率变动是观看者最容易察觉的，而画面短暂变粗基本不会。所以一个频道整个会话都用源自身的帧率播放，控制器调的是画面每秒可以花多少**字节**。每帧被压到「字节速率除以帧率」以内，放不下就变粗直到放得下。

它取代的是：一个依据写入耗时和丢帧在 3 到 12 之间调帧率的控制器，每个频道的上限由 `预算 / 每帧字节数` 推出。它的预算（185000 B/s）从未作为链路上限测量过，而在它生效时设备只能画出 12 fps，同一条链路、同一份固件在把控制器固定在某个速率时能画出 24.3 fps。那次测量见进度文档第 1 节。

## 2. 服务端现在做什么

| 位置 | 做什么 |
|---|---|
| `server/live.py` `probe_source_fps` | 启动时用 `ffprobe` 问频道帧率：优先 `avg_frame_rate`（25 fps 的节目以 50 场传输时，`r_frame_rate` 是 50 而 `avg_frame_rate` 是 25），超过 30 就对半折算——30 是设备自身的上限（`main/av_player.c` 里的 `json_between(j,"fps",1,30)`）。按 URL 缓存。显式设置 `TV_FPS` 就跳过探测；源不回应时按名义 25 |
| `server/live.py` `LiveChannel.fps`、`source_graph`、`source_command` | 探测到的帧率同时进入 ffmpeg 滤镜图、内容时间轴和发送侧节拍，三者从构造上就一致 |
| `server/rate.py` `ByteRate` | 控制器。帧率固定，调的是字节速率：写入超过 250 ms 或连续两个窗口有丢帧就立刻降；连续两个窗口写入低于 120 ms **并且**用掉了至少 80% 的速率才涨 5%。第二个条件才是关键：静止画面因为字节少所以写得快，靠这个涨速率等于给下一次场景切换放开闸门 |
| `server/frames.py` `encode_within` | 逐帧：先按当前画质压缩，再逐级放粗颜色（红绿 8→4→3→1 级，蓝 4→1 级），取第一个放得进「速率 ÷ 帧率」的，帧与帧之间不保留状态。发出的每个条带都来自当前帧。只有最粗一档仍放不下时才丢条带，按变化量从大到小 |
| `server/frames.py` `choose_stripes` | 发哪些条带：每帧轮换刷新一个，其余按与设备当前画面的差异像素数排序，直到花完目标。没轮上的条带下一帧排序只会更高，不需要任何记账 |
| `server/tv_server.py` `_pace_live` | 读取 `channel.fps`，驱动 `ByteRate`，每秒把速率推给频道。时隙算法未变 |
| `server/media.py` | `FPS` 现在是名义 25，用于 CONFIG 的 `fps` 字段和预生成媒体。设备只检查它的范围，所以可以在看源之前就发出去 |

delta 现在**默认开启**（`TV_DELTA=1`，容差 `TV_DELTA_MAX_DIFF=0.01`）。长度为 0 的条带正是设备会跳过的，所以**旧固件会在第一个这样的条带上结束会话**；要么刷配套固件，要么设 `TV_DELTA=0`。

可选的 v2 发送器（`TV_LIVE_ENGINE=v2`，`server/live_sender.py`）**不受以上任何改动影响**：它仍然驱动旧的 `RateController` 和它自己那套 64 KB/s 字节预算。这是有意不碰，而不是迁移了一半。`media.FPS` 不再等于 `rate.MAX_FPS` 会悄悄改变它的默认上限，所以那一行改为直接读 `rate.MAX_FPS`。

## 3. 测到了什么

离线，在录制频道上（本地录制的频道素材，25 或 30 fps，200 帧），在开发机上，期间没有并发运行 ffmpeg。

**控制器不再是帧率上限。**旧控制器下产品跑 12 fps；把帧率固定在源自身的速率、控制器关掉，设备在一次 90 秒运行里画出中位 24.3 fps、349 KB/s。现在动的是字节速率。

**每帧硬性大小上限是错的，正是这次测量定下了设计。**把每帧硬卡在 9–12 KB 时，最忙频道的最差帧只有 **PSNR 11 dB**，并出现可见的上一场景横带：一帧里每个条带都变了，就没有任何办法只用 10 KB 发出它，于是新场景只能一块一块到达。让切换整幅放行、之后几帧还债（早先的令牌桶规则）消除了横带。现在的规则改成让画面变粗，这样每个条带都是当前帧的，在同一频道上 16 KB 时是 17.95 dB，9–12 KB 时是 10.7–10.9 dB。

**字节花在哪里。**每帧、无损、200 帧：

| 频道 | 整帧 | delta，3% 容差 | 比例 |
|---|---|---|---|
| CCTV6（30 fps，基本静止） | 6.1 KB | 0.5 KB | 8% |
| DFWS | 10.2 KB | 6.2 KB | 61% |
| HEBEI（25 fps） | 12.6 KB | 10.3 KB | 82% |
| CCTV1（25 fps） | 13.6 KB | 7.9 KB（p95 19 KB） | 58% |
| CCTV13（25 fps，最忙） | 22.4 KB | 16.9 KB | 75% |

按 25 fps 折算，需要约 30 KB/s（CCTV6）到 421 KB/s（CCTV13）。只有最忙的频道超过设备已被证明能接收的 349 KB/s，所以大多数频道是在源自身帧率下无损播放，那些额外的工作根本不会发生。

**按省下的字节算，变粗付出的画质比其它做法少。**CCTV13，60 帧，以原始彩色画面为参照的加权平方 RGB 误差：

| 方法 | 每帧字节 | PSNR |
|---|---|---|
| 无损 | 13.2 KB | 21.0 dB |
| 颜色阶梯，目标 16 KB | 8.2 KB | 18.0 dB |
| 颜色阶梯，目标 12 KB | 4.2 KB | 10.9 dB |
| **感知式取舍，阈值 4000** | 9.0 KB | **21.2 dB** |
| 感知式取舍，阈值 16000 | 6.1 KB | 19.1 dB |

「感知式取舍」尚未实现：逐像素决定是否沿用设备已持有的值或左邻值，条件是它与该像素真实颜色的差异小于阈值，从而让 deflate 看到更多重复。同样字节数下好约 2.5 dB，而且在颜色阶梯会崩掉的档位它退化得很平缓。它需要原始 RGB（ffmpeg 输出帧数据变 3 倍）以及 numpy，而服务端目前完全没有第三方依赖。`tools/quality_lab.py` 可以重跑出这张表。

**编码开销。**单独 `choose_stripes` 在 Python 里是每帧 0.3–2.6 ms（六个频道）。加上颜色阶梯后，在最忙频道上最高 **8.3 ms 每帧**，因为每帧最多要压六次。相对 40 ms 的帧间隔还可承受，但余量从 20 倍变成 5 倍。

**对设备的实测，真实 CCTV1**（一个会话，747 秒，无故障）：帧率固定在 25，字节速率爬到 583 kB/s，写入耗时 31–78 ms，设备两个 10 秒窗口是 24.5 和 24.1 fps、丢 4 帧、无音频中断、无重置。在该码率下观看者报告没有卡顿也没有撕裂。同一份代码固定在 500 kB/s 时，观看者认为变粗**明显可见**。

## 4. 尚未确认的事

1. **要维持每帧 20 KB，变粗就明显可见。**这是观看者自己在真实 CCTV1、500 kB/s 下的报告。这是首要未解问题：机制是对的，画质损失还不能接受。
2. **三个码率默认值是猜的。**`TV_RATE_START=250000`、`TV_RATE_MAX=320000` 来自一次 90 秒单频道、总计 349 KB/s 的测量。真正起作用的上限是链路的上限，而测量它的工具只有写入耗时和丢帧数——仍然没有设备反馈。
3. **压力下的画质从没被人当动态画面看过**，任何频道都没有。上面每个数字都是静止帧上的 PSNR。
4. **一条链路、一个频道、一个观看者。**第 3 节里设备侧的内容全部是热点上的真实 CCTV1，总计约 20 分钟。
5. **帧率探测没有对真实 HLS 播放列表验证过。**只用本地文件和打桩的 `ffprobe` 测过。真实 HLS 播放列表经常不报告 `avg_frame_rate`。
6. **改动之后没有重新调参。**`AUDIO_LEAD_MS`、`PREBUFFER_SECONDS`、`VIDEO_QUEUE_SECONDS` 和时隙节拍都是在帧率在 3 到 12 之间变动、画面还很小的年代选的。都没有重新审视过，而且已经能看到一个可疑点：25 fps 下 16 秒的视频队列是 400 帧、约 13 KB 一帧。
7. **验证缺口。**`tools/validate.sh` 在这台机器跑不了（它的 `python3` 是 Microsoft Store 的占位程序，也没有原生 C 编译器和 `actionlint`）。四个 Python 测试失败和一项固件测试早于本次改动，把改动 stash 掉同样失败。新展开函数的宿主机 C 测试只做了语法检查。
8. **8096 端口上的旧服务端浪费了将近一天。**上一个会话遗留的服务端一直占着端口，于是设备连的是它，而新服务端什么都没记录。所有症状看起来都像设备或固件故障。先查 `netstat -ano | grep :8096`。

## 5. 接下来的步骤，按顺序

1. **解决可见的变粗**，也就是第一个未解问题的全部。实现感知式取舍（`tools/quality_lab.py` 既是参照也是测量），并对阈值做二分以命中目标。它要么需要 ffmpeg 给出原始 RGB（在现有 socket 上加第二路输出，到父进程的字节数变 3 倍），要么用索引反算颜色距离，后者更弱。**服务端是否允许依赖 numpy 需要由操作者决定**；不依赖的话，25 fps 下用纯 Python 做逐像素运算是否划算并不显然，在承诺之前必须先测。
2. **按固定 25–30 fps 的画面重新调队列深度和前导量。**最便宜的改动，可能换来延迟下降；那些数字是按 3–12 fps 的发送者选的。
3. **在多个频道和弱网下重测码率范围**，决定上限该是多少。要包含剧烈运动的内容；CCTV13 是目前唯一录下的繁忙样本。
4. **至少三个频道上把画面当动态画面看一遍**，在控制器实际稳定下来的速率下，然后才有资格称这次改动是改进。这是项目一直缺的验收。
5. **考虑 4 位自适应调色板**（早先离线结果：字节少 35%，而且在安静频道上 PSNR 比 3-3-2 更好）作为字节问题的真正解法，它能减轻变粗的压力。它需要改设备端解码，所以是联合改动，不是快速改动能解决的。
