# 任务状态表，2026-09-16

**开工前先读这张表，再拿它跟代码核对。**下面每条都写明可以在哪里核实。**代码与这张表冲突时，代码是对的，这张表过期了——请改表。**

写这张表的原因：本项目的会话被压缩过一次上下文，回来时对"什么已经做过"的印象是错的——它提议重建一个已经存在的机制，又把已经修好的缺陷列成待修。这两件事犯起来很便宜，发现起来很贵。

**状态只用下面这几个等级，不要混用：**

| 等级 | 含义 |
|---|---|
| 待验证 | 只是怀疑，还没有证据 |
| 源码已定位 | 在源码里找到了具体位置，尚未复现 |
| 离线复现 | 在主机上用受控输入复现了，可重复 |
| 已修改 | 代码改了，但验证还不充分 |
| 局部测试通过 | 主机测试通过，**且验证过它在旧代码下会失败** |
| 实机验收通过 | 在设备上实测通过 |

**审查发现的条目，一律不得直接升级为"已修"。**

### 时间轴这一条要怎么做

方向是**共享同一次源读取与解复用**：保留两路各自的 PTS 与 time base，再换算到共同的会话基准。**把两个 epoch 改成同一个系统时刻，不是修法。**

当前 ffmpeg 输出 `rawvideo` 与裸 PCM，Python 只读载荷，**而 raw 格式本身不携带时间戳**，所以只加 `-copyts` 而继续按原方式读裸载荷，修不好这件事。要么用能携带时间的接口，要么配一套明确的元数据机制；滤镜的重采样与直播时间戳跳变都要一并考虑。

**设备侧还有一个约束**：`main/av_protocol.c:48` 要求音频从 0 开始、严格按 40 毫秒连续推进。上游 PTS 不能直接填进现有包头。上游内容时间如何映射到会话播放时间、跳变与缺失与重缓冲各怎么处理，必须先定下来，两端一起改。

### 必须补的回归场景

同一内容晚到 600 毫秒、源停止产出、视频发送阻塞、短时音频饥饿及恢复、音频队列溢出、源 PTS 跳变、单帧多包。

**必须核验内容 ID 与 PTS 以及恢复结果**，不能只检查连接没关或某个函数被调用。
