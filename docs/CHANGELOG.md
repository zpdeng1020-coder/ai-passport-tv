# Changelog

## Unreleased

- Correct live-trial evidence: preserve per-session silence and final drop counters, distinguish observation from warm-up and deliberate shutdown, and report missing telemetry as unknown. Capture completion does not declare device acceptance.

- **Opt-in live sender v2 candidate.** Packet-boundary audio priority, bounded partial writes, byte-paced adaptive video, and joint backlog trimming address real-channel congestion without changing native geometry or FAV1. Host tests are not device acceptance. See [candidate operation and limits](development/live-sender-v2.md).

- **A frame inside dropped sound was given a session time it could not have, and the clamp that followed corrupted the recovery frame by 4.8 seconds.** An external review measured it through the real push/pop methods: three frames inside a 4.88 s hole were stamped 4750, 4833 and 4917 -- session times no sound occupies -- and the recovery frame, mapping correctly to 120 ms, was then pushed to **4918** by the strictly-increasing rule that exists so the device can detect a reordered stream.
  **Fixed on three levels.** Segments now carry an **end** as well as a start, so content outside every segment has no session time rather than inheriting one by extrapolation. A frame whose content falls in the hole is **refused a timestamp** and dropped. And a frame claiming a moment later than any sound taken is refused too, which catches the same defect while the segment is still open and the hole is not yet known. Refusals are counted (`unplaceable=`) because a silent refusal cannot be told from a frame never offered.
  **The guard is one-sided on purpose.** A picture may sit *behind* the sound the session has taken -- that is the ordinary state, since the sound runs ahead by the queue depth -- but never *ahead* of it: nothing has been heard that has not been taken. An earlier version of this guard compared the absolute distance and refused healthy frames 400 ms behind, which is not a fault at all.
- **The live fallback is now chosen by whose failure it was, not by the URL.** The previous correction classified by file extension; a review defeated it by serving the same file from `/watch?id=1`, and the calibration defect it had already disproved returned -- the picture's first four frames discarded again. What separates the two cases is not the URL and not the probe's success: the media answering "no start times" is a fact about the source, while a probe that could not run says nothing about it. Only the first licenses launch times, and the result is labelled. A last-resort extension check may still refuse the fallback; it can never permit it.
- **A calibration failure is now visible.** `timeline.calibration_note` was set on an object and never surfaced, `start()` discarded the return value, `failure()` stayed None, and `prebuffered()` only counts queue length -- so the server knowing "ffprobe is missing" and an operator being able to find out were two different facts. A WARNING now names the reason and states that no frames will be sent. It is not a failure: refusing the session would turn a degraded mode into no service.
- **A test was leaking module state into the next test.** Restoring `CHANNELS` by dict-update left `DEFAULT_CHANNEL` naming a key the following test's table did not contain, so an unrelated test failed with `KeyError: 'ch000'`. Every name `load_channels` rebinds is restored now. Found by running the file whole; running one class at a time hid it.
- **This round's device measurement is weaker than the last one, and is recorded that way.** Five minutes on hardware: the first session **degraded** (61 dropped, 47 late, 19 `nobuf` over 90 s, 10.72 fps) and ended in a session reset at t=255 s; the second ran 20 s clean at 11.66 fps. Per-frame panel cost held at 34.3 ms throughout. **This does not reproduce the previous run's clean 12.0 fps and zero drops, and it is the later of the two measurements.** The cause is not isolated -- `AUDIO_EMPTY` appears four times and the reset reason was `video-read`. Raw logs are in `docs/development/logs/device-native-12fps-r9.txt`.

- **A frame is now stamped with its OWN content position, not the position of the sound it was paired with.** An external review built the case by construction and measured it: a frame whose content was 666.7 ms, paired with sound at 1000 ms, was stamped **1000** -- 333 ms of error added to a stream with no audio gap at all. The old stamp was `video(session_clock.audio_items)`, which cannot see the difference because pairing tolerates up to 350 ms and the stamp discarded it. Now `video(frame_at)`, where `frame_at` is the frame's own content on the sound's clock. The mapping is **piecewise**: a dropped block removes content time without removing session time, so every discontinuity starts a new segment, and content on either side of it maps correctly rather than being fitted to one line.
- **The live-source fallback was re-chosen by fault instead of by source, and a file fell through it.** The black-screen repair used launch times whenever `ffprobe` returned None -- which is true for a missing program, a timeout, a refused request, and a file whose start times were not reported. A review measured the consequence: the same file, with only the audio process launched 600 ms later, discarded the picture's first four frames again, exactly as before the fix. What decides the basis is now the **source** (`is_live_source`); a file with no start times is left uncalibrated and reports why, rather than being shipped on an offset taken from process launch order. A picture that does not go out is visible; a lip-sync error is not.
- **The probe carried no User-Agent, so sources refused it and the refusal was read as the media's answer.** The two ffmpeg processes send the channel's agent because many sources answer only the player they were captured for; `ffprobe` sent none, was 403'd, and the code concluded "this source reports no start times". It now sends the same agent, and a probe failure records **why** it failed -- "ffprobe is not installed", "ffprobe timed out", "refused" and "the media has no start times" are four different findings and only the last is about the programme.
- **Three claims in the previous handover were not true of the code, and all three are now fixed.** `basis=` was said to be printed on every line; it was printed **zero** times -- set on an object and never emitted. `tools/timeline_acceptance.py` crashed on the current API while an older copy of its output shipped beside it, so the shipped output described code that no longer existed; the script is rewritten against the current API, covers six conditions, and exits non-zero when any expectation fails. And the test count was given as "223 passed, 1 skipped", which implies 224: the run is 223 total, **222 passing and 1 skipped here, 220 passing and 3 skipped as root**.
- **D4 is NOT closed, and the closure is withdrawn.** Three of its four parts are done; two are open, and both were found by reviews *after* the closure was claimed. The second open part is new to this document: **the two decoders read two independent HLS windows.** Video ffmpeg, audio ffmpeg and ffprobe each open the source separately; measured against a local HTTP origin, the video window began at 1.464 s and the audio window at 3.512 s -- a real 2048 ms difference -- while the third opening reported 48 ms, and the project used 48 ms. That is recorded as F22 and **not fixed**: the honest repair is one input providing picture, sound and timestamps together, which changes how the two processes are launched.
- **On device, the mapping change is not a performance regression: 12.0 fps sustained, 0 dropped, 0 late, 33–34 ms per frame.** The residual the report prints is unchanged in kind and is now correctly labelled -- it measures **queue depth difference**, not lip-sync error, because the two streams are placed on one clock by construction. A constant residual means the picture queue is that much deeper than the sound's; a walking residual is what would mean drift.

- **The picture was never reaching the device at all, and the fix for it was a live-only fallback. Measured on hardware: 12.0 fps at native 320x240, no drops.**
  **The failure.** After the content timeline was moved onto the media's own stream start times, `stream_start_times()` returned None for every channel in the table -- a live URL reports no start times -- so the timeline never calibrated, and `pop_video()` refused to pair **for ever**, by design. Measured on the device: `audio_sent` past 2600 with `video_sent` at 0 across two minutes, sound perfect, screen black. No test caught it because every test drove a stub channel that answers `pop_video()` from its own queues and never consults a calibration.
  **The fix is not a retreat.** A file and a live source are physically different and the review's counterexample applies to only one of them. A file has content whether or not anyone decodes it, so launch order says nothing about which part is produced -- that argument stands. A **live** source has no content before a decoder attaches, so both processes attach to the same live edge and the launch difference *is* the content difference. The basis is now chosen by what the source is, stored on the timeline, and printed with every report, because the same 600 ms means opposite things depending on which basis produced it.
- **`tools/transport_probe.py` had five defects, and every one of them made the link look worse than it is.** Found by using it, not by reading it:
  - It sent 640-byte/20 ms audio and declared `audio_chunk_ms: 20`. The firmware requires 1280/40 and refuses the CONFIG otherwise, so the probe could not hold a session at all -- and its numbers still looked like numbers.
  - A mid-frame write timeout was caught and the loop continued. `send_packet` can raise after a partial write, so the stream desynced and the device ended every session on "header-decode". 12 sessions in 110 seconds, read from outside as a device refusing the load.
  - Pacing compared a deadline against a clock captured before the frame write, so it always slept its maximum: a requested 4 fps produced **267 kB/s**. An instrument that cannot set the rate it measures at is not measuring the rate.
  - Audio was sent in bursts after each frame instead of on a tick, so the device's flow control stalled the reader and the picture went unread.
  - The picture was stamped with the **wall clock** while the sound ran a lead ahead. The device's clock is its sound (`estimated_pts()` is `submitted_samples/16000`) and it discards a frame more than 100 ms behind it, so every frame looked stale: 97.4 kB/s received, 134 packets, **1.4 complete frames a second**. This is the same defect, in the same shape, that `SessionClock` was written to remove -- the probe reproduced it, which is a point in favour of the server-side fix.
  With all five fixed the probe holds 4, 8 and 12 fps exactly and completed a 38-second step at **232 kB/s total** (200.8 video + 31.2 audio).
- **Measured on device, five minutes, native 320x240, budget 240000: 11.78 fps mean over 270.6 s, 3189 complete frames, `late` 0, `dropped` 8, `nobuf` 8.** Per frame: panel 33.8 ms, inflate 16.2 ms, 167.3 kB/s received. Server side over the same run: 7265 audio blocks, 3406 frames sent. Raw logs are in `docs/development/logs/device-native-12fps-300s.txt` and `docs/development/logs/server-native-12fps-300s.txt` -- the "8 fps" claim from the fifth round had no such log and was recorded as unverified; this one does.
- **The lip-sync residual is bounded, not walking: −292 ms mean, −348 ms worst, flat across 843→3406 pairings.** Reported as `drift=`/`worst=` on every line. It is a residual and not a count of unequal pairs, because a picture is placed within a tolerance and never exactly on its point.
- **`stray` is misnamed: it counts continuation packets, not strays.** `starts=79 stray=158` is exactly two continuations per three-packet frame. Nothing is being lost that the name suggests is being lost; recorded so the next reader does not chase it.

- **Content time now reaches the wire. The frame's timestamp is decided where the frame is chosen, and the sender can no longer compute its own.**
  **What was wrong.** `pop_video()` chose the frame from content time and then threw that result away -- `pop_audio()`/`pop_video()` returned bare payloads, and `tv_server.py` stamped the picture with `video_pts = max(audio_pts, last_video_pts + 1)`. That value states how far the *sender* has got. It moves whether or not a frame was chosen, and it was committed on the pass a frame happened to go out, so the picture carried the moment it was found rather than the moment it belongs to. On a healthy stream it equals the sound block's index and looks right; that is why it survived every test until now.
  **What replaces it** (`SessionClock` in `server/timeline.py`): content time and wire time are different domains and neither can be used as the other. The device's playback clock is `submitted_samples / 16000` -- it counts sound it has received -- and `av_stream_accept()` refuses a sound packet whose timestamp is not exactly the previous one plus one chunk. So the sound's wire timestamp is its **index**, contiguous by construction, and the picture's is the index of the sound it was paired with. Both pops now return `(payload, stamp)`.
  **The sound's content time is not discarded; it is where the skip becomes visible.** A source that jumps does not break the wire sequence -- the device would refuse that, and the missed sound was never heard and occupies no time in the session -- so the gap is counted instead, and reported as `gaps=N/Tms`.
  **The drift the wire cannot show is measured where both clocks are visible.** Because the picture is stamped with the sound's position, the two advance together *by construction* and their difference proves nothing. The residual is taken at the pairing, on content time, and reported as `drift=+Nms worst=+Nms`. It is a residual and not a count of unequal pairs: a first attempt counted pairs that were not exactly equal, and on a *perfectly healthy* stream it reported nine frames "behind", because a picture is placed within a tolerance and never exactly on its point. A number that fires on health cannot be acted on.
  **`test_the_sender_cannot_substitute_its_own_timestamp` is the one that discriminates**, and it was checked by putting the old rule back: it fails with `frame stamped 440 ms` where the pairing had said 4000000. The companion test that reads grid alignment off the wire passes on **both** rules and now says so in its docstring, rather than being left to look like coverage it does not provide. Both defects found by running things: the first draft of the new test passed on the old code, and the drift counter was wrong until a healthy stub reported drift.
- **The channel-table test passed or failed according to the working directory.** `load_channels()` resolves `channels.txt` against the process's cwd, so the table built at import holds the real 127 rows from the repository and the four built-in channels from `tests/`. The assertion compared the repository's row count against whichever had happened. It now parses the named file explicitly, so it measures the code and not the caller.

- **The content timeline's offset basis was wrong for the second time, and an external review disproved it with real ffmpeg. It now comes from the media itself, and both of the review's reproducers pass.**
  **The two mistakes have one shape.** The first used each stream's *first arrival* -- the network's behaviour treated as the programme's. The second used the two `Popen` timestamps -- the scheduler's behaviour treated as the programme's. Both decoders read the same source from its beginning, so **when a process starts says when it begins producing, not which part of the media it produces**. The review showed it directly: the same file, with only the audio process launched 600 ms later, produced an offset of +600 ms and discarded the picture's first four frames, with the media untouched. And a file whose audio genuinely starts 600 ms in produced +0.2 ms, erasing a real difference.
  **What replaces it**: `ffprobe -show_entries stream=start_time`, read once by `stream_start_times()` in `server/live.py`. That is a property of the programme and the only one of the three candidates that both streams can be asked about. Measured on the review's own fixtures: `same_origin.mkv` reads `(0.0, 0.0)`, `audio_offset_600ms.mkv` reads `(0.0, 0.6)`. Re-running the review's script against this source gives `same_source_different_launch_selects_different_content: false` and `known_600ms_source_audio_offset_lost: false`.
  **When ffprobe cannot answer** -- a live HLS playlist often reports no start times -- the timeline stays uncalibrated and `pop_video()` refuses to pair. Inventing an offset is worse than admitting there is none, which is exactly what the two earlier versions did.
- **`BoundedQueue` is deleted rather than wired up.** It was imported and never instantiated, and an external review added the part that settles it: at a fixed production rate a `deque(maxlen=N)` already has a content-duration bound, so the class was solving a problem that does not exist. Removing it is the correct response to "do not add more helper modules for review vocabulary".
- **`SourceState` was computed and dropped into a local variable** -- cited as done while reaching nothing. Its result now appears in the periodic report as `source=`. It is deliberately **not** fed to the controller: a stopped source can still have queued content whose real writes are valid evidence about the downstream, so source progress and downstream capacity stay two measurements rather than one boolean.
- **The static gate did not run the tests added in the last two rounds.** `tools/validate.sh --static` uses an explicit file list, and `test_config_agreement.py` and `test_timeline.py` were not on it -- so the gate was green while covering neither, and a person running `unittest discover` saw them pass and reported them as covered. A discovery pass now runs after the list; the gate reports 203 tests where it previously covered fewer. Verified by breaking one line of `test_timeline.py` and watching the gate fail.
- **The multi-packet acceptance case was demonstrated with a black frame, which encodes to one packet.** An external review produced the counterexample at the same geometry with a fixed-seed noise frame: **four packets, 77003 bytes**. Multi-packet frames are ordinary content here, not a corner case. A real test now covers that the packets of one frame share one content time and leave the queue together.
- **A claim of "8 fps on the device" had no supporting log.** The three supplied logs were byte-identical to the previous package, so that figure is recorded as unverified rather than restated. `v_lag` is a difference between queue heads and is not a measurement of what a viewer hears against what they see.

- **The shared content timeline is implemented and running in the real playback path. The alignment no longer compares arrival times.** Four rounds of review asked for this and this is the round that has it rather than a plan for it.
  **What was wrong.** An item's position in the session was `arrival - that decoder's own start`, which is still an arrival: it moves when the network stalls, when the reader is slow, when a process is descheduled. An external review built the counterexample -- the same picture delivered 600 ms late stopped matching its sound, because 600 ms is past the 350 ms tolerance.
  **What replaces it** (`server/timeline.py`, wired into `server/live.py`): content time is **counted**, `items_produced x interval_ms`, because a decoder paced at real time emits frame N at N/FPS seconds of content whether that frame arrived on time or three seconds late. The two streams share no origin -- there are two ffmpeg processes -- so the relationship between them is observed **once** from the two `Popen` timestamps and frozen.
  **A mistake of mine, caught by running the real path rather than only the tests.** The first version calibrated from each stream's *first arrival*. Rerunning the counterexample through `pop_video()` gave `offset=-600ms, frame=None`: the transit time had been folded into the origin, which is the same defect moved from the comparison into the calibration. My unit tests passed throughout, because they had been written to the same wrong assumption. **An arrival time may never enter the offset**; the `Popen` timestamps are known, unambiguous, and unaffected by anything the network does afterwards. Both cases now read `offset=+0ms, frame=v0, lag=0.083s`.
  **Also in the module:** `BoundedQueue` is bounded by **content duration** rather than item count, because 180 items is fifteen seconds at twelve frames a second and a minute at three; and `SourceState` separates a stopped source from a congested link, which read identically from the sender's seat and want opposite responses. One quiet window is not starvation -- HLS delivers in bursts -- so it takes two.
  **Verified on device**: five minutes, `panel_ms/interval_frames` 33.4 ms, `dropped`/`late`/`nobuf` all zero, and the picture reaching 8-10 frames a second where the shipped configuration had been settling near 5. 29 cases in `tests/test_timeline.py`, including the counterexample and a reconstruction of the old rule that fails it.
- **A `measured_by_caller` argument was added to `RateController.observe` and then removed, because working out what it should do showed it could not change anything.** It was going to let the sender say "the source has stopped". But a window where the source is gone and queued content is still going out has real bytes and a real write time, and those are congestion evidence whatever the source is doing; a window whose queues are empty already reads as unmeasured from the counters. **An argument that cannot affect any input is a claim that it does**, and the three tests written for it passed on the old code for exactly that reason.
- **"PASS (186 tests)" in the previous round's response was a number I never ran.** The real total is 177 (`unittest discover` counts skips, `pytest` reports them separately). The review's 174 passed + 3 skipped is the same 177 in an environment where two more tests skip. Corrected, and the habit recorded: a test count is a measurement and is quoted from a run.

- **A third external review passed six earlier items and found one more defect, which is fixed.** The `insufficient` flag -- true when a window carried no picture and no measurable write -- was cleared at the *end* of `observe()`, after the over-budget branch and after the drop branch, both of which return early. So a window that carried a real slow write, a real overload or a real drop left the flag holding the **previous** window's answer. Reproduced from the review's script: empty window → `insufficient True`; then 200000 bytes, a 500 ms write and 5 frames → still True. The rate came down correctly; only the label was stale. The flag is now set with `measured`, so every return path describes the window that just ended. **The previous round's test could not have caught this**: it used a light ordinary window, which reaches the end of the function and is cleared there -- a test that passes for a reason unrelated to the thing it names. Four cases added covering the three early-return paths, three of which fail on the old code. Nothing reads this flag in the playback path, so it is a reporting fault and is recorded as one.
- **The stale `Allocated JPEG=49152 PCM=12800 stripes=20480` line is now computed from the constants instead of written in.** Read from the device after the change: `Allocated video=2x22528=45056 PCM=24x1280=30720 stripes=2x10240=20480`. The old figures dated from when the picture used three 16384-byte buffers. A log line reporting numbers nobody computed is worse than no line, because it is read as a measurement.
- **Every benchmark reference is now bound to the log it came from.** The handed-over log had been re-captured (2768 / 1980 ms, giving 46.13 / 33.00 ms per frame) while several documents still quoted the previous run's 2763 / 1979 (46.05 / 32.98). Close enough to look right, which is the problem: the state table, the display baseline and the changelog now all quote the current run and say that an earlier one exists and was replaced.

- **A second external review found three more code defects; all reproduced, all fixed, each with a test shown to fail on the old code.**
  - **The empty-window guard ran after the branch it guards.** `projected = cost_now() * fps` sits above it, so an established frame cost went on being multiplied by the current rate and read as "still over budget" however many empty windows passed. Reproduced: start 8, one 30000-byte frame, three empty windows → `7, 6, 5, 4`. **The previous round's test passed throughout**, because a fresh controller has no cost estimate to project -- the test had been written for the one case where the guard's position does not matter. The guard now sits before the projection and freezes only that: a stale cost says what the last real window cost, while a slow write or a drop inside an empty window is still judged. Five cases added, two failing on the old order.
  - **`floor_ms` printed 3 ms for a 30.72 ms bus, and this was my own botched repair.** The expression was missing a divide by 1000; that was noticed and "fixed" by adding it back, with a comment claiming the matter settled -- and it still printed 3, because what was actually missing is the eight bits in a byte. The clock is in Hz, so bytes have to become bits before being divided by it. Now written out in full and pinned by `_Static_assert(PANEL_FLOOR_MS == 30u)`, with the log line printing the same macro the assertion checks. **A repair that was never recomputed is not a repair.**
  - **`tools/check_config_agreement.py` printed three fields without checking them.** `fps`, `sample_rate` and `audio_chunk_ms` were displayed beside a note and never compared, so the script answered "Both ends agree; CONFIG will be accepted" for `fps=31`, `sample_rate=8000` and `audio_chunk_ms=20` -- every one of which `config_valid()` rejects -- and exited 0 each time. All three are now assertions, the last one requiring the server's value, `media.AUDIO_CHUNK_MS` and the firmware's `AV_AUDIO_MS` to agree, which is one relation more than a literal comparison. **A check whose pass message is broader than what it checks is worse than no check**, because it gets quoted as evidence. The script had no tests at all, which is how it drifted; `tests/test_config_agreement.py` adds eight, four failing on the old script.
- **Four corrections to the data dictionary, every one of them a field I had described wrongly in the same direction -- by copying the previous round's wording instead of reading the code.** `dropped` **does** include frames lost to a full buffer (`av_player.c:1131`, `:1172`), so it overlaps `nobuf` while counting a different unit; `in_bps` accumulates at `:1786`, **before** the three success tests at `:1789`, so "only bytes that inflated successfully" is wrong on the failing path; `late_video` increments where the socket was not writable, not where a slot expired, so the name is not the condition; and **`parts_ms` exceeding `panel_ms` is not by itself a timer fault**, because the parts accumulate as work happens while the total accumulates at packet end and the statistics read each counter separately -- **the counting windows are not guaranteed to align**, which the dictionary now says plainly.
- **The Chinese and English state tables had drifted apart, and the Chinese one was broken.** It was down to four rows: F2 through F8 were lost when the status column was added. Both are rewritten and now carry F1-F11 fixed, D1-D9 confirmed, M1-M5 measured, with identical numbering and a status grade on every row. The English version had no D5-D9 at all, so a reader following the default index would have got a stale plan -- which is what the review warned about.

- **An external review of the handover package confirmed four code defects and corrected one of my own claims. All were checked against the source before being acted on, and four are now recorded with a status rather than assumed fixed.**
  - **The controller treated an empty window as evidence of spare capacity.** Reproduced exactly as reported: six consecutive windows of 0 bytes, 0 frames and a 0 ms write climbed the rate 5, 6, 6, 7, 7, 8. Both comfort tests passed every time, for the reason that makes the case dangerous -- the writes were instant because nothing was written and the bytes were under budget because there were none. A source that has stopped producing and a link with room to spare are the same reading from the sending side, and only one of them means "send faster". A window with no picture and no measurable write now freezes the capacity inference, breaks the run of comfortable windows and is marked `insufficient`; it does not lower the rate, because empty is not congestion either. Five cases added to `tests/test_rate.py`, **two of which fail on the old shape**.
  - **`rate.py` described `dropped` as device feedback and it never was.** The value comes from `window_dropped`, incremented on the branch where the *sender* abandons a frame; the device reports nothing, there is no reverse message, and nothing reads its `late` or `nobuf` counts. The docstring claimed the opposite in as many words: "the only signal here that comes from the *device*". Corrected. **The mechanism is still missing** -- adding it means a new protocol message and a receive loop that currently accepts only END, and it is now tracked as D5 rather than closed by a comment.
  - **Three stale comments that would send the next reader down a wrong path are corrected rather than deleted**, each keeping the original reasoning and stating what replaced it: `rate.py`'s "the link carries about 160 kB/s" (both halves of that subtraction are now known to be false -- `in_bps` is not throughput, and 160 is where the controller converges, not the link's ceiling); `frames.py`'s "72 packets a second, one 640-byte chunk every 20 ms" (an older geometry and an older protocol -- the chunk is 40 ms and 1280 bytes now); and `media.py`'s "the rate the picture is produced at, which is the rate it is sent at" (measured: 12 produced, about 5.5 carried, the surplus discarded at the queue, `prod_drop` climbing by 6.5 a second against a measured 7.0).
  - **The review's correction of one of my own statements is also correct.** The handover said that when a source stops, the per-frame cost estimate falls to zero and so the ceiling follows it down. It does not: `observe()` only updates the estimate when `frames > 0`, so the estimate holds at its last value. Reproduced: an established 20000 B/frame estimate is still 20000 after six empty windows. What is genuinely wrong is the missing "insufficient sample" state, which is what the fix above adds.
- **`docs/development/metrics-dictionary.md` (and `.zh_CN.md`): a data dictionary stating what every counter counts and what it must not be read as.** Every field on both ends, with the "and not" column first. It exists because three rounds of this project have been misled by reading a number for something it is not: `panel_frames` as frames, `in_bps` as link throughput, `rx_bps` as total throughput. It also records the gaps -- the device's playback position and audio depth are not reported at all, and the physical moment a picture appears is not measured anywhere.
- **The review's recomputation of the device log reproduces mine exactly, and adds one thing I had missed.** 421 complete frames over 110191 ms, weighted 3.82 fps; `panel_ms ÷ interval_frames` weighted at 33.90 ms, range 33.00-35.72. Its extra finding: `parts_ms` and the sum of the six printed parts differ by 2 to 4 ms, and `panel_ms` exceeds `parts_ms` by 4 to 18 ms. Both are now explained in the dictionary -- the first is per-field truncation, since each part is divided by 1000 before printing, and the second is real untimed loop overhead. Neither is a fault; `parts_ms` exceeding `panel_ms` would be.

- **Three defects in the send loop are fixed, each with a regression test that was shown to fail on the old code.** An external review found them, and found that a previous round had reported them as "not yet fixed" when one already was and had mis-stated another — which is why `docs/development/state-20260916.md` now exists and is linked from the development index.
  1. **`window_frames` counted packets rather than frames** (`server/tv_server.py`). The increment sat inside `for n, part in enumerate(frame)`, so a frame of five packets was reported to the controller as five frames and the bytes-per-frame it derives was a fifth of the truth. It is now outside the loop.
  2. **`video_pts` advanced once per pass of the loop rather than once per picture actually sent.** Computed at the loop head, it was committed there too; it is now committed only where the frame is known to be going out.
  3. **A pass with a picture queue but no frame due to send skipped the wait, the controller update and the periodic report.** That was a single `continue`, and the three things it skipped are the three that notice a stream going wrong. Measured from outside with a controlled clock on the original loop: 500 attempts to take a frame, and **zero** waits, zero controller updates and zero reports over more than five seconds. Sleeping before the `continue` would not have fixed it — the controller is what goes unupdated.
- **`RateController` no longer lets an isolated dropped frame hide everything else in its window.** The dropped branch returned before the over-budget and slow-write tests were computed, so a window that lost one frame *and* recorded a five-second write was judged on the drop alone — and an isolated drop is tolerated by design, so in that window every other piece of evidence was discarded too. Measured with the controller's own inputs: 960000 bytes in a second with a 5000 ms worst write held the rate where the same window without the drop stepped down. `over` is now evaluated first and the drop test decides only whether the isolated case is tolerated. Six cases added to `tests/test_rate.py`; **four of them fail on the old shape**, which is the check that they test the defect rather than the change.
- **`docs/development/state-20260916.md` (and `.zh_CN.md`): the task state as a table, to be read and checked against the code before the first edit.** It lists what is fixed with its evidence, the four confirmed defects that remain, the measured figures *with what each does not establish*, the configuration in force, and the next steps in order. - **The device draws a frame in 33.2 ms instead of 70.5 ms, measured on the device — and the ceiling was never the processor, it was a wait that could be overlapped.** `push_stripe()` submitted each stripe and then blocked until its DMA transfer finished, making the panel strictly serial with the CPU: build a stripe, send it, wait, build the next. It now has two stripe buffers and queues a transfer ahead of the stripe being built, draining only once two are outstanding. **Measured on the device: `panel_ms ÷ interval_frames` falls from 70.5 to 33.2 ms and the wait per stripe from 40.6 ms to 0.04 ms** — the 30.7 ms SPI transfer is now entirely hidden under the 32.5 ms of CPU work, and the device's drawing capacity goes from about 14 to about 30 frames a second. A stopped-world benchmark in the same firmware (`AV_DISPLAY_BENCH`) puts the two paths side by side with no network at all: **46.13 ms a frame serial against 33.00 ms pipelined, with 1 ms of wait remaining** (2768 and 1980 ms over 60 frames), so about 33 ms is this panel and this bus at their limit. An earlier run read 2763 and 1979; close, but a different run, and the numbers are quoted with the log they came from.
  **This reopens a verdict this project had closed twice.** The code recorded that a second stripe buffer "does exactly what it was meant to do and does not help" — the wait did fall, 37 ms a frame to 2.2 ms, and the frame rate did not move, so the wait was judged irrelevant. **Both readings came from a session the link was pacing, so the frame rate could not have moved however much time came back.** The measurement was of the sender's rate, not the device's; the code now says so at the point where the old number is quoted.
- **The link is not 160 kB/s, and the evidence is that raising the budget almost doubles the device's measured receive rate.** Measured across four channels on four different source origins, with the device dialling `ch000` and only that id's address changed: **`rx_bps` reaches 184–195 kB/s at a budget of 240000 against 91–101 kB/s at the shipped 120000.** The 160 kB/s figure is closer to where the controller converges under a budget of 120000 than to a property of the link.
- **Raising the budget is not what ships, because one channel in four collapsed.** At `TV_VIDEO_BUDGET=240000` three of the four channels roughly doubled — 4.99 → 8.38, 5.38 → 8.76, 4.49 → 8.78 frames a second — but with **47 to 174 frames dropped in a 120-second run**, and the fourth (`ch009`, ottiptv) went to a median of **0 fps with 215 dropped and 206 late**, its own source falling to 30 kB/s and one server session failing. At the shipped 120000 the same four channels ran 4.49–5.38 fps with 0–9 dropped and **zero late frames on all four**. Dropped frames are the unevenness the viewer is complaining about, so the shipped budget is unchanged and the sender-side adaptation is left as the next piece of work.

- **The channel list no longer needs 8192 contiguous bytes, and with 127 channels it no longer fits in a session.** `config_valid()` allocated a temporary `channel_t[AV_CHANNEL_MAX]` — 64 bytes an entry, 8192 for the table — parsed the server's JSON into it, and copied it into the published table under the lock, so that a reader would keep the old list until the new one was whole. On the shipped 127-channel list that allocation is the one that fails: `No memory to parse the channel list: wanted 8192 B, heap=13192 largest=7680`. **Free heap was 13 KB and the largest contiguous block was 7680 — 512 bytes short, a fragmentation failure and not a shortage.** The cJSON tree for 127 channels is itself live at that moment, which is what splits the free space. Every session then failed at config-validation and the screen sat on its waiting picture. The parse now writes straight into the published table with the count set to zero for the duration of the walk, which removes the allocation entirely and fixes the leak on the empty-list path at the same time (the old code returned without freeing `staged` when every entry was filtered out). The index computation degrades instead of refusing: if its `char*[n]` allocation fails, the session is published with index 0 rather than rejected. What is given up is that readers see an empty list while the walk runs; the old list was not really being preserved either, since it was shown until the new one was ready — on a channel change, the list you just left.
- **The display path's cost is now split into its parts, and the split adds up.** `panel_us` covered inflation, expansion, enlargement, the overlay and the DMA wait as one number, and `decode_max_ms` gave a peak over the same span: three different remedies behind one figure. `expand_us`, `enlarge_us`, `overlay_us` and `submit_us` are now counted separately and printed beside `inflate_ms` and `panel_wait_ms`, together with `parts_ms`, their sum. **That sum is its own instrument check** — a total larger than the interval containing it means a timer was broken, and this project has already been misled once by a unit carried wrong inside `panel_us`. The overlay is timed even though it is free on stripes it does not touch, because "the overlay costs nothing" is an assumption this project has had to correct before.
- **A measurement build that takes the link out of the question (`AV_DISPLAY_BENCH`, off by default).** It runs at boot before any socket exists and pushes a filled stripe buffer at the panel for sixty frames, printing the total with fill, submit and wait separately. **It is the only measurement of the panel at its rated 40 MHz, and therefore the only evidence the 30.7 ms floor has ever had** — a floor every other figure in this project is compared against, and which so far has been arithmetic. It settles something the running firmware cannot: **every previous figure for the device's own drawing speed was taken during a live session, where the rate could not exceed what the link supplied.** The two-buffer stripe experiment is the clearest case — the DMA wait fell from 37 ms a frame to 2.2 ms with no change in frame rate, and that was read as "the wait is irrelevant". - **Clearer statement of what the two-buffer result did and did not show** (`main/av_player.c`, `push_stripe`): the comment now records that both readings came from a link-paced session, so `panel_wait_us` near zero on two buffers proves the transfer overlapped and proves nothing about this device's drawing ceiling.
- **`docs/development/device-display-baseline-20260916.md` (and `.zh_CN.md`): how to isolate the device's display performance from the link, layer by layer.** Four freeze points — the server, the receive task, the drawing task, the SPI — each measured with the others stopped, plus the queue-backup table that says which stage is holding which. - **"Most channels turn into colour bars after a while" is diagnosed: the bars are not a picture fault, they are the device ending the session over an audio underrun and going back to its waiting screen.** A viewer reported nine channels out of ten turning to bars within a minute. The device's own serial log gives the order: `AUDIO_EMPTY gap_ms=305`, then `Session reset: audio underrun; reconnect/rebuffer`. Three pieces of evidence put the cause on **picture packets draining the sound**: the device judges an underrun at `AUDIO_UNDERRUN_MS` (300 ms) and the gaps recorded at failure were 300, 304 and 305 -- **a figure that is always exactly the threshold is not a measurement that varies, it is the threshold being reached**, a number that appears repeatedly in this project's earlier audio work without the conclusion being drawn from it; the device's own log records one picture read as `RX_IO stage=video-read bytes=19240/21399 elapsed_ms=612`, so 612 ms passed in which the single task reading both streams never touched the audio queue, against a 300 ms tolerance; and **with the picture switched off and the sound alone, eighty seconds passed with no underrun at all** while the sender's longest gap between writes was zero, where both streams together underrun every twenty seconds. That last part is structural: one task reads both streams, and it is written into the firmware.
- **The colour bars are fixed: the device no longer ends a session over an audio starvation. Measured 560 seconds on one session with no failure, where it had been dropping every twenty seconds.** Three changes, each with a measurement behind it:
  1. **Device: a starved queue now plays silence instead of ending the session** (`main/av_player.c`, new `AUDIO_SILENCE_MAX_MS` = 3000 ms). It called `fail("audio underrun")` after 300 ms of an empty queue -- and the queue is emptied by the *picture*, because one task reads both streams and a picture packet in flight measured 612 ms. It now plays silence and carries on, exactly as the picture drops a frame rather than tearing down the stream. **Nothing is faked**: the clock advances by the samples actually submitted, so the picture aligns to a timeline that really was played. Past 3000 ms it gives up, which the receiver's own inactivity timeout also covers.
  2. **Device: the four read deadlines go 1500 to 3000 ms** (new `AV_READ_DEADLINE_MS`). The device allowed 1500 ms for one packet while **the server allowed only 630** -- the sender giving up before the receiver, which is the wrong way round. They now agree.
  3. **Server: the rate the picture is produced at is the rate it is sent at** (`media.FPS` reads `rate.MAX_FPS`). ffmpeg was asked for ten frames a second while the sender was held to five, so five a second piled up in a fifteen-second queue: `video_q` sat at 180 of 180, `prod_drop` climbed by five a second and the picture ran about eighteen seconds behind the channel. That is not a fault so much as **a queue that stopped draining** -- producing faster than the link carries only discards the surplus at the far end.
- **The per-channel rate ceiling was implemented -- the arithmetic is right, the round as a whole was not, and it is reverted to the configuration that has been verified.**
  How it works: the controller already receives each window's `video_bytes`, so it is also told how many frames went out; the quotient is what a frame of this channel costs, and `budget / frame_bytes` is the rate that exactly spends the budget. **The mechanism works on the device and its readings are honest**: on the median channel it measured `frame=19036B` and computed `ceiling=6`, settling between 5 and 7 where it used to sit flat at five; on the cheapest it measured `frame=2900B` and computed `ceiling=12`, climbing 5, 6, 7, 8, 9, 10, 11, 12 exactly as the arithmetic predicts. **The derivation is sound; what surrounds it was not.**
  Four things came with it: ceiling 5 to 12, budget 210000 to 120000, a producer throttle, and discarding the sender's backlog. **The throttle tested the wrong thing** -- elapsed time since the last frame rather than queue depth -- and since a source's own rate can be below the target (that cheapest source delivers six), it **threw away the source's own frames as if they were surplus**: measured, the picture ran at 6.2 packets a second with the queue empty and `prod_drop` past 1900. Queue depth is the right test, but the run that used it produced an empty device log (another capture process held the serial port), so **no valid reading was obtained**.
  **The lesson to put first**: six changes were layered onto a round that never passed, each one unverified before the next went on, so nothing could be attributed at the end. **One change, one 300-second run.** Reverted to ceiling 5, budget 210000, no producer throttle and a no-argument `pop_video()`, which measured 300 seconds on one session with no failure, `prod_drop=0` and `late_video=0`. **The derivation stays in `RateController.ceiling()`**, inactive inside a ceiling of five, until the throttle is written correctly and verified on its own.
- **Two attempts to exploit the channel spread were unstable and are reverted. The direction was right; the mechanism was not.**
  Four changes were made to use the finding that a cheap channel can run ten frames: ceiling 5 to 12, budget 210000 to 100000, queue 180 to 36, and a separate start rate of 5. **None held.** With the ceiling raised the controller climbed 5, 6, 7, 8, 9 before a write went slow, by which time the device's picture queue was full (179 of 180), the audio lead had gone to -1200 ms and `prod_drop` had reached 1578; it then fell to three and did not recover. Lowering the budget to 100000 to stop the climb early was worse, because `media.FPS` follows the ceiling and so production ran far ahead of the link: `video_q` filled again (36 of 36), `prod_drop` reached 2138 and `video_pps` fell to zero. **All are back to ceiling 5, budget 210000, queue 180.**
  **The missing piece is mechanical**: the rate ceiling should be derived from **that channel's own frame size** -- budget divided by bytes a frame -- rather than being a global constant that has to be discovered by probing past the link. The server already knows each frame's size and `rate.py` already has `VIDEO_BUDGET_BYTES`; joining the two would let a cheap channel run ten frames and a heavy one settle at three with no overshoot at all. **That is the next change to make.** It was not made here because it touches both the production rate and the transmission rate, which are currently the same number, and that is larger than one session can verify.

- **Measured across the whole channel list, after the viewer corrected this method three times, and it overturns a constant.** All 103 channels were measured offline (15 s each at 6 fps, cut into the same 16-row stripes the server cuts, so the figure is what the link carries): **the cheapest frame is 2266 bytes and the dearest 31271, median 17632 -- a factor of 13.8.** The spread is the content: a still studio shot compresses to a fraction of a fast-moving one.
- **`AV_VIDEO_MAX = 22528` therefore does not cover the list: ten channels (about 10%) exceed it and every one of their frames is split in two.** Confirmed on the device by pointing `ch013` -- the id the device asks for, unchanged -- at the dearest source. **This is the lever the project has been missing: the channel id and the source are independent, so any source can be measured.** Result: **`stray` (same-frame continuation count) read 664, `nobuf` 9, two failures in 300 seconds, 3.6 frames.** This is not a new fault; it is the same packet-splitting mechanism recorded earlier as "native looked worse than enlarged" -- **it was only ever measured on ch000, so only part of it was visible.**
- **The more important finding is at the other end: `MAX_FPS = 5` was set from the median channel and flattens the cheap ones.** At a fixed ceiling of 12: **the cheapest channel ran 10.2 frames, the median 5.0, the dearest 3.6 -- a factor of three under one ceiling.** Five was not protection, it was levelling: it held a channel that could run ten to the rate a heavy one needs. **The ceiling is back at 12 and the controller finds each channel's own rate.** `START_FPS` stays at 5, the median channel's measured landing point, because starting at 12 would open every session over the link and cost the first seconds in dropped frames.
- **`stray` also read 271 on the median channel**, so "only the first ten split" is not right: any channel splits during a busy moment. Together with the above, the ceiling belongs to the frame's actual size rather than to a static list.
- **One change was made and reverted: adding a "do not retry the rate that just failed" rule to stop a 4-5 oscillation.** The oscillation is real -- `RATE 4 / 5 / 4 / 5 / 4 / 5 / 4 / 3 / 4 / 3`, settling at four -- but the rule was wrong and the test caught it: `test_a_comfortable_window_after_a_bad_one_starts_the_count_again` documents that the controller must climb **back to** the rate a fault cost, not stop short of it. **The oscillation is the design**: probing at the link's capacity, stepping down when it is exceeded and up when there is room. Pinning it a step lower trades a permanent loss of frame rate for a little less jitter. Reverted in full.

- **The real ceiling is the link, and the link is jittery rather than merely slow -- which overturns a standing assumption in `docs/development/handoff-20260915`.** Measured with 1200-byte pings (small ones hide it): **twenty packets with no loss, but round-trip times from 7 ms to 314 ms, mean 110, standard deviation 108.** That is queueing, not loss. The handoff document states "our link drops rather than queues, and the device reports no per-packet information, so a delay estimate cannot be built" -- **the first half of that is now measured to be false**, and the reason it gave for rejecting WebRTC-style congestion control goes with it. A second measurement on the same link gave **7.5% packet loss over forty packets, mean 115 ms, peak 334 ms**.
  It also explains the difference between two runs on one day: the first held five frames steadily, the second, on the same configuration, fell to `video_pps=0.8` with `lookahead_ms=-1329` and `send_gap_max_ms=1851`. **The throughput across five runs spans 110 to 160 kB/s; it is not one number.**
- **The device is not the constraint, and this one is decisive.** From the healthy intervals of its own log: `panel_ms=3839` against 10000 ms of wall clock (38%), `inflate_ms=1061` (11%), `decode_max_ms=71` against a 200 ms frame interval. **The device has ample headroom; the link does not feed it.**
- **The encoding side is exhausted, measured offline.** Sweeping `zlib`'s strategies at the native geometry over 120 frames of a real channel: the current setting is 18968 bytes a frame, and **Z_FILTERED costs 3.9% more, Z_RLE 49.5% more, Z_HUFFMAN_ONLY 63.7% more**; level 9 saves 0.2%. Compressing whole frames rather than stripes would save 4.5%, but the device would have to hold all 76800 bytes before drawing and that exceeds its 10 KB stripe buffer -- **not available**.
- **The memory route to a bigger window is closed, with a number.** The device's TCP receive window is 32768 and, since throughput is roughly window over round-trip time (200 to 314 ms measured), raising it is the direct lever. **It cannot be raised: the session's free heap is about 20 KB with a largest block of 9728 bytes** (`heap=20060 largest=9728`, seen in several sessions), which will not hold a 32 KB window buffer. An earlier note of roughly 40 KB free was from an older, suboptimal build and is corrected here.

- **The frame-rate ceiling is five, measured, and the floor comes down from six to three.** The device reports about 160 kB/s sustained; the sound takes a fixed 32 kB/s, leaving roughly 128 for a picture whose native frame is 20.5 kB. At a fixed rate: **six frames (123 kB/s) gave four failed sessions in 240 seconds; five (102 kB/s) ran the same span with no reset and no failed session.** The floor of six was "the lowest that still reads as movement", measured when the panel could be fed ten; now that silence is tolerated, **slowing down is far better than disconnecting**, so the floor has to give way -- otherwise the range is empty (6 > 5) and the controller cannot even be constructed.
- **The server's write deadline goes from 630 ms to 1250 ms** (new `FRAME_WRITE_DEADLINE_S`). It was derived from `frame_bytes / 32768`, a pessimistic figure where the link measures 160 kB/s, so the sender abandoned a frame the device was still willing to wait for -- `TimeoutError` in `live_video_send` is the failure this investigation kept arriving at. It sits just under the device's 1500 ms so that giving up is the sender's decision rather than a closed socket's.

- **Tried and rejected: splitting a frame into two packets so the sender can feed the sound between them. Flashed and measured -- distinctly worse, and reverted.** It came from the device's own comment (`main/av_player.c:1123`): the gap this design was built around "is the sender's to close, and the sender closes it: the frame's packets are separated by audio whenever a chunk falls due mid-frame." At 22528 bytes a packet a native frame is **one** packet, so that gap never existed, and the server does carry a drain-the-sound loop between packets (`tv_server.py:1072`) that was spinning for nothing. At 12288 a frame is two packets, so in theory there are two chances a frame. **Measured, fixed at eight frames a second over three hundred seconds on one channel: underruns 5 to 9, device resets 11 to 24, twelve of thirteen sessions failed, and the actual rate fell from 6.4 to 2.4.** The queue high-water rose to eighteen chunks, a picture read took up to 492 ms and the sender's worst gap was 512 ms. **Shorter packets do not shorten the stall, and doubling the packet count costs the one chance a frame had.** The earlier note that "packets are not the constraint, bytes are" **had not expired** -- it was assumed to have done so when the geometry changed, and the measurement says it still holds. The device's comment describes an opportunity the sender has, not a problem splitting solves.
- **Found why the cushion was always 280 ms: the sender has a "not before real time" gate.** Substituting the origin into the release condition gives `audio_at = t0 + audio_pts`, and a chunk may go only when `now >= audio_at`. The timestamps advance one chunk per chunk sent, so **the sound is released at exactly real time and never gets ahead of it**; the device plays at real time too, so the queue neither fills nor empties and sits at its opening transient. `AUDIO_MAX_LOOKAHEAD_MS` is a cap on how far ahead it *may* run, and under a real-time gate it is never reached. That accounts for two measurements that otherwise look contradictory: with the lead at 320 and at 700, and with the cap at 280 and at 700, the device's queue high-water was **280 ms every time**. Neither parameter could move it.
- **Added `TV_AUDIO_FILL` (off by default), which lets the sender fill the cushion to the cap ahead of time.** With it on the sender's own lead reading goes from 0-30 ms to 596-629 ms, the device's queue high-water rises from seven chunks (280 ms) to **eighteen to twenty-one (720-840 ms)**, and underruns fall from five to **two** with resets from eleven to six -- all at a fixed eight frames a second over three hundred seconds. **It does not cure it.**
- **The remaining cause is that the server's own loop blocks on writes.** The same log shows `send_gap_max_ms=737` and `busy=2.1 s` -- two seconds of a five-second window spent inside socket writes -- while the device reports `queue=0, gap_ms=302`. The blocking is not something "audio first" can rescue, because **it happens inside a picture packet's write**. No cushion is deeper than the time the sender stops: a worst stall of 737 ms against an 800 ms cushion leaves 63 ms, which is why filling reduces the underruns without removing them. The `SO_SNDBUF` route was already taken and its conclusion is in the code (16384 measured best; 65536 was worse, one run ending with ten failed sessions).
- One change was made in the wrong direction and has been reverted, recorded because it reads as obviously correct. `tv_server.py` computed `origin = now + max(START_DELAY_MS, AUDIO_LEAD_MS)` while a chunk is released at `origin + (audio_pts - AUDIO_LEAD_MS) / 1000`, which looks like the lead cancelling out exactly -- as though `AUDIO_LEAD_MS` had been inert since the day it was set. The origin was changed to `now + START_DELAY_MS` on that reasoning and **that was wrong, and backwards**. What the expression decides is not when the first chunk leaves but how far `audio_pts` may run ahead of the clock, and solving it gives 320 ms either way when the lead is 320. The change cut the cushion to 120 ms instead, because the origin is the wall-clock instant the timestamps are measured against and the lead is measured from it. Reverted.
- **Raising the cushion to 800 ms did not stop the underruns either**, so "too small a buffer" is not the whole answer, and the same log says why: one picture read takes 612 ms, and an 800 ms cushion puts the device on its own flow-control line (`PCM_QUEUE-4`, twenty chunks of forty milliseconds), past which it stops reading the socket and the picture is held up instead.
- **Lowering the frame rate does not save it either, and that rules bandwidth out.** Held at a fixed seven frames a second -- 155 kB/s all in, well inside the link's measured 141 to 243 -- for 300 seconds: **five underruns, eleven device resets, five failed sessions**, and an actual rate of 4.4. A hundred-second run at eight frames on the same channel had shown none at all, so **a clean short run means nothing here**, and that misreading is worth keeping alongside the result.
- A **structural miscount** worth recording even though it is not this fault: `rate.py`'s `VIDEO_BUDGET_BYTES` (210 kB/s) counts the picture and not the sound, while the link carries both. At the native geometry a frame is 20.5 kB, so ten frames is 205 kB of picture -- read by the controller as room -- while the socket is asked for 237 kB/s. Lowering the budget to 180 kB (148 kB/s of picture) **did not help and was worse**: over 180 seconds, four sessions and four underruns.
- **A methodological correction, made by the viewer at the time**: "you cannot test one channel; one channel working does not mean the others do." The earlier synchronisation test ran on ch000, which turned out to be the one channel out of ten that held for a full fifty seconds, and the fault was missed. Two tool facts worth keeping: **the device names the channel it wants in its HELLO and the server's `--channel` is only a fallback**, so a test channel cannot be chosen from the server side; and a sweep script **must wait for the port to be released rather than sleeping a fixed two seconds**, or one cell ends up with no server on it at all and reads zero -- which looks like a device finding and is a tool fault.

- **A tool error that cost one false reading.** The cell with the cap at 700 ms counted `AUDIO_EMPTY` as zero and the script reported "no underruns" -- while the device log file was **0 bytes**, because the previous capture script was still running and two processes were competing for the same serial port. **An empty log returns zero for every signal; that is a vacuous zero, not a clean measurement.** The capture scripts now refuse a cell whose device log is implausibly small.

- The picture path was rebuilt end to end: instead of sending a 160x120 JPEG for the device to magnify, the server now sends a full 320x240 palettised frame. Three quarters of the old picture were pixels the device had copied from their neighbours, which is where the blockiness came from; every pixel is now the source's own. A frame is cut into fifteen sixteen-row stripes and each is compressed and sent on its own, so the panel begins updating before the whole frame has arrived, and the device needs no scratch buffer larger than one stripe. On the device the stripes are inflated with the zlib decompressor built into the C3 chip's ROM (`0x400000f4`), and indices are turned into panel colour in place, backwards through the same buffer -- so the change cost no frame buffer at all, only about 11 KB of decompressor state. The palette is generated per channel: half a second of the source is sampled before each channel starts and 256 colours are sent ahead of the first frame, so each channel carries its own colour table, and the error against the original frame fell from 28.2 (RMSE, fixed palette) to 10.1. Raised by a user: the released version's picture was neither smooth nor clear.

- Fixed the colours being wrong, because ffmpeg's `rgb8` is not "8-bit colour". It is ffmpeg's own fixed 3-3-2 grid, so asking for it re-quantises every pixel onto that grid and discards the chosen palette entirely. It fails silently -- the picture still appears, the adaptive palette simply does nothing. The pipeline now uses `pal8`, which passes the indices through untouched, verified by replaying those indices through the palette and comparing against the same frame rendered as rgb24 in the same ffmpeg run: 307200 pixels, no mismatches.

- **The palette question is settled, and the other way round.** The entry above says `rgb8` was the fault and `pal8` the cure, and that holds only while the palette is *adaptive*. The fault was never the format: it was the adaptive palette itself, chosen once from a second and a half at the start of a channel and then **frozen for the session**, so any later picture whose colours were not in that sample is drawn in the wrong ones. Measured on a clip that opens dim and brown and then cuts to colour bars: the frame at 2.5 s drawn with the stale palette, RMSE 275 out of 255; drawn with a palette from that frame itself, RMSE 0; drawn on the fixed 3-3-2 grid, RMSE 57. That is the viewer's "sometimes normal, sometimes grey, sometimes green, sometimes brown". **A still test card cannot detect it** -- the card holds every colour it will ever show in its first frame, so a palette sampled from the opening second is exactly right for it. Two smaller faults sat in the same code: `stats_mode=single` with `-frames:v 1` means "use the first frame", the opposite of the sampling the function's own comment promised.
  The pipeline now uses ffmpeg's fixed 3-3-2 grid (`-pix_fmt rgb8`), which the device already implements in `av_palette_rgb565`; nothing is sampled, so nothing can go stale. The bit order was checked by encoding pure red, green and blue and reading the indices back -- 0xE0, 0x1C, 0x03, which is RRR GGG BB and matches the device's table on all 256 entries. **It is also smaller**: a regular grid is more temporally consistent, so frames measured 21087 B at the median against the adaptive palette's 24604 B.

- Fixed the receiver task's priority. The task reading the socket sat at priority 5, **below** the decoding task at 6, on a single core: an inflate takes up to 146 ms, nothing reads the socket while it runs, the server's writes go undrained and the sound falls behind by the same amount and underruns. The comment defending the ordering worried about priority inversion; that worry does not apply here, because `xQueueReceive(s.free_video, &v.jpeg, 0)` has a zero timeout and discards a packet when no buffer is free rather than blocking. Now **receiver 6 / video 5 / audio 7**. Measured at 8 fps: healthy intervals 7 of 26 before, 30 of 37 after; median frames 43 to 79 against 80.

- Turned the screen-capture diagnostic off (`CONFIG_AV_SCREEN_CAPTURE` now defaults to n). It was left behind by the colour investigation, which means every performance measurement since was taken on a build carrying a diagnostic. Its cost lands at the worst moment: sixty frames into a session it allocates 9600 bytes and prints about 10 KB of hex, which at 115200 baud blocks the device for roughly 0.9 s -- the first seconds of playback, where a session is most likely to be lost.

- **Fixed native 320x240 looking worse than the enlarged settings -- the cause was packet splitting.** The viewer tried the enlarged setting first, reported a "grid of pixel dots" (the inherent artefact of a non-integer enlargement: spreading 200 or 240 source columns across 320 screen columns copies some pixels once and their neighbours twice), and asked for native with no scaling. Native then looked *worse*, and the mechanism was:

  **A 320x240 frame compresses to 20.4 kB at the median and 22.0 kB at the worst, and all thirty sampled frames exceeded `AV_VIDEO_MAX` (then 16384), so every frame was split into two packets.** The device's video queue is two deep -- a split frame fills it exactly, the second packet arrives with nowhere to go, the frame is left incomplete, and an incomplete frame is discarded by rule. **So more pixels meant whole frames being thrown away, and native came out worse than enlarged.**

  The fix: `AV_VIDEO_MAX` from 16384 to **22528** (enough for the worst frame), buffers from 3 to **2**. Memory goes down rather than up: 2 x 22528 = 45056 against 3 x 16384 = 49152. Measured over 300 seconds: **zero dropped frames, zero `nobuf`, no underruns**, a median of 9.2 frames a second, the sound full, 148 kB/s of video (180 kB/s all in).

  The control, same native geometry and same audio fix but still splitting: 195 dropped frames, 166 `nobuf`, four underruns. **Both counters going to zero together is what identifies splitting as the mechanism.**

- **320x240 native was re-tested after the audio timing fix. The conclusion changed; the choice did not.** The original rejection -- nineteen session interruptions in 300 seconds, seven frames a second at best -- was measured while the audio lead was still 200 ms, and the lead was not settled until **an hour and twenty minutes later**. The premise had expired, so it was measured again. With the fix it reaches **8.9 frames**, and **draws a frame in 34.7 ms** (against 54.7 ms at 280x210, because there is no enlargement step), dropping only three. But it uses **219 kB/s**, hard against the top of the link's measured 141 to 243, and over 300 seconds it still underran **four times** with the server losing eleven connections to the device. **It is the sharpest setting -- every screen pixel is the source's own -- and it cannot hold a session.**

  All three settings, measured over 300 seconds each after the audio fix:

  | Setting | Content pixels | fps | Picture a second | Link | Underruns | Own pixels |
  | --- | --- | --- | --- | --- | --- | --- |
  | 240x180 | 32,400 | 13.9 | 450k | 192 kB/s | 0 | 3/4 |
  | **280x210 (default)** | **43,960** | **10.1** | **444k** | **203 kB/s** | **0** | **7/8** |
  | 320x240 | 57,600 | 8.9 | 547k | 219 kB/s | 4 | all |

  **240x180 and 280x210 deliver almost exactly the same picture a second -- 450k against 444k pixels -- and 280x210 gets there with less enlargement**, which is why it wins. 320x240 delivers the most of the three and cannot hold a session.

- **The picture moves up a step: geometry from 240x180 (enlarged 4/3) to 280x210 (enlarged 8/7), so the share of the panel carrying a pixel of its own goes from three quarters to seven eighths.** Measured over 300 seconds: a median of **10.1 frames a second**, no underruns, the sound full, 177 kB/s of video. Content pixels rise from 32,400 to 43,960 (**+36%**) and the frame rate falls from 13.9 to 10.1.

  This is a real trade and both settings were measured. **Both stay in the build, switchable**:

  | Setting | Content pixels | Median fps | Sound |
  | --- | --- | --- | --- |
  | 240x180 | 32,400 | 13.9 | full |
  | **280x210 (current default)** | **43,960** | **10.1** | full |

  10.1 frames is far above the four the viewer once described as "like a slideshow", and a 36% increase in pixels is visible, so 280x210 is the default.

- The geometry is now chosen **by name** rather than by three environment variables that have to be set together and consistently. The device compiles its geometry in, so the two ends must match exactly or every session is refused -- and a refusal does not announce itself as a configuration error, it looks like a broken link: the device connects, authenticates and drops. Three variables are three chances to get that wrong, and the failure is expensive to diagnose. It is one name now: `TV_GEOMETRY=240x180` or `TV_GEOMETRY=280x210`, and a name the firmware does not have fails at start-up with the options listed. `tools/check_config_agreement.py` prints which pane the firmware was built for and which the server is about to send, and names the value to set when they disagree. This geometry must match on both ends and the mistake has been made three times.

- **Re-swept the frame rate on the fixed firmware: fourteen is the combined ceiling.** 240x180, compression level 6, after the audio fix:

| Asked | Actual | Total | Underruns | Dropped |
| --- | --- | --- | --- | --- |
| **14** | **13.9** | **192 kB/s** | **0** | **2** |
| 16 | 13.8 | 239 kB/s | 1 | 220 |
| 18 | 13.1 | 203 kB/s | 0 | 534 |
| 20 | sessions will not establish | -- | -- | -- |

**Ask for more and get less**, the same shape as the packet ceiling found earlier. Sixteen and eighteen are both slower than fourteen and lose 220 and 534 frames doing it; the sender's own `send_gap_max_ms` goes from a median of 83 ms at fourteen to 127 and 112, and `prod_drop` climbs from 57 to 91 and 129 -- **the sending side is blocking**. Eighteen's byte total (171 kB/s) is *lower* than sixteen's (207) because frames that cannot be sent are discarded, which is the mechanism behind asking for more and getting less.

**Fourteen is the combined ceiling of link and device at this geometry**: 13.9 frames delivered, no underruns, two frames dropped.

- **The frame-rate ceiling moved from 11 to 14, and the measured median rate from 10.5 to 13.4 -- an increase of 28%.** Eleven had been set on the reasoning that a frame's 74 ms `decode_max_ms` peak needs a slot wider than itself, but that peak is one frame in a hundred and a sustained rate runs on the mean. Measured at a fixed fifteen for 200 seconds: the device held 14.1 to 15.0 frames with the sound full and no underruns, the only cost being a burst of 53 dropped frames at the start -- the picture aligning itself with the audio clock once, not a device that cannot keep up. **That distinction is what the controller had been missing.**

- **The rate controller could not tell a burst of losses from a sustained inability to keep up.** It stepped back for any dropped frame, so at the edge of thirteen to fourteen it oscillated: measured over 300 seconds the median was 11.9 while a fixed fourteen held 14.4 -- **the session was spent climbing rather than at the top**. A rate now drops only when two consecutive windows both lose frames; an isolated drop is recorded and nothing more, and it no longer clears the run of comfortable windows that the climb depends on. The windows needed to raise the rate went from four to two.

- Rejected: **deepening the pipeline** (a fourth video packet buffer, and a video queue of three). The reason to try was `nobuf` -- the receiver running out of free buffers -- going non-zero at thirteen to fourteen frames, which the controller read as a device that cannot keep up. But the fourth buffer wanted 16 KB, and **the channel list is parsed after the session's buffers are allocated**, so the two compete for one heap; cJSON then failed to allocate, returned NULL, and every CONFIG field looked missing to the device, which dropped every session on connect. What that looks like from outside is not "out of memory" but "configuration rejected", indistinguishable from a link fault. This is the third time this trap has been sprung: anything added to a session is spent before the channel list is parsed. To save the next person the time, `config_valid` now prints the server's value and the device's expectation **field by field** on rejection, and the heap and largest free block when the parse itself fails.

- Fixed a **unit error on the device that made a broken instrument look like a fast one**. `elapsed` was already in milliseconds -- the divisor had been applied when the timestamp was taken -- and it was then accumulated into a field named `panel_us` and divided by a thousand again on the way out. Measured, that reported 6 ms of drawing for 107 frames, which is 0.06 ms a frame, while `inflate_ms` on the same line reported 12.3 ms a frame for work that happens inside that very interval. Two numbers in one line that cannot both be true is what a unit error looks like. Corrected, a frame costs 63.5 ms to draw, consistent with the 74 ms `decode_max_ms` peak. `decode_max_ms` was also changed from a session-wide maximum to a **per-interval peak** -- it was reset only at session start and printed directly, so it could only ever climb -- and a `panel_frames` count was added so the mean has a denominator and the instrument can be checked.

- Re-measured after the fix, **the previous round's ceiling conclusion holds and now has independent confirmation**: 63.5 ms a frame to draw, a 74 ms peak, against a 90.9 ms slot at eleven frames a second -- about 16 ms of slack. The earlier conclusion rested on a field with a unit error: right answer, unsound evidence.

- Measured and rejected: **double-buffering the stripe so the SPI transfer overlaps the next stripe's decoding.** The reasoning held -- waiting for the DMA 31 ms a frame with the processor idle -- and the device showed no improvement at all: 10.5 frames a second against 10.4, `decode_max_ms` 70 against 72 to 81, panel time per frame 61 ms against a range that was already 38 to 82. The SPI engine is already overlapped with the next stripe's preparation; the wait was not the serial point it appeared to be. The second buffer also wanted 10 KB of a heap that had none, which surfaced as the channel list failing to parse at session start (`No memory to parse the channel list`), and cutting the packet buffers to pay for it then cost 31 dropped frames. Reverted in full.

- **The device's own drawing time is the frame-rate ceiling.** `MAX_FPS` had been set by fixed-rate probes (twelve, then fifteen), and that probe contradicted itself: asking for eighteen frames a second failed to establish a session while asking for twenty-one established one and delivered 13.9. Removing the ceiling and letting the controller hunt upward showed why a probe cannot answer this -- every session climbed to 14.9 frames, the receiver ran out of free buffers (`nobuf` went 0, 12, 45 within three windows), and the picture then lost frames permanently, while both of the controller's signals read healthy: **from the sending side, a fast link and a device that cannot draw look identical.** Measured, a 240x180 frame takes up to 80 ms to draw (`decode_max_ms`, steady across hundreds of frames). At twelve frames the slot is 83.3 ms, three milliseconds of slack; at eleven it is 90.9 ms. **The ceiling is eleven.**

- Fed dropped frames into the rate controller. It had two signals -- write duration and window bytes -- both measured at this end of the socket and both blind to whether the far end could draw what it was sent. A frame abandoned because it could not be placed in time now lowers the rate immediately. **Every drop counts**: tolerating isolated drops (on the theory that one loss is noise) was tried for 420 seconds and raised the median rate to 12.1 while the frames lost went from 0 to 339. When the operating point *is* the device's limit, a lost frame is a signal rather than a statistic.

- Measured and rejected: **merging the index expansion and the 4/3 enlargement into a single pass.** The merged version was verified pixel for pixel against the two-pass result and writes 153600 fewer bytes a frame, and it is slower -- the device's `decode_max_ms` went from 78 to 91, and replacing the inner division with a multiply changed nothing (90). The cost is the lookups: two passes do 43200 palette reads and then move bytes, one pass does 76800, one per panel pixel, and a table read on this chip costs more than the byte moves it saves. Reverted.

- Fixed the sound being drained while a picture packet was in flight, which is what the viewer reported as the picture coming and going. Three changes: **audio chunks 20 ms to 40 ms** (the same number of queue slots then holds twice the time; this had been rejected once for saving no bytes, and that reasoning rested on bytes being scarce when the scarce thing is packets); **the audio lead from 200 ms to 320 ms** (one task reads both streams, so a picture packet in flight is time in which nothing drains the queue, and a 240x180 frame is about 13 KB taking some 220 ms to cross -- longer than the 200 ms the queue held; measured, every underrun was preceded by a ten-second interval with the sound full and the gap at failure was 305 ms every time, which is the device's threshold and not a variable); and **separating the audio lead from the video lead** (they were equal, and raising them together released the picture 200 ms early, bunching it against the sound -- measured, dropped frames rose from 9 to 58). The sweep: at 200 ms, ten underruns; at 260, none with a median of 10.0 frames; at **320, none with a median of 10.8 and nothing dropped**; at 400, none but 39 dropped and back to 9.0. The device's `PCM_QUEUE` went from 30 slots to 24.

- **Compression level 1 to 6, saving 9.4% of every frame.** Level 1 was chosen because the gap to level 6 measured under a fifth of a percent -- measured at the old geometry, and the figure moved when the geometry did. At 240x180 indexed: level 1 costs 13412 bytes a frame, level 3 12905, level 6 12147, level 9 12141, for 0.9 ms of compression a frame against 0.4. **Those bytes are frame rate directly**: over 420 seconds the median rate rose from 9.1 to **11.9**, video traffic fell from 143 to 121 kB/s, and dropped frames went from 46 to **0**. The lesson is that "under a fifth of a percent" has to be re-measured when the geometry changes rather than quoted from the day it was measured.

- Raised the video packet ceiling from 12288 to 16384 bytes and cut the buffer count from four to three, so that one frame of live television crosses as one packet. **The scarce resource is packets a second, not bytes** -- the device's receive path tops out near 72 a second, and a 240x180 frame measures about 13400 bytes, so at the old 12288 ceiling every frame split into two, costing twenty-four video packets a second at twelve frames against fifty for the sound. With the ceiling raised the same rate costs twelve. Memory is unchanged: three of sixteen kilobytes is 49152, exactly what four of twelve was, and a single 16384-byte block still fits the device's largest free block of 36864. This explains an earlier reading that made no sense -- asking for sixteen frames a second delivered *less* than asking for twelve (83 kB/s against 156) -- because the surplus packets crowded out the sound, whose underrun then took the session down. After the change a sixteen-frame request reaches 13.7 frames with the sound full.

- Three encoding-side ideas measured and rejected, recorded so they are not tried again: **PNG filters** (sub/up/avg/paeth) all made it worse, the best of them by 19%, because the indices are already quantised and deflate's back-references exploit their repetition directly -- subtracting a neighbour destroys the pattern rather than exposing it; **sharpening** (unsharp) is unusable, worsening error by 61% to 165%, because the 3-3-2 grid gives blue only four levels and ringing and banding arrive before any perceived gain; and **reducing colour depth** to 64 colours saves 30% of the bytes for 66% more error, so at a fixed budget bytes are always better spent on pixels than on colours.

- 320x240 native was re-measured after the packet ceiling rose and still cannot hold a session: nineteen interruptions in 300 seconds, every one an audio underrun, and seven frames a second at best. It has the lowest error in the offline comparison (9.85 against 11.78 for 240x180) but the live path will not carry it. 240x180 is where sharpness and stability meet.

- Confirmed that adapting beats a fixed rate: over the same 300 seconds the controller underran the sound twice and dropped nine frames, while a fixed twelve underran eight times and dropped thirty-three. The controller's median rate is one frame lower and it keeps the session.

- The picture geometry is settled at 240x180 in, enlarged 4/3 on the device. Every member of the family -- each multiple of twenty columns, each size whose stripes divide the panel's 240 rows -- was rendered offline through the device's own enlargement and compressed the way the server compresses, and the promising ones were then flashed and measured. **Enlarging does not pay**: compressed bytes per pixel get worse as the picture shrinks (0.28 at 320x240 against 0.33 at 160x120, measured), so part of what sending fewer columns saves is handed back, and picture per second falls with every step down. Measured: 160x120 enlarged 2x runs 12 frames, 200x150 at 8/5 runs 12, **240x180 at 4/3 runs 11**, and 320x240 native manages 7 with the sound underrunning every forty seconds. 320x240 has the most pixels a second but cannot hold a session; 240x180 holds eleven a second for 200 seconds with the sound full and nothing dropped, which is the most picture a second among the ratios that stay up. With the adaptive controller on it is cleaner still: 200 seconds, no interruption, no dropped frames, sound at 499-503. The default is therefore adaptive, starting at ten. Added `tools/geometry_sweep.py`, which compares the family without touching the device.

- Corrected two earlier and wrong accounts of what the link carries. `server/rate.py` and `server/usb_link.py` each stated a figure (227000 and 175000 bytes a second), both derived rather than measured, while the device has been measured receiving 243000 with nothing dropped and the sound full -- an estimate of ours had been taken for the device's limit and written into the documentation as one. No constant capacity is stated anywhere now: the rate controller decides from measurement, and the same device in the same room has measured between 141 and 243 kB/s across sessions.

- The picture geometry now takes 200x150 in and enlarges it 8/5 on the device to fill 320x240. The version before this sent a full 320x240 frame, which measured out at 6.5 frames a second on this link; and the link's ~175 kB/s is a hard ceiling: ask for 190 kB/s and sessions stop establishing, while 156 kB/s runs indefinitely. With the total fixed, the only free variable is how many pixels a frame carries. 8/5 is the one integer ratio that beats the published version on both counts at once: 200x112 on screen against the published 160x90 is **1.56x the pixels**, and twelve frames a second measured 117/120 completed (97%) with the sound at 500/500 and no dropped frames, **1.13x the rate**. The ratio is integer rather than arbitrary so that every output pixel is an exact copy of an input one, with no interpolation and no rounding; the stripe geometry follows from the ratio rather than being chosen separately -- the panel takes sixteen rows at a time, the picture supplies ten (16 x 5/8), and 150 rows is fifteen of those; ten rows of 200 pixels are 2000 index bytes, which enlarge into exactly the panel's 10240-byte stripe, so **the change costs no memory**.

- Fixed the device dropping every session on connect because CONFIG failed validation. `AV_STRIPE_ROWS` has sixteen uses on the device; fifteen mean "the panel takes sixteen rows at a time" and exactly one means "how tall a stripe the server cuts". Changing the picture to ten-row stripes updated the former and missed the latter, so the server sent 10, the device demanded 16, CONFIG was judged illegal, and every session connected and dropped a second later having sent no media. What that looks like from outside is not a rejected configuration: it is a device that keeps reconnecting and sends nothing, indistinguishable from a link fault or an unstable network -- and this repository has recorded the same symptom once before (the `channels` key collision), so it should have been recognised. - Fixed ffmpeg taking the 256th palette entry. `palettegen` reserves an entry for transparency by default and writes pure green into it, which the device has no use for -- that entry could hold a colour from the source instead. The reservation is now off and all 256 come from the source.

- Fixed the exit summary's failure count being sometimes too high and sometimes too low. When a device disconnects after authenticating, two code paths can notice, and which one notices first decided whether the session counted as completed or as a fault -- measured, wrong about one run in ten, and that number is the only statistic the operator is shown at exit. The boundary is back where it belongs: a break before the handshake is a viewer who changed their mind and is not counted, and a break after it is a real fault and is.

- Fixed importing a clip leaking a file descriptor each time: only the pipe being read was closed and the stderr pipe was left open. Invisible from a single command-line run, one descriptor per clip on a long-running server.

- Fixed importing a clip writing *a picture of* the frame rather than the frame. ffmpeg's `image2` muxer picks an encoder from the file extension, so a 76800-byte indexed frame became a 13287-byte PNG -- both larger and no longer the indices the device reads. The import now reads raw bytes a frame at a time, with no encoder between the two ends.

- Fixed the device abandoning a channel that was playing but momentarily unstable. The old rule counted consecutive sessions that ended without a picture, and a source that stutters produces exactly the same count as a source that is gone: two fruitless reconnects and the channel was treated as dead and skipped, taking the viewer's choice with it. What separates the two is whether the channel has ever produced a picture -- one that has is retried where it stands however many times it fails, and only an entry that has never shown anything is stepped over. The original purpose is untouched: a dead entry is still skipped, or the viewer stays trapped on the test pattern. The rule lives in `main/av_channel_policy.c` so it can be tested on a host; `tests/test_av_channel_policy.c` covers twelve cases, including the one that needs more than a single remembered channel -- watch A, watch B, return to A, and A is still protected. Reported by a user: an unstable channel made the device move on by itself.

- Fixed an automatic channel step clearing the flag that records a deliberate choice. That flag gives a channel the viewer picked a wider allowance -- four fruitless sessions rather than two -- and clearing it made the next channel look automatically reached, which is narrower. The step now clears the flag only for the channel it is leaving, and the flag means what it was written to mean.

- Fixed HTTPS failing in every downloaded build: the playlist would not load and ffmpeg was never fetched, both answering `unable to get local issuer certificate` for addresses that work in a browser. Python reads its certificate authorities from a path fixed when it was compiled, and a build made on one machine and downloaded to another inherits the build machine's path, which does not exist on the reader's. `tools/certs.py` now adopts a bundle that is actually present, and checks how many authorities loaded rather than that a file exists -- the weaker check is what the first attempt got wrong. Verified by building with a Python that has no bundle of its own and taking the machine's away: before, both the playlist and the ffmpeg download failed; after, both work. Reported by the user, in the first thing they tried.

- Fixed the two child processes outliving the launcher. The next run then reported a busy port with nothing on screen connecting it to a program the user believed they had closed. In a bundled build the orphaned children also held a reference to a temporary directory their parent had already deleted, so they worked from what they had loaded and then died with `LookupError: unknown encoding: idna`, a message that describes the symptom and nothing about the cause.

- The orphan watch now works on Windows, which took two attempts and a measurement. Watching `os.getppid()` detects an orphan on POSIX, where a child is reparented; on Windows the parent id never changes and the check never fires, so the build passed on macOS and Linux and failed on the platform it was reported from. A stdin pipe held by the launcher works on POSIX -- the kernel closes it when the launcher dies however it dies -- but the Windows bundle goes through a bootloader that does not pass stdin through, so the child was reading a different stream. Windows now uses the mechanism it has for this: a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which makes the kernel end every process in the job when the launcher's handle closes. Verified both ways -- `kill -9` on the launcher leaves nothing behind, and an ordinary exit still lets the children shut down properly and print their last line, which is the order that matters: the forceful path is a fallback, not the normal one.

- A daemon thread reading `sys.stdin.buffer` while the interpreter shuts down is a fatal error, not a warning: Python finalises with the lock held and aborts with `_enter_buffered_busy`, turning a clean exit into a crash. The watch now reads the raw file descriptor with `os.read`, which takes no such lock. Found by running it rather than by reading about it, and worth recording because the failure only appears on the exit path -- the one path nothing else exercises.

- Closing the terminal window no longer prints a Python traceback.
