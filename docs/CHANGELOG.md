# Changelog

## Unreleased

- Fixed HTTPS failing in every downloaded build: the playlist would not load and ffmpeg was never fetched, both answering `unable to get local issuer certificate` for addresses that work in a browser. Python reads its certificate authorities from a path fixed when it was compiled, and a build made on one machine and downloaded to another inherits the build machine's path, which does not exist on the reader's. `tools/certs.py` now adopts a bundle that is actually present, and checks how many authorities loaded rather than that a file exists -- the weaker check is what the first attempt got wrong. Verified by building with a Python that has no bundle of its own and taking the machine's away: before, both the playlist and the ffmpeg download failed; after, both work. A build check now asks the built executable this question with the machine's bundle withdrawn, so a release that cannot verify a certificate fails before it is published. Reported by the user, in the first thing they tried.

- Fixed the two child processes outliving the launcher. A closed terminal window or a plain `kill` sends SIGTERM, which took Python's default path and skipped the cleanup entirely, leaving the media server and the channel page running in their own session with ports 8096 and 8097 still open. The next run then reported a busy port with nothing on screen connecting it to a program the user believed they had closed. Signals now route through the same shutdown as Ctrl-C, and each child stops itself if the process that started it disappears -- the case a signal cannot cover. In a bundled build the orphaned children also held a reference to a temporary directory their parent had already deleted, so they worked from what they had loaded and then died with `LookupError: unknown encoding: idna`, a message that describes the symptom and nothing about the cause.

- The exit line no longer reports ordinary events as faults. A connection closed during the handshake -- what a channel change, a sleeping device and a port check all look like -- was counted as a failure, so a healthy run ended by reporting three faults and no way to find out what the three were. Those are now counted separately and kept out of the line; a session that breaks after authentication is still a failure and still reported.

- Audited every line the server prints to the person running it. The start-up notice went from sixteen lines to four: the address being listened on was dropped (it is this machine's own number, wanted by nobody in particular -- the device is given the name), and what remains is the one address to type on the device, with at most one line naming the fallback. Five prompts that were still English became Chinese, so the program no longer changes language halfway through; the Ctrl-C exit stopped reporting an internal failure count; and a port already in use -- twenty lines of Python traceback ending in `OSError: [Errno 48] Address already in use` -- is now two readable sentences, told apart by `errno.EADDRINUSE` because that number is 48 on macOS and 98 on Linux. `--help` is Chinese as well, including the `usage` and `options` headings argparse spells for itself.

- Release pages now explain themselves instead of showing a list of filenames: which file is for which computer, that flashing the device and running the server are two separate things both needed, and the two prompts users meet first (the Windows firewall and the unsigned-program warning). These were reported as an empty body twice before the cause was found: the release job does not check out the repository, only downloads the built artifacts, so a `body_path` naming a file in the repo resolved to nothing and the action fell back to an empty page. The text is inlined into both workflows, and it has to stay identical in both -- whichever job runs second rewrites the release.

- The server is now a download-and-run: single-file executables for Linux, macOS and Windows (`tv-server-*`), double-clicked with no Python to install. The first run fetches ffmpeg itself (about 21-31 MB, once; a machine that already has ffmpeg never touches the network), announcing the size beforehand and verifying a pinned sha256 -- a mismatch writes and runs nothing. ffmpeg is not bundled because those builds are `--enable-gpl`, and redistributing one carries the obligation to supply its source, whereas fetching it on the user's own machine does not. The executables are distributed through the releases page rather than committed.

- Server data is now separate from the code location: `tools/datadir.py` resolves a writable directory from `TV_DATA_DIR`, then the program's own directory when a real write succeeds, then the per-user location, and the chosen path is printed at start-up. The two used to share one `__file__`-derived path, which coincides only from a checkout; bundled, it names a temporary directory deleted on exit, so a saved channel list was lost. Children now find the `server` package through `PYTHONPATH` rather than the working directory, which separates those two duties.

- Fixed the first save of a channel list not restarting the media server: the check compared two timestamps, which requires the file to already exist, while a new data directory starts empty and the first save is exactly the case of a file appearing. Also fixed the restart passing a channel name from the old table -- a first save replaces the built-in channels entirely, so that name is never in the new one, and the server treats `--channel` as a required choice, exiting with nothing listening. It now falls back to the first entry of the new table.

- Windows console encoding: every message this program prints is Chinese, and a Windows console defaults to the system code page, so on an English system (cp1252) the first character raised `UnicodeEncodeError` and ended the process -- the user's first sight of the program was a crash. `tools/console.py` sets UTF-8 before anything is printed, called from all four entry points; a test reproduces the failure with a cp1252 stream, and a scan keeps a new script from being missed.

- Repository CI fixes: `main/ui_menu.c` used the POSIX `strnlen`, which glibc exposes only behind a feature-test macro, so macOS passed locally while Linux CI failed continuously; adding `_POSIX_C_SOURCE` was checked by cross-compiling to aarch64-linux-gnu and reproducing the original errors without it. Added a three-platform build workflow that starts each build as a smoke test, sharing a release concurrency group with the firmware workflow so the two cannot rewrite one release at the same time and lose files.

- Renamed the server side from `av` to `tv`: the module `server/av_server.py` to `tv_server.py`, along with the executable, release assets, environment variables and documentation. The firmware's `av_` prefix is unchanged -- that is audio/video codec work, which is not what this project does -- as is the firmware module name `av_protocol`. `AV_PAIRING_TOKEN` was kept at first on the mistaken belief that it was a name shared with the device; it is not -- the firmware's constant of that spelling only has to agree in value, so the server's environment variable became `TV_PAIRING_TOKEN` with the rest.

- The build's own smoke test could not read the program's Chinese output on Windows: `subprocess.run(text=True)` decodes with the system code page, so the reader thread raised `UnicodeDecodeError`, stdout came back as `None`, and the check died comparing it. The program was correct throughout -- the check that inspects it was the broken part. Every subprocess capture in the repository now states its encoding, checked by an AST scan that would notice a new one, and it found a second instance in the repository checker, where a Chinese path would have done the same thing.

- The orphan watch now works on Windows, which took two attempts and a measurement. Watching `os.getppid()` detects an orphan on POSIX, where a child is reparented; on Windows the parent id never changes and the check never fires, so the build passed on macOS and Linux and failed on the platform it was reported from. A stdin pipe held by the launcher works on POSIX -- the kernel closes it when the launcher dies however it dies -- but the Windows bundle goes through a bootloader that does not pass stdin through, so the child was reading a different stream. Windows now uses the mechanism it has for this: a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which makes the kernel end every process in the job when the launcher's handle closes. Verified both ways -- `kill -9` on the launcher leaves nothing behind, and an ordinary exit still lets the children shut down properly and print their last line, which is the order that matters: the forceful path is a fallback, not the normal one.

- A daemon thread reading `sys.stdin.buffer` while the interpreter shuts down is a fatal error, not a warning: Python finalises with the lock held and aborts with `_enter_buffered_busy`, turning a clean exit into a crash. The watch now reads the raw file descriptor with `os.read`, which takes no such lock. Found by running it rather than by reading about it, and worth recording because the failure only appears on the exit path -- the one path nothing else exercises.

- Closing the terminal window no longer prints a Python traceback. It sent SIGHUP twice -- measured under a pty, not assumed -- and the second arrived while the first was being handled, so the interrupt was raised from inside the handler for the interrupt: nothing caught it, and the last thing the user saw was a stack. The shutdown itself had been completing correctly; only the message was wrong, which is the kind of wrong that makes someone think the program broke. A second stop request is now ignored, and the same protection covers the stages before the children exist -- fetching ffmpeg, which takes half a minute -- by catching the interrupt at the top of the launcher rather than only around the part that runs children. Verified by closing a window under a pty: the traceback is gone, the exit code is 0 rather than 1, and both ports are released.

- Fixed the availability check calling working channels dead. The page asked each channel for `c.ua`; the field is `agent` and always has been -- the playlist parser emits it, the table stores it, the saver writes it back. So the probe request always carried an empty user agent, and a source that answers only a particular player refused it: a 403, no frame, and a verdict of dead for a channel that plays. Reported by a user who tested one, watched it play, and said the page was wrong -- which it was. Measured both ways with the real table: with the agent, eight of eight channels decode a frame in about half a second; without it, they fail in a tenth of a second, which is what the page had been showing. `tests/test_channel_config.py` now compares the field names the page reads against the names the server produces, so a name on one side and a name on the other are no longer connected by nothing.

- The start-up notice now says that closing the window stops the service. Nothing said it before, and the window looks like a log -- a thing you close when you have finished reading it -- while closing it ends the television picture on the device. A black screen and a window tidied away are two events with no visible connection, so the cost of not saying it is a picture that stops for a reason the reader cannot reconstruct. One line, after the address and after the network note, which is the only place it can be said while the reader is still looking at it.

- The flashing instructions told the reader that unplugging the cable would restart the device. It does not, for two reasons that were each checked against the hardware. The device talks over the ESP32-C3's built-in USB peripheral -- esptool's default reset pulls the RTS line, which is how an external USB-to-serial chip is wired, and a USB peripheral has no such pin, so `loader.after()` reported "Hard resetting via RTS pin..." and reset nothing. And the device has a 520 mAh battery, so unplugging stops the charging and nothing else. The result is a chip left in download mode with a dark screen, which looks exactly like a failed write. All three copies of the instructions -- the flashing page, the English README and the Chinese one -- now say to hold the power button to switch the device off and on, and the page no longer calls a reset that cannot work. A test keeps the three in step and keeps the claim out of the flashing section; it does not restrict the same words in the setup flow, where the firmware really does restart the device after the credentials are saved.
