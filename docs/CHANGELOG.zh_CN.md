# Changelog

## Unreleased

- 修正直播试验记录：保留各会话补静音及最终丢帧计数，区分正式观察、暖机和主动停止，缺失遥测报告为未知。采集完成不代表设备验收通过。

- **新增可选的直播发送引擎 v2 候选版。**完整包边界上的音频优先、有界部分写入、按字节配速的自适应视频及共同积压裁剪，用于处理真实频道拥塞，保留原生尺寸和 FAV1。主机测试不等于真机验收。见[候选版操作与边界](development/live-sender-v2.zh_CN.md)。

- **落在被丢弃音频区间内的画面拿到了它不可能有的会话时间，随后的钳制把恢复帧污染了 4.8 秒。**外部复核用真实的入队/出队方法实测：4.88 秒空洞内的三帧被打成 4750、4833、4917——没有任何声音占据的会话时刻——而映射正确为 120 毫秒的恢复帧，被"必须严格递增"这条规则推到了 **4918**。这条规则存在是为了让设备识别乱序的流。
  **三层修复。**分段现在除了起点还带**终点**，于是不在任何分段内的内容根本没有会话时间，而不是靠外推继承一个。内容落在空洞里的画面**被拒绝打戳**并丢弃。声称比已取走的声音更晚的画面同样被拒——它在分段还开着、空洞尚未暴露时就能抓住同一个缺陷。被拒的帧会计数（`unplaceable=`），因为静默拒绝和"从未有帧"无法区分。
  **这个守卫是单向的，这是有意的。**画面可以**落后**于会话已取走的声音——那是常态，声音本来就领先一个队列深度——但绝不能**超过**它：没有取走的声音就是没有听到的声音。这个守卫的早期版本比较的是绝对距离，结果拒绝了落后 400 毫秒的健康画面，而那根本不是故障。
- **直播回退现在由"谁的失败"决定，不由网址决定。**上一次修正按文件后缀分类；复核用同一个文件、换一条 `/watch?id=1` 的路径击败了它，已经被推翻的标定缺陷随之回来——画面前 4 帧再次被丢弃。两件事的分界既不是网址、也不是探测成不成功：媒体答了"没有起始时间"是关于源的事实，探针跑不起来则什么都说明不了。只有前者允许使用启动时间，且结果带标签。最后兜底的后缀检查只能拒绝回退，永远不能批准它。
- **校准失败现在看得见了。**`timeline.calibration_note` 被赋值在对象上、从未呈现；`start()` 丢掉返回值；`failure()` 始终为 None；`prebuffered()` 只看队列长度——于是"服务端知道 ffprobe 不在了"和"操作者能查出来"是两件事。现在记录一条 WARNING，写明原因并说明不会发送画面。它不是故障：直接拒绝会话会把降级变成没有服务。
- **有一条测试把模块状态泄漏给了下一条测试。**用 dict-update 还原 `CHANNELS` 时漏掉 `DEFAULT_CHANNEL`，它指向的键在下一条测试的表里不存在，导致一条无关测试报 `KeyError: 'ch000'`。现在 `load_channels` 重新绑定的每个名字都会被还原。整文件运行时才发现，单独跑一个类时看不到。
- **本轮真机测量比上一次弱，就如实这样记录。**真机五分钟：第一个会话**出现降级**（90 秒内 dropped 61、late 47、nobuf 19，10.72 fps），并在 t=255 秒以会话重置结束；第二个会话干净跑了 20 秒、11.66 fps。每帧面板成本全程 34.3 毫秒。**这没有复现上一次那条干净的 12.0 fps 零丢帧，而且它是两次里更晚的一次测量。**原因未隔离——`AUDIO_EMPTY` 出现四次，重置原因是 `video-read`。原始日志在 `docs/development/logs/device-native-12fps-r9.txt`。

- **画面现在用它自己的内容时刻打戳，不再用它所配对的那块声音的位置。**外部复核从构造上给出并实测了这个反例：内容 666.7 毫秒的画面配上 1000 毫秒的声音，被打成 **1000**——在一条完全没有音频缺口的流上人为加了 333 毫秒误差。旧式子是 `video(session_clock.audio_items)`，它看不见这个差，因为配对容差有 350 毫秒、而打戳把容差丢掉了。现在是 `video(frame_at)`，`frame_at` 是画面自己的内容在声音时钟上的位置。映射是**分段**的：丢弃的音频块消灭内容时间却不消灭会话时间，所以每个不连续点开启一个新分段，两侧的内容各自映射正确，而不是被强行拟合到一条直线上。
- **直播回退改成了"按故障"选择而不是"按源"选择，于是文件也漏了进去。**黑屏修复在 `ffprobe` 返回 None 时一律使用启动时间——而程序缺失、超时、请求被拒、文件未报起始时间，都会返回 None。复核实测了后果：同一个文件、仅让音频进程晚启动 600 毫秒，又丢掉画面前 4 帧，和修复前一模一样。现在依据由**源的种类**决定（`is_live_source`）；读不到起始时间的文件保持未标定并说明原因，而不是按进程启动顺序推算的偏移把画面发出去。画面不出，看得见；音画不同步，看不见。
- **探针不带 User-Agent，于是源把它拒了，而这个拒绝被读成了媒体的回答。**两路 ffmpeg 会带频道的 UA，因为很多源只应答它们被采集时用的播放器；`ffprobe` 没带，被 403，代码就断定"这个源不报起始时间"。现在它带同一个 UA，并且探测失败会记下**失败原因**——"ffprobe 没安装"、"ffprobe 超时"、"被拒绝"和"媒体没有起始时间"是四种不同的结论，只有最后一种是关于节目的。
- **上一轮交接里有三条声明与代码不符，现在都已修。**声称每行打印 `basis=`，实际打印了 **0** 次——字段挂在对象上而从未输出。`tools/timeline_acceptance.py` 在当前 API 上崩溃，而一份旧的输出还随包交付，那份输出描述的是一个已经不存在的代码版本；脚本已按当前 API 重写，覆盖六项验收条件，且期望落空时以非零退出。测试计数报成"223 通过、1 跳过"，隐含 224；实际总数 223，**本机 222 通过 1 跳过，root 下 220 通过 3 跳过**。
- **D4 未关闭，关闭声明撤回。**四部分完成三部分，两项待办，而且两项都是关闭声明**之后**由复核发现的。其中第二项是本文件新增的：**两路解码器读的是两个各自独立的 HLS 窗口。**视频 ffmpeg、音频 ffmpeg、ffprobe 各自独立打开同一个源；用本地 HTTP 源实测，视频窗口起点 1.464 秒、音频窗口起点 3.512 秒——真实相差 2048 毫秒——而第三次打开报出 48 毫秒，项目采用了 48 毫秒。记为 F22，**未修**：诚实的修法是由同一个输入同时提供画面、声音和时间戳，那要改动两个进程的启动方式。
- **真机上这次映射改动没有造成性能回退：持续 12.0 fps、丢帧 0、晚到 0、每帧 33–34 毫秒。**报告里那个残差的含义没有变，但标签现在是对的——它量的是**队列深度差**，不是音画同步误差，因为两路按构造被放在同一个时钟上。残差为常量表示画面队列比声音队列深那么多；残差持续走偏才是漂移。

- **画面根本没到过设备，而修好它的是"只对直播源生效"的回落依据。真机实测：原生 320×240 下 12.0 fps，零丢帧。**
  **故障本身。**内容时间轴改为依据"媒体自身的流起始时间"之后，`stream_start_times()` 对频道表里的每一个源都返回 None——直播 URL 不报起始时间——于是时间轴永远标定不了，`pop_video()` **永远**拒绝配对。真机实测：两分钟里 `audio_sent` 涨到 2600 以上而 `video_sent` 是 0，声音完全正常，屏幕全黑。没有测试抓到，因为每个测试都用桩频道，桩自己从队列里回答 `pop_video()`，从不查标定状态。
  **修法不是退回去。**文件和直播源在物理上是两回事，复核的反例只适用于其中之一。文件的内容在没人解码时也存在，所以进程启动先后说明不了它产出的是哪一段——这个论证成立。**直播**源在解码器接入之前没有内容，两个进程接入的是同一个直播边缘，所以启动差**就是**内容差。依据现在由源的种类决定，存在时间轴上，并随每一行报告打印出来，因为同一个 600 毫秒在不同依据下含义相反。
- **`tools/transport_probe.py` 有五个缺陷，每一个都让链路显得比实际更差。**是用出来的，不是读出来的：
  - 它发 640 字节/20 毫秒的音频并声明 `audio_chunk_ms: 20`。固件要求 1280/40，否则拒绝 CONFIG，所以这个探针根本维持不了会话——而它的数字看起来仍像数字。
  - 帧内写超时被捕获后继续循环。`send_packet` 可能在写了半个包之后抛错，于是流错位，设备每个会话都以 "header-decode" 结束。110 秒里 12 个会话，从外面看像设备拒绝负载。
  - 配速拿一个在写帧之前取的时间戳去比截止时刻，于是永远睡满上限：请求 4 fps 实际打出 **267 kB/s**。一个设不准自己测量速率的仪器，没有在测速率。
  - 音频是每帧之后成串发的，不是按节拍发的，于是设备的流控把读取端卡住，画面反而没人读。
  - 画面用的是**墙上时钟**打戳，而声音领先一圈。设备的时钟就是它的声音（`estimated_pts()` 是 `submitted_samples/16000`），落后超过 100 毫秒的帧会被丢弃，于是每一帧都显得陈旧：收到 97.4 kB/s、134 个包，**每秒只画完 1.4 帧**。这和 `SessionClock` 要消除的是同一个缺陷、同一个形状——探针复现了它，这反过来是服务端那处修法的佐证。
  五处修完之后，探针把 4、8、12 fps 都跑准了，并完整跑完一个 38 秒的档位，合计 **232 kB/s**（画面 200.8，声音 31.2）。
- **真机实测，五分钟，原生 320×240，预算 240000：270.6 秒内均值 11.78 fps，画完 3189 帧，`late` 0，`dropped` 8，`nobuf` 8。**每帧：面板 33.8 毫秒，解压 16.2 毫秒，收到 167.3 kB/s。同一时段服务端：发音频 7265 块、画面 3406 帧。原始日志在 `日志/设备原始串口-原生12fps-5分钟.txt` 与 `日志/服务端会话-原生12fps-5分钟.txt`——第五轮那条"8 fps"没有这样的日志、只能记为未核验，这一条有。
- **音画残差是有界的，不是持续走偏：均值 −292 毫秒、最大 −348 毫秒，在 843 到 3406 次配对之间保持平坦。**每行报告为 `drift=`/`worst=`。它是残差而不是"不相等配对数"，因为画面配在容差之内，从不恰好在点上。
- **`stray` 这个名字是错的：它数的是续包，不是杂散包。**`starts=79 stray=158` 恰好是三包一帧里每帧两个续包。按字面理解以为丢了东西，其实没丢；记下来，免得下一个人去追。

- **内容时间现在真的到了线上。画面的时间戳在选帧的地方决定，发送端再也算不出自己的那份。**
  **原来错在哪。**`pop_video()` 用内容时间选了帧，随后把这个结果丢掉了——`pop_audio()`/`pop_video()` 只返回负载，`tv_server.py` 用 `video_pts = max(audio_pts, last_video_pts + 1)` 给画面打戳。那个值说的是**发送端**走到哪儿了。它不管那一趟有没有选出画面都在动，又只在画面恰好发出去的那一趟提交，于是画面携带的是"它被找到的时刻"而不是"它所属的时刻"。在健康的流上它等于声音块的序号，看着是对的——这正是它至今躲过所有测试的原因。
  **换成什么**（`server/timeline.py` 的 `SessionClock`）：内容时间和线上时间是两个不同的量，谁也不能当另一个用。设备的播放时钟是 `submitted_samples / 16000`——它数的是**收到**的声音——而 `av_stream_accept()` 会拒绝任何时间戳不等于上一块加一个分块的音频包。所以声音的线上时间戳就是它的**序号**，按构造连续；画面的时间戳是它所配对的那块声音的序号。两个出队函数现在都返回 `(负载, 时间戳)`。
  **声音的内容时间没有被丢掉，它正是跳段变得可见的地方。**源跳了不会打断线上序列——设备会拒绝那样做，而被漏掉的声音从未被听到、在会话里不占时间——所以改为把缺口计数并报告为 `gaps=N/Tms`。
  **线上看不见的漂移，在两个时钟同时可见的地方测量。**因为画面用的是声音的位置，两者按**构造**同步前进，它们的差证明不了任何事。残差在配对处按内容时间取，报告为 `drift=+Nms worst=+Nms`。它是残差，不是"不相等配对数"：第一版数不相等的对，结果在一条**完全健康**的流上报出九帧"偏后"——因为画面是配在容差之内、从不恰好在点上。**一个在健康时就报警的数不能用。**
  **有鉴别力的是 `test_the_sender_cannot_substitute_its_own_timestamp`**，验证方式是**把旧规则放回去跑**：它报 `frame stamped 440 ms`，而配对处给的是 4000000。另一条从线上读网格对齐的测试在**新旧两版都通过**，现在它的文档字符串里如实写明这一点，而不是留着让人以为它覆盖了什么。两个缺陷都是跑出来的：新测试的第一版在旧代码上照样通过，漂移计数器也一直错到一条健康的桩报出漂移才现形。
- **频道表那条测试会随工作目录通过或失败。**`load_channels()` 按进程当前目录解析 `channels.txt`，于是 import 时建的表在仓库里是真实的 127 行，在 `tests/` 里是四条内置频道。断言拿仓库的行数去比哪一种，全看从哪儿启动。现在它显式解析指定文件，量到的是代码，不是调用者。

- **内容时间轴的偏移依据第二次出错，被一次外部复核用真实 ffmpeg 推翻。现在依据来自媒体本身，复核的两个反例都通过了。**
  **两次错误是同一个形状。**第一次用每个流的**第一个到达时刻**——把网络的行为当成了节目的行为。第二次用两个 `Popen` 返回时刻——把调度器的行为当成了节目的行为。两个解码器都从源的**第 0 个采样**开始读，所以**进程何时启动，说的是它何时开始产出，不是它产出的是哪段内容**。复核直接证明了这一点：同一个文件、仅让音频进程晚启动 600 毫秒，算出的偏移是 +600 毫秒，并丢掉了画面的前 4 帧，而媒体根本没变。另一个音频确实从 600 毫秒开始的文件只算出 +0.2 毫秒，把一个真实的差异抹掉了。
  **换成什么**：`ffprobe -show_entries stream=start_time`，由 `server/live.py` 的 `stream_start_times()` 读取一次。那是节目的属性，也是三个候选量里唯一能被两条流同时回答的。在复核自己的样本上实测：`same_origin.mkv` 读出 `(0.0, 0.0)`，`audio_offset_600ms.mkv` 读出 `(0.0, 0.6)`。把复核的脚本对着这份源码重跑，得到 `same_source_different_launch_selects_different_content: false` 与 `known_600ms_source_audio_offset_lost: false`。
  **ffprobe 答不出来的时候**——直播 HLS 播放列表常常不报起始时间——时间轴保持未标定，`pop_video()` 拒绝配对。**编一个偏移比承认没有偏移更糟**，而前两版正是这么做的。
- **`BoundedQueue` 被删掉，而不是接上去。**它被 import 却从未实例化，而外部复核补上了定论的那半句：固定产出率下 `deque(maxlen=N)` 本身就有内容时长上界，所以这个类在解决一个不存在的问题。删掉它，正是对"不要再为审查术语增加辅助模块"的正确回应。
- **`SourceState` 算出来之后被丢进了局部变量**——被当作已完成引用，却什么也没影响到。它的结果现在出现在周期报告的 `source=` 字段里。它**有意不接控制器**：源停止时队列里的存量仍在真实写入，那是对下游能力的有效证据，所以源进度与下游容量是两个测量，不是一个布尔值。
- **静态门禁没有跑最近两轮新增的测试。**`tools/validate.sh --static` 用的是显式文件清单，而 `test_config_agreement.py` 与 `test_timeline.py` 都不在其中——于是门禁是绿的，却一个都没覆盖；而人工跑 `unittest discover` 的人看到它们通过，就报告说已覆盖。现在清单之后加了一道发现式调用；门禁报 203 项，此前覆盖得更少。验证方式：故意改坏 `test_timeline.py` 的一行，看门禁报错。
- **多包的验收是用全黑帧演示的，而黑帧编码出来只有一个包。**外部复核用同几何的固定种子噪声帧给出了反例：**4 个包、77003 字节**。多包帧在这里是普通内容，不是边角情况。现在有真实测试覆盖"一帧的多个包共用一个内容时刻、并且一起离开队列"。
- **宣称"实机 8 fps"没有对应的日志。**随包的三份日志与上一包逐字节相同，所以这个数字记为未核验，不再重述。`v_lag` 是队列头之间的差，不是观众听到与看到的实际同步误差的测量。

- **共同内容时间轴已实现，并且跑在真实播放路径上。对齐不再比较到达时间。**这一条四轮复核都在要，这一轮交付的是它本身，不是它的计划。
  **原来错在哪。**一个条目在会话中的位置是「到达时间 − 该解码器自身的启动时刻」，而那仍然是到达时间：网络停顿、读取慢、进程被调度走，它都会动。外部复核构造过反例——同一张画面晚交付 600 毫秒，就配不上它所属的声音，因为 600 毫秒超出了 350 毫秒的容差。
  **换成什么**（`server/timeline.py`，接进 `server/live.py`）：内容时刻是**数出来的**，`产出条数 × 间隔毫秒`。按实时播出的解码器，第 N 帧就是 N/FPS 秒的内容，无论它准时到还是晚三秒到。两个流没有共同原点——它们是两个 ffmpeg 进程——所以两者的关系**只从两个 `Popen` 返回时刻标定一次**，此后冻结。
  **我自己犯的一个错，是靠跑真实路径而不是只跑测试发现的。**第一版用每个流的**第一个到达时刻**标定。把反例重新走一遍 `pop_video()` 得到 `offset=-600ms, frame=None`：传输耗时被折进了原点，这就是同一个缺陷从"比较"挪到了"标定"。**而我的单元测试全程通过**，因为它们当初就是照着同一个错误假设写的。**到达时间绝不能进入偏移量**；`Popen` 返回时刻是已知的、无歧义的，网络之后做什么都改变不了。现在两种情形都读作 `offset=+0ms, frame=v0, lag=0.083s`。
  **模块里还有两件：**`BoundedQueue` 按**内容时长**而非条数设界，因为 180 条在 12 fps 时是 15 秒、在 3 fps 时是一分钟；`SourceState` 把源断供与链路拥塞分开，这两者在发送侧读出来完全相同，而要的对策相反。单个安静窗口不算断供（HLS 是突发投递），连续两个才算。

- **频道表不再需要 8192 字节连续内存，127 个频道的发布版因此能起会话了。**`config_valid()` 原本要分配一张临时的 `channel_t[AV_CHANNEL_MAX]`——每条 64 字节、整表 8192 字节——把服务端的 JSON 解析进去，再在锁内整表拷到发布表上，好让读的人在新表齐备之前继续看旧表。**在发布版的 127 个频道上，失败的正是这一次分配**：`No memory to parse the channel list: wanted 8192 B, heap=13192 largest=7680`。空闲堆有 13 KB，最大连续块 7680——差 512 字节，是碎片导致的失败，不是总量不足。127 个频道的 cJSON 解析树此刻正活在同一片堆上，把空闲空间切开了。于是每个会话都在配置校验这一步失败，屏幕一直停在等待画面。现在解析直接写进发布表，遍历期间把条数置零，这一次分配被整个取消，同时也修掉了空列表路径上的泄漏（旧代码在全部条目都被过滤掉时直接返回，没有释放 `staged`）。索引计算改为降级而不是拒绝：为它分配的 `char*[n]` 若失败，会话以索引 0 发布，不再当作失败。让出去的是遍历期间读者看到一张空表；而旧表本来也没有真正保住——它一直被显示到新表就绪，换台时显示的就是你刚离开的那张表。
- **显示通路的耗时拆成了几段，而且各段之和能对上。**`panel_us` 把解压、展开、放大、叠加和 DMA 等待混成一个数，`decode_max_ms` 又给出同一区间的峰值：三种不同的对策藏在同一个数字后面。新增 `expand_us`、`enlarge_us`、`overlay_us`、`submit_us` 四个计数器，与 `inflate_ms`、`panel_wait_ms` 并列打印，并新增 `parts_ms` 为六者之和。**这个和本身就是仪器自检**——总和大于它所在区间的长度，说明某个计时器坏了，而本项目已经因为 `panel_us` 里带错单位被误导过一次。叠加也在计时之列，尽管它在不覆盖的条带上成本为零，因为"叠加不花钱"这个假设本项目已经纠正过一次。

  **不产生伤害，所以不动它**：上限只是"还能不能再快"的天花板，实际发多少帧由预算判据按实测字节决定——链路能承载多少照旧发多少。跳档只影响控制器试探的方向，不影响已经发出的速率。**把上限磨平（比如限定它一秒最多变一次、或对它再做一层平滑）会换来一个更迟钝的控制器，代价大于收益。**记下来是因为这个跳动在日志里很显眼，下一次读日志的人会想修它。
- **设备实测与离线的算术吻合。**控制器测出 `frame=14106~16760B`（离线 17171），算出 `ceiling=6~8`（离线 7.0），实际落点 4→7。单会话、零失败、音画对齐 `v_lag` 稳定在 −0.3 至 0.0 秒。**这条同时验证了"上限由每帧字节推出"的机制在真实发布版频道上成立。**

- **修复一个被我自己的改动引发的连锁故障，使用者的三个症状是同一个根因。**把帧率天花板从 5 抬到 12 之后，`media.FPS` 跟着变成 12，而 `PREBUFFER_FRAMES = PREBUFFER_SECONDS × FPS` 于是从 40 帧涨到 **96 帧**；源实际只产约 6 帧/秒，**填满预缓冲从 8 秒变成 16 秒**。三个症状由此而来：
  - **换台慢**——预缓冲等待翻倍。
  - **换台还没出画面就自动跳到下一个台**——设备的"这个频道没救活就跳过"窗口等不过这 16 秒。
  - **音画不同步**——预缓冲是把画面和声音都攒够才开始发，攒的过程中声音照常实时灌进设备，而画面要等 96 帧才动；发送端又取队列**最老**的一帧，于是画面整体滞后十几秒。
  **修法**：预缓冲要等多久是**时长**，不该由天花板决定，改按 `START_FPS`（中位频道实测落点）折算。96 帧 → 40 帧，等待回到约 6.7 秒。实测 `video_q` 由满格 180 降到 **9**，音画恢复同步。
- **修复控制器的窗口时长错误——这是"帧率一路掉到地板"的真凶。**窗口的判据是 `now - window_started >= 1.0`，但它每次循环只求值一次，而循环会阻塞在写 socket 里：**被卡 800 ms 的那个窗口实际跑了 1.8 秒，却拿 1.8 秒的字节去比每秒预算 120000**，于是每一窗都判为超预算，速率 5→4→3 一路降到底。日志里的对不上正好指向它：`fps=4 video=123kB frame=16885B`，而 `123000 ÷ 16885 = 7.3` 帧，不是 4——按 1.8 秒算则是 `68 kB/s = 4 × 17 kB`，分毫不差。**现按实际窗口时长归一化**（`window_s` 由发送端传入），实测窗口读数回到 1.00–1.01 秒。
- **新增每帧字节数的测量，速率上限由它推出。**控制器每窗口拿到 `video_bytes` 与发出帧数，相除即该频道每帧成本；`预算 ÷ 每帧成本` 就是该频道能跑的速率。实测读数：`frame=15245B/12896B ceiling=7`（斜杠前后分别是平滑值与即时值）。**这条机制在设备上验证有效**：中位频道算出上限 6–9 并落在 4–6，最省频道算出 12 并一路爬到 12，与算术一致。
- **预算由 210000 改为 120000**，取链路实测约 160 kB/s 减去音频固定的 32 kB/s 后剩下的那一份。原先的 210000 自称"刻意宽松、是后备值不是测量值"，而**一个永远够不着的上限拦不住爬升**——控制器会一路升到写操作变慢为止，那之前队列已经满了。

- **「多数频道播一会就出现彩条」查清了：彩条不是画质问题，是设备音频欠载之后主动断开会话，屏幕退回等待画面。**使用者报告十个频道里九个在一分钟内变成彩条；设备串口日志给出的顺序是 `AUDIO_EMPTY gap_ms=305` → `Session reset: audio underrun; reconnect/rebuffer`。三条证据把成因钉在**画面包把声音抽干**上：其一，设备认定欠载的阈值是 `AUDIO_UNDERRUN_MS`（300 ms），而失败时记录的间隙每次都是 300、304、305——**一个恒定等于阈值的数不是会变的测量值，它就是阈值本身**，这个数在这个项目的音频工作里出现过多次而当时没有据此下结论；其二，设备自己的日志记着一次画面读取 `RX_IO stage=video-read bytes=19240/21399 elapsed_ms=612`，即 612 ms 里那个同时读两路流的接收任务没有碰过音频队列，而它只有 300 ms 的容忍；其三，**关掉画面只跑声音，八十秒零欠载**，服务端记录的最长发送间隔是 0 ms，而两路同开时每二十秒欠载一次。这一条是架构性的：一个任务读两个流，写在固件里。
- **把"速率上限由该频道自己的每帧字节数推出"实现了，算术是对的，但整组改动仍不稳，已按验证过的配置回退。**
  实现方式：控制器每窗口已经拿到 `video_bytes`，再让它知道这个窗口发了多少帧，两者相除就是该频道的每帧字节数；`预算 ÷ 每帧字节` 就是该频道的速率上限。**这个机制在设备上实测有效，读数如实**：中位频道测出 `frame=19036B`、`ceiling=6`，落点在 5–7 之间（原来是硬性 5）；最省频道测出 `frame=2900B`、`ceiling=12`，控制器一路 5→6→7→8→9→10→11→12，与算术预测完全一致。**所以推导是可靠的，不可靠的是配套的那几处。**
  配套改动有四：天花板 5→12、预算 210000→120000、生产端按目标帧率限流、发送端丢弃队列积压。**其中限流那处写错了判据**——我按"距上一帧的间隔"判断是否多余，而源本身的帧率可能低于目标（最省那个源只出 6 帧），于是**把源自己的合法帧当多余帧丢掉**：实测画面只剩 6.2 包/秒、队列空着、`prod_drop` 涨到 1900。改成判队列深度才是对的，但那一次运行时设备端日志为空（另一个采集进程占着串口），**没有拿到有效读数**。
  **本轮的教训要写在前面**：在一个没能一次跑通的改动上连续叠加了六处修改，每一处都还没验证就压上下一处，结果是越改越乱、且最后无法归因。**应做的是每改一处跑一次 300 秒**。已回退到天花板 5、预算 210000、无生产限流、`pop_video()` 无参，实测 300 秒单会话零失败、`prod_drop=0`、`late_video=0`；**推导机制保留在 `RateController.ceiling()` 里**，在天花板 5 之内暂不起作用，等配套的限流写好、单独验证过，再把天花板放上去。
- **两次利用"频道差异"的改动，实测都不稳，已回退。记下原因，因为方向是对的、机制不对。**
  想利用"省流频道能跑 10 帧"这个实测事实，先后动了四处：天花板 5→12、预算 210000→100000、队列 180→36、起点单独设 5。**结果都不稳定**：抬高天花板后控制器从 5 一路爬到 9 才撞墙，那时设备画面队列已满（179/180）、音频领先掉到 -1200 ms、`prod_drop` 到 1578，随后一路掉到 3 不再恢复；把预算降到 100000 想提前刹住，反而因为 `media.FPS` 跟着变成 12、生产远快于链路，`video_q` 又满格（36/36）、`prod_drop` 涨到 2138、`video_pps` 归零。**已全部回退到天花板 5、预算 210000、队列 180。**
  **机制上缺的一环**：速率上限应当由**该频道自己的每帧字节数**推出来（`预算 ÷ 每帧字节`），而不是一个全局常数、也不该靠在链路上试错去发现。服务器每帧的字节数是现成可得的，`rate.py` 也已经有 `VIDEO_BUDGET_BYTES`——把两者接起来就能让省流频道跑 10 帧、重频道落在 3 帧，且不需要任何探测过冲。**这是下一步该做的，本轮没做是因为它要同时改生产速率与发送速率两处，而两者现在是绑在一起的，改动幅度超出本轮能验证的范围。**
- **按使用者三次强调的"不能只测一个频道"做了全量测量- **按使用者三次强调的"不能只测一个频道"做了全量测量，结果推翻了一个常数。**先把 103 个频道离线过了一遍（各 15 秒 @6fps，按服务端的方式切成 16 行一条压缩，所以量到的就是链路上跑的字节）：**最省 2266 B/帧，最费 31271 B/帧，中位 17632，最费是最省的 13.8 倍。**差异来自内容本身——静止的演播室画面压起来只有快动作画面的一个零头。
- **于是发现 `AV_VIDEO_MAX = 22528` 覆盖不了全部频道：10 个频道（约 10%）一帧就超过它，每一帧都被拆成两个包。**上机验证（把设备要的 `ch013` 指向最贵的源，id 不变、只换源——**这是本项目一直缺的那个杠杆，频道 id 与源解耦，所以可以任意指定测哪个源**）：**`stray`（同帧续包计数）读到 664，`nobuf=9`，300 秒内 2 次失败，帧率 3.6。**这不是新毛病，就是先前记录里那个"原生反而不如放大清晰"的同一个拆包机制——**当时只在 ch000 上测，所以只看见了一部分。**
- **更要紧的是另一头：`MAX_FPS = 5` 是按中位频道定的，把省流频道硬压住了一半以上。**固定上限 12 时实测：**最省频道 10.2 帧**、中位 5.0、最贵 3.6。**同一个上限下相差三倍。**所以那个 5 不是保护，而是削平——它把一个本该跑 10 帧的频道压到一个重频道才需要的速率上。**现把天花板放回 12，让控制器按每个频道自己找**（`START_FPS` 保持 5 作为起点，因为它是中位频道的实测落点，而起点击在 12 会让每个会话开局过载、连丢几秒的帧）。
- **`stray` 在中位频道上也读到了 271**，所以"只有前 10 个频道会拆包"这个判断不成立：任何频道在画面繁忙的瞬间都会越过 22528。这一条与上面那条一起，说明上限该由每帧的实际字节决定，而不是由一份静态名单决定。
- **一次改错并回退：给控制器加"不重试刚失败的速率"以消除 4↔5 的横跳，是错的。**实测确实看到 `RATE 4 / 5 / 4 / 5 / 4 / 5 / 4 / 3 / 4 / 3` 的横跳，平均停在 4。于是加了一条"刚失败过的速率不再尝试"，被测试挡下——`test_a_comfortable_window_after_a_bad_one_starts_the_count_again` 的文档字符串写着它要断言的行为正是"一次故障之后爬回原处，而不是越过它"，而"原处"就是那个刚失败的速率。**横跳不是缺陷而是设计**：控制器的职责就是在容量附近探测，一超就退、有余量就进；把它钉在低一档，是拿永久损失帧率换掉一点抖动，更糟。已完全回退。

- **链路质量本身在恶化，而且用 40 个包量到了实据**：零丢包的那次 RTT 摆动 7–314 ms，随后同一条链路 **40 个包丢 7.5%、RTT 平均 115 ms、峰值 334 ms**。设备仍在 2.4GHz **信道 1**（40MHz 宽），而主路由不可改动，这一层无法从本项目处理。
  对项目的意义要说清楚：**这条链路的质量不足以支撑当前设计所依赖的时序假设。**设备与服务器都按"每帧 200 ms 级送达"来规划，而实测 RTT 的中位数就超过 100 ms、尾部到 334 ms，还伴随丢包。**在这种链路下讨论帧率目标是没有意义的**——控制器降到 3 帧、`video_pps` 仍只有 0.8，而设备端 CPU 只用了 38%。
- **内存这条路也堵死了，有硬数字。**曾考虑把设备的 TCP 接收窗口从 32768 抬到 65536（吞吐 ≈ 窗口 ÷ RTT，而 RTT 实测 200–314 ms，放大窗口是按这个模型最直接的杠杆）。**但会话期的堆只有约 20 KB、最大连续可用块 9728 字节**（`heap=20060 largest=9728`，在多个会话里反复出现），装不下 32 KB 的窗口缓冲。**放弃。** 先前曾误判会话有约 40 KB 空闲堆，那是早期次优固件的读数，已纠正。

- **查清了真正的瓶颈：不是带宽，是延迟抖动。而且它推翻了记录里的一条旧假设。**用 1200 字节的 ping 测这条链路（小包会掩盖问题）：**20 个包零丢包，但 RTT 从 7 ms 摆到 314 ms，平均 110、标准差 108。**这不是丢包，是**排队**。而 `docs/development/handoff-20260915` 里写着"我们这条链路是直接丢，不排队；而且设备不回报任何逐包信息，建不起延迟估计"——**前半句已被实测推翻**，当初用它否决 WebRTC 式拥塞控制的理由随之失效。
  这一条也解释了同一天内前后两次测量的巨大差异：先一次稳定跑 5 帧，后一次同一配置下 `video_pps` 掉到 0.8、`lookahead_ms=-1329`、`send_gap_max_ms=1851`。**五次测试给出的吞吐区间是 110–160 kB/s，而不是一个数。**
- **设备不是瓶颈，这一点有硬数据。**取同一份设备日志里的健康区间：`panel_ms=3839` 对 10000 ms（38%）、`inflate_ms=1061`（11%）、`decode_max_ms=71` 对 200 ms 的帧间隔。**设备有大量余力，是链路不喂它。**
- **编码侧也到头了，离线实测。**在原生 320×240 上用 `zlib` 扫策略（输入是同一段真实频道的 120 帧）：当前设置每帧 18968 字节；**Z_FILTERED 反而多 3.9%、Z_RLE 多 49.5%、Z_HUFFMAN_ONLY 多 63.7%**，level 9 只省 0.2%（与 level 6 的 0.2% 一致，早已记录）。条带放大到整帧能省 4.5%，但设备必须收完整个 76800 字节才能画，且超过条带缓冲 10 KB 的容量，**不可行**。
- **Mac 与设备在不同频段**：Mac 在 5GHz 信道 36（1200 Mbps、-36 dBm），设备在 2.4GHz 信道 1（40MHz 宽）。所以瓶颈在设备那一侧的 2.4GHz 链路——而 2.4GHz 信道 1 配 40MHz 会与 1–5 信道重叠。**主路由不可改动**，所以这一层只能如实记录，不能动。

- **帧率上限在超时修复后重扫过，5 仍然是正确的数。**原先定为 5 是在设备等 1500 ms、服务端只等 630 ms 的时期测的，那个不对称已经消除，所以前提已变、必须重测。实测（各 300 秒，固定帧率）：6 帧前 240 秒干净、第 300 秒起失败，最终 2 个会话 1 次失败；7 帧 6 个会话 5 次失败；8 帧 3 个会话 2 次失败。**三档的峰值入向速率都落在 151–162 kB/s**，请求更高只换来更多失败。**一个不随请求量变化的速率，就是链路的形状而不是负载的形状。**
- **两次针对"160 kB/s 是不是真上限"的尝试，都被实测否决，记此以免重来。**
  1. **放大 `SO_SNDBUF`**（16384 → 65536）。触发点是 `netstat` 反复显示发送队列顶在 16384——一个总是满的缓冲区看着就是太小。**实测相反：队列积压到 64 KB 而画面帧率反而从 5.0 掉到 2.2**（无失败会话）。**一个拿着 64 KB 却送不出去的发送端，缺的不是空间而是链路。**已回退。
  2. **抬高 Wi-Fi 的 `STATIC_RX_BUFFER_NUM`（6→12）与 `RX_BA_WIN`（4→12）**。两者都低于 ESP-IDF 默认值（10 和 6），且官方文档写明 AMPDU 开启时前者应不小于后者才有利于吞吐，而项目里这两个数是为解决内存问题设小的、从未为吞吐测过——**看起来是个真缺口，但受限于没有 sudo 抓包，无法在本轮判定，改动暂不回退的理由不足，故先回退并记录**。
- **链路本身在分钟尺度上波动，这是当前的现实。**同一天内先后两次测量，前一次稳定跑 5 帧，后一次同一配置下 `write was 558 ms`、五秒窗口里 3.9 秒卡在写操作上、帧率被压到地板 3。**这意味着单一的上限数字不足以描述这条链路**，也说明"按最好情况定上限"是错的。

- **根治了彩条：设备不再因为音频欠载而断开会话。实测 560 秒单会话零失败，此前是每 20 秒断一次。**三处改动，每一处都有实测支撑：
  1. **设备端：欠载改为播放静音而不是终结会话**（`main/av_player.c`，新增 `AUDIO_SILENCE_MAX_MS` = 3000 ms）。原来空队列超过 300 ms 就 `fail("audio underrun")`，而空队列是被**画面**造成的——一个任务读两路流，画面包在途实测 612 ms，而容忍度只有 300 ms。现在播放静音并继续，与画面掉帧而非断流同理。**不给假数据**：时钟按实际提交的采样数前进，画面对齐的就是真正播出去的时间轴。超过 3000 ms 才放弃，交给接收端自己的不活动超时。
  2. **设备端：四处读超时 1500 → 3000 ms**（新增 `AV_READ_DEADLINE_MS`）。原来设备对单个包的容忍是 1500 ms，而**服务端只等 630 ms**——服务端比设备先放弃，方向反了。现在两者一致。
  3. **服务端：生产速率与发送上限绑成一个数**（`media.FPS` 从 `rate.MAX_FPS` 读取）。原来 ffmpeg 产 10 帧而发送上限 5 帧，五个队列快照全是 `video_q=180/180`（满格）、`prod_drop` 每秒涨 5、画面落后直播约 18 秒。这不是故障而是**队列停止排水**：生产快于链路，多出来的帧在队列另一端被丢掉。
- **帧率上限按实测改为 5，下限由 6 降到 3。**设备实测持续吞吐约 160 kB/s；音频固定占 32 kB/s，画面剩约 128 kB/s，而原生一帧 20.5 kB。固定速率实测：**6 帧（123 kB/s）240 秒内 4 次失败；5 帧（102 kB/s）同样时长零重置、零失败**。下限 6 是"还能算动起来"的旧实测值，来自面板能跑 10+ 的时代；现在有了静音容忍，**降速远好于断连**，下限必须让位，否则区间为空（6 > 5）连控制器都构造不出来。
- **服务端写超时从 630 ms 提高到 1250 ms**（新增 `FRAME_WRITE_DEADLINE_S`）。原来它由 `frame_bytes / 32768` 得出，那个 32 kB/s 是悲观假设，而链路实测 160 kB/s。结果服务端在同一帧内就放弃，而设备还能再等——`TimeoutError phase=live_video_send` 是这次排查里反复出现的那个失败。上限设在设备 1500 ms 之下，保证放弃的决定由服务端做出，而不是被关闭的 socket 通知。

- **试过并否决：把一帧拆成两个包，让发送端在包与包之间有机会喂音频。已刷机实测，明显更差，已回退。**这条的来历是设备端自己的一段注释（`main/av_player.c:1123`）："这个间隙是真实的，但它是发送端该补上的，而发送端确实补上了——**只要一帧里的多个包之间有音频到期，音频就插在它们中间**。" 22528 字节一包时原生一帧只有**一个**包，那个间隙从来不存在；而服务端循环里确实有一段"包与包之间抽空送音频"的内层逻辑（`tv_server.py:1072`），等于白白空转。改成 12288 字节/包后一帧两包，理论上是每帧两次机会。**实测（固定 8 帧、300 秒、同一频道）：欠载 5→9 次、设备重置 11→24 次、13 个会话里 12 个失败、实测帧率 6.4→2.4。** 音频队列高水位反而升到 18 块、画面读取最长 492 ms、服务端最长发送间隙 512 ms。**结论：缩短单包并不能缩短整体阻塞，反而因为包数翻倍挤占了每帧一次的机会。**先前记录里那条"包数不是约束，字节才是"**并没有失效**——我一度以为它随几何变更而失效了，实测证明它仍然成立。设备端那句注释描述的是**发送端理论上有机会**，不是**拆包就能解决**。
- **找到了缓冲一直是 280 ms 的原因：发送端有一条"不得早于实时"的闸门。**把释放条件代进 origin 解一遍：`audio_at = t0 + audio_pts`，而放行要求 `now >= audio_at`。时间戳每发一块前进一块，于是**声音恰好按实时速率放行，一毫秒都攒不下来**；设备也按实时播放，队列就既不填也不空，只能停在启动时的瞬态。`AUDIO_MAX_LOOKAHEAD_MS` 是"最多可领先多少"的上限，在实时闸门之下**永远够不着**。这解释了两次看似矛盾的实测：领先量取 320 和 700、上限取 280 和 700，设备队列高水位**全都是 280 ms**——两个参数都推不动它。
- **新增开关 `TV_AUDIO_FILL`（默认关），允许发送端提前把缓冲填到上限。**打开后服务端记录的领先量从 0–30 ms 变成 596–629 ms，设备队列高水位从 7 块（280 ms）升到 **18–21 块（720–840 ms）**，欠载从 5 次降到 **2 次**、重置从 11 降到 6（都是固定 8 帧、300 秒）。**但没能根治。**
- **服务端自己会被写操作阻塞，这是剩下的成因。**同一份日志里 `send_gap_max_ms=737`、`busy=2.1 s`（五秒窗口里两秒多卡在写 socket 上），设备端同时 `queue=0`、`gap_ms=302`。也就是说：**循环的阻塞不是"音频优先"能救的，因为阻塞发生在画面包的写操作内部**。缓冲再深也深不过发送端停摆的时间——737 ms 的最坏停顿对 800 ms 的缓冲，只剩 63 ms 余量，所以填充能减少欠载而不能消除。`SO_SNDBUF` 这条路先前已经走过并把结论写进了注释（16384 是实测优选，65536 反而更差，一次跑出十个失败会话）。
- **一次改错并已回退的尝试，记下来是因为它读起来完全正确。**`tv_server.py` 里 `origin = now + max(START_DELAY_MS, AUDIO_LEAD_MS)`，而一块音频的释放时刻是 `origin + (audio_pts - AUDIO_LEAD_MS) / 1000`，于是看起来**领先量被精确抵消**、`AUDIO_LEAD_MS` 从设上那天起就是空转的。据此把 origin 改成 `now + START_DELAY_MS`——**这是错的，而且方向相反**。这个表达式决定的不是第一块音频何时发出，而是 `audio_pts` 相对时钟能领先多远；解出来，领先量取 320 时两种写法都给 320 ms。改后反而把缓冲砍到 120 ms，因为 origin 是时间戳所依据的那个墙上时刻，而领先量是从它量起的。已回退。
- **一处工具性错误，代价是一次假读数。**看门值取 700 ms 的那一格，`AUDIO_EMPTY` 数出来是 0，脚本据此报"零欠载"——而设备日志文件其实是 **0 字节**，是上一个采集脚本还在跑、两个进程抢同一个串口。**空日志对每个信号都返回零，那是一个空洞的零，不是一次干净的测量。**采集脚本现已加入自检：设备日志小到不合理就直接判该格无效并停止。
- **把缓冲加到 800 ms 也并没有止住欠载**，所以「缓冲不够大」不是完整答案。原因在同一份日志里：那样一次画面读取要 612 ms，而 800 ms 的缓冲意味着设备已经顶到自己的流控线（`PCM_QUEUE-4`，二十块四十毫秒），设备一旦越线就进入睡眠不再读 socket，画面反而被卡住。
- **降帧率也救不了，这条把"带宽"排除了。**固定 7 帧/秒、总流量约 155 kB/s（远在链路实测 141–243 之内）跑 300 秒：**5 次欠载、11 次设备重置、服务端 5 次会话失败**，实测帧率只有 4.4。而同一个频道、同样两路同开，100 秒的短跑曾零欠载——**短时段的好读数靠不住**，这一点要连同这次的误判一起记。
- 顺带记一条**结构性的量错**：`rate.py` 的 `VIDEO_BUDGET_BYTES`（210 kB/s）只数画面，不数声音，而链路上跑的是两者之和。原生一帧 20.5 kB，十帧就是 205 kB 的视频——控制器读作"还有余量"，而 socket 实际被要求 237 kB/s。实测把预算降到 180 kB（合视频 148 kB/s）**并没有改善，反而更差**（180 秒内四个会话、四次欠载），所以这条虽然是对的，却不是本次故障的成因。
- **一个方法上的教训，由使用者当场纠正**："你不能光测一个频道，一个频道正常不代表其他频道也正常。"先前那次同步测试跑的是 ch000——恰好是十个频道里唯一能撑满五十秒的那个，于是故障被漏掉。另有两条工具性事实记下来免得再踩：**设备在 HELLO 里自己指定要播哪个频道，服务端 `--channel` 只是回退**，所以从服务端指定不了测试频道；以及**扫描脚本必须等端口真正释放再起下一个**，只 `sleep 2` 会让某一格根本没有服务端在跑，读数回来是全零，看起来像设备发现而其实是工具故障。

- 画面通路整体重做：不再下发 160×120 的 JPEG 由设备放大两倍，改为下发 320×240 的调色板索引整帧。原方案的屏幕上四分之三的像素是复制出来的，方块感来自这里；新方案每一像素都是源画面。一帧切成十五条十六行的横条、每条单独压缩后下发，一块屏幕能在整帧到齐之前就开始更新，而设备端需要的缓冲区不超过一条。设备端改用 C3 芯片 ROM 里自带的 zlib 解压（`0x400000f4`），索引展开成屏幕色时在缓冲区里从后往前就地做，因此这项改造没有增加帧缓冲，只多了约 11 KB 的解压状态。调色板按频道实时生成：每次换台先在源上采一秒半，选出 256 色随首个画面之前下发，所以不同频道各有各的色表，同一帧的色差（RMSE）从固定调色板的 28.2 降到 10.1。由用户提出：已发布版本的画面不流畅、画质不好。

- 修复画面颜色对不上的问题，成因是 ffmpeg 的 `rgb8` 并非「8 位色」。它是 ffmpeg 自己固定的 3-3-2 栅格，要它就意味着每个像素被重新量化到那个栅格上，选定的调色板整个被丢掉。这条不会报错——画面照样出来，只是自适应调色板白做。现改用 `pal8`，索引原样透传，并以「把索引经调色板还原成颜色后与同一帧的 rgb24 输出逐像素比对」验证：307200 像素零差异。

- **调色板问题定案，结论与上一条相反。** 上一条记录说 `rgb8` 是错的、`pal8` 才对；那是在调色板是**自适应**的前提下成立的。真正的问题不在格式，而在**自适应调色板本身**：它在开播时采一秒半生成，然后**整场冻结**，画面内容一变，256 个索引指向的就不再是画面该有的颜色。实测（开场昏暗偏褐、随后切彩条的素材）：用过期调色板画第 2.5 秒那一帧，RMSE 275（满值 255）；用该帧自身的调色板，RMSE 0；用固定 3-3-2 栅格，RMSE 57。这就是使用者描述的「时好时坏、有时灰、有时绿、有时褐」。**静态测试卡测不出它**——测试卡第一帧就含全部颜色，对采样来的表恰好正确。另发现 `palettegen` 的 `stats_mode=single` 配 `-frames:v 1` 实为「只取第一帧」，与函数注释承诺的「采样一秒半以免异常帧左右结果」正相反。
  现改用 ffmpeg 固定的 3-3-2 栅格（`-pix_fmt rgb8`），设备端 `av_palette_rgb565` 早已实现同一张表，不采样就不会过期。位序经纯红/绿/蓝编码后读回索引验证：0xE0、0x1C、0x03，即 RRR GGG BB，与设备端 256 项全吻合。**意外收益**：固定栅格的时间一致性更好，帧反而更小（中位 21087 B 对自适应 24604 B）。

- 修复接收任务的优先级。读 socket 的任务原为优先级 5，**低于**解码任务的 6，而这是单核芯片：解码一条条带最长 146 ms，这期间无人读 socket，服务端的写入没人取走，音频落后同样多而欠载。原注释担心的是优先级反转（接收占住缓冲饿死解码），但那个担心在本代码里不成立——`xQueueReceive(s.free_video, &v.jpeg, 0)` 超时为零，拿不到缓冲就丢包继续，永不阻塞。现为 **接收 6 / 解码 5 / 音频 7**。实测 8 fps：健康区间 7/26 → 30/37，帧中位 43 → 79（目标 80）。

- 关闭截屏诊断（`CONFIG_AV_SCREEN_CAPTURE` 默认 n）。它跟随颜色排查被留下，意味着其后所有性能测量都是在带诊断的固件上做的。代价不小且落在最坏的时刻：会话第 60 帧分配 9600 字节并打印约 10 KB 十六进制，在 115200 波特率下阻塞约 0.9 秒——正是刚开始播放、最容易掉线的那几秒。

- **修复原生 320×240 反而不如放大清晰的问题——根因是拆包。**使用者先试了放大档，指出画面有"网格状的像素点"（这是非整数倍放大的固有产物：200 或 240 个源像素摊到 320 个屏幕像素上，有的复制一次、有的两次），要求改回原生不缩放。改回原生后观感反而更差，查出的机制是：

  **一帧 320×240 压缩后中位 20.4 kB、最差 22.0 kB，实测 30 帧全部超过 `AV_VIDEO_MAX`（当时 16384），每一帧都被拆成两个包。**而设备端视频队列深度为 2——一帧拆成两包正好把队列占满，第二个包到达时无处可放，该帧残缺，而设备按规则丢弃不完整的帧。**于是像素变多的同时整帧被丢，原生比放大更差。**

  修法：`AV_VIDEO_MAX` 16384 → **22528**（容下最差的一帧），缓冲 3 → **2**。内存不增反降：2 × 22528 = 45056，比 3 × 16384 = 49152 少 4 KB。实测 300 秒：**掉帧 0、nobuf 0、零欠载**，帧率中位 9.2、音频全满、视频 148 kB/s（合计 180）。

  对照组（同样原生、同样音频修复后，但仍在拆包）：掉帧 195、nobuf 166、4 次欠载。**两项计数同时归零，说明拆包确实是那个机制。**

- **320×240 原生在音频时序修复之后重测，结论变了但落点不变。**原先的否决（300 秒内 19 次会话中断、只能跑 7 帧）是在音频领先量还是 200 ms 时测的，而领先量定案在**一小时二十分钟之后**——前提已经失效，所以重测。修复后它能跑 **8.9 帧**（原 7 帧），**单帧绘制只要 34.7 ms**（比 280×210 的 54.7 ms 低得多，因为没有放大这一步），掉帧仅 3。但它用的是 **219 kB/s**，正贴在链路实测区间 141–243 的上沿，300 秒里仍有 **4 次欠载**、服务端 11 次连接被设备断开。**它是最清晰的一档（100% 源像素）却守不住会话。**

  三个档位的实测对照（音频时序修复后，每档 300 秒）：

  | 档位 | 内容像素 | 帧率 | 每秒上屏像素 | 带宽 | 欠载 | 屏幕自有像素 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 240x180 | 32,400 | 13.9 | 450k | 192 kB/s | 0 | 3/4 |
  | **280x210（默认）** | **43,960** | **10.1** | **444k** | **203 kB/s** | **0** | **7/8** |
  | 320x240 | 57,600 | 8.9 | 547k | 219 kB/s | 4 | 100% |

  **240x180 与 280x210 每秒上屏的像素几乎相同（450k 对 444k），而 280×210 用更少的放大达到它**——所以后者更优。320×240 每秒像素最多，但守不住。

- **画质再提一档：几何由 240×180（放大 4/3）改为 280×210（放大 8/7），屏幕上自有像素的比例由四分之三提高到八分之七。**实测 300 秒：帧率中位 **10.1**、零欠载、音频全满、视频 177 kB/s。内容像素由 32,400 增至 43,960（**+36%**），代价是帧率由 13.9 降到 10.1。

  这是一次真实的取舍，两档都实测过，且**两档都留在固件里可切换**：

  | 档位 | 内容像素 | 帧率中位 | 音频 |
  | --- | --- | --- | --- |
  | 240x180 | 32,400 | 13.9 | 满 |
  | **280x210（当前默认）** | **43,960** | **10.1** | 满 |

  10.1 帧远高于使用者当初判定为"像幻灯片"的 4 帧，而 36% 的像素提升在清晰度上看得出，因此默认取 280x210。

- 几何改为**按名字选择**而非三个必须同时设对的环境变量。设备把几何编译进固件，两端必须完全一致，否则每个会话都被拒——而拒绝对外表现得像链路故障：设备连上、鉴权、随即断开。三个环境变量就是三次设错的机会，而排查代价很高。现在是一个名字：`TV_GEOMETRY=240x180` 或 `TV_GEOMETRY=280x210`，填了固件里没有的档位会在启动时立刻报错并列出可选项。`tools/check_config_agreement.py` 也会先打印"固件是按哪一档构建的、服务端准备发哪一档"，不一致时直接给出该设的值。这个项目的几何必须两端一致，而这个错误已经犯过三次。

- **在修复后的固件上重扫帧率，确认 14 是综合上限。**240×180、压缩级别 6、音频修复后：

| 要求 | 实到 | 合计带宽 | 欠载 | 掉帧 |
| --- | --- | --- | --- | --- |
| **14** | **13.9** | **192 kB/s** | **0** | **2** |
| 16 | 13.8 | 239 kB/s | 1 | 220 |
| 18 | 13.1 | 203 kB/s | 0 | 534 |
| 20 | 会话建不起来 | — | — | — |

**要得越多拿到越少**，与更早的包数瓶颈同一形状。16 和 18 都没有更快，而且丢帧分别涨到 220 和 534；服务端的 `send_gap_max_ms` 由 14 帧时中位 83 ms 涨到 127/112 ms，`prod_drop` 由 57 涨到 91/129——**发送侧开始阻塞**。18 帧的字节数（171）反而低于 16 帧（207），因为发不出去的帧被丢弃了，这正是"要更多拿更少"的机制。

**14 是当前几何下链路与设备的综合上限**：实到 13.9 帧、零欠载、掉帧 2。

- **帧率上限由 11 提到 14，实测帧率中位由 10.5 升到 13.4（+28%）。**11 这个上限是在"单帧绘制峰值 74 ms 需要更宽的槽位"这个推理下定死的，但那个峰值是百里挑一的一帧，而持续速率跑在均值上。用固定 15 帧实测 200 秒：设备守住 14.1–15.0 帧、音频全满、零欠载，代价只是开头一阵掉帧（53 帧）——那是画面与音频时钟的一次性对齐，不是设备跟不上。**这正是控制器原先缺的区分。**

- **速率控制器原先分不清"一整子掉帧"和"持续跟不上"。**它见到任何掉帧就退让，于是在 13–14 帧的边缘反复拉锯：实测 300 秒，帧率中位 11.9，而固定 14 帧能守住 14.4——**控制器把会话时间花在爬升途中而不是顶上**。现改为：连续两个窗口都掉帧才退让，孤立的一次掉帧只记下不降速；且单次掉帧不再清空"舒适"窗口的累计。同时把升级所需窗口从 4 降到 2。

- **否决：给流水线加深（第四个视频包缓冲 + 视频队列 3 格）。**理由是 `nobuf`（接收端取不到空闲缓冲）在 13–14 帧时开始非零、控制器据此误判设备跟不上。但第四个包缓冲要 16 KB，而**频道表解析发生在会话缓冲分配之后**——两者挤同一片堆，结果是 cJSON 分配失败返回 NULL，设备端每个 CONFIG 字段都查不到，会话连上即断。从外部看到的不是"内存不足"，而是"配置被拒"，与链路故障同形。这是同一个坑的第三次：会话分配在前、频道表解析在后，任何在会话里新增的分配都在和它抢。为下一次省时间，`config_valid` 现在会在拒绝时**逐字段打印服务端值与设备期望值**，并在解析失败时打印堆与最大连续块。

- 修复设备端一个**单位错误，它让坏掉的仪器看起来像很快的设备**。`elapsed` 已经是毫秒（取时间戳时就除过 1000），却又被累加进名为 `panel_us` 的字段并在输出时再除一次 1000。实测后果：107 帧只报 6 ms 绘制时间，即每帧 0.06 ms——而同一行的 `inflate_ms` 报每帧 12.3 ms，且这 12.3 ms 就发生在这个计时区间**之内**。同一行里两个不可能同时为真的数字，就是单位错误的样子。修正后每帧绘制 63.5 ms，与 `decode_max_ms` 的 74 ms 峰值自洽。同时把 `decode_max_ms` 由"会话级最大值"改为**每区间峰值**（原先只在会话开始时清零、日志直接打印，所以在会话里只增不减），并新增 `panel_frames` 计数，使均值有分母、口径可验证。

- 修复后重测，**上一轮的帧率上限结论成立且现在有了独立验证**：每帧绘制 63.5 ms，`decode_max` 峰值 74 ms，11 fps 的槽位是 90.9 ms——余量约 16 ms。此前那个结论靠的是一个单位错误的字段，数字对但依据不牢。

- 实测并否决：**给条带缓冲做双缓冲流水**，让 SPI 传输与下一条带的解析重叠。推理成立（提交后等待 DMA 的 31 ms/帧里处理器空闲），但设备实测毫无改善：帧率 10.5 对 10.4，`decode_max` 70 对 72–81，每帧面板计时 61 ms 对原本的 38–82 ms 区间。SPI 引擎本就已经与下一条带的准备重叠，等待并非看起来那样的串行点。而且第二个缓冲要 10 KB，而堆已无余量——表现为会话启动时频道表解析失败（`No memory to parse the channel list`），把视频包缓冲从 3 减到 2 去腾空间之后又付出 31 帧丢失。已完全回退。

- **设备自身的绘制耗时才是帧率上限。**此前 `MAX_FPS` 由定速探测设定（12，后改 15），而那次探测自相矛盾——请求 18 帧建不起会话，请求 21 帧却建起来并交付 13.9 帧。把上限撤掉让控制器自己找，结果是每个会话都爬到 14.9 帧、接收端空闲缓冲耗尽（`nobuf` 三个窗口内 0→12→45）、之后永久掉帧且不再恢复，而控制器两个信号都显示健康：**从发送侧看，"链路很快"和"设备画不动"长得一模一样**。实测设备单帧绘制峰值 80 ms（`decode_max_ms`，数百帧稳定），12 帧的槽位是 83.3 ms——只剩 3 ms 余量，第一个抖动就丢帧；11 帧的槽位是 90.9 ms，余量 11 ms。**上限据此定为 11。**

- 把掉帧数接进速率控制器。此前控制器只有两个信号——写耗时与窗口字节数——两者都来自本机 socket，对远端的绘制能力一无所知。现在画面因排不进时间轴而被放弃时，控制器立即降一帧并清零"舒适"计数。**每一次掉帧都计数**：曾试过容忍零星掉帧（理由是单次丢失是噪声），420 秒实测帧率中位升到 12.1，代价是丢失帧数由 0 涨到 339。在设备极限就是工作点的情况下，掉一帧是信号而不是统计噪声。

- 实测并否决：**把"索引展开"和"4/3 放大"合并成一遍**。合并版经过逐像素比对与两遍法完全一致，且每帧少写 153600 字节，但更慢——设备自报 `decode_max_ms` 由 78 涨到 91，把内层除法改成乘法也无改善（90）。原因是查表次数：两遍法每帧 43200 次调色板读取再搬字节，合并后变成 76800 次（每个屏幕像素一次），这颗芯片上一次查表比它省下的字节搬运更贵。已回退并保留两遍法。

- 修复音频在视频包传输期间被抽干的问题，这是使用者报告的"时有时无"的成因。三项改动：**音频块 20ms → 40ms**（一等份时间翻倍，而设备队列的块数不变即缓冲时长翻倍；这项改动此前被否过，理由是不省字节——而当时的前提错了，稀缺的是包数不是字节）；**音频领先 200ms → 320ms**（一个任务读两路流，画面包在途时音频队列无人取走，而 240×180 一帧约 13KB、过链要 220ms，比队列持有的 200ms 还长；实测每次欠载前的十秒区间音频都是满的，失败时的间隔每次都是 305ms，即设备的阈值本身）；**音频领先与视频领先解耦**（二者原本相等，一起提高会让画面提前 200ms 发出、与声音挤在一起，实测掉帧从 9 涨到 58）。扫描结果：200ms 时欠载 10 次，260ms 时 0 次、帧率中位 10.0，**320ms 时 0 次、帧率中位 10.8 且零掉帧**，400ms 时 0 次但掉帧 39、帧率回落到 9.0。设备端 `PCM_QUEUE` 随之由 30 块改为 24 块。

- **压缩级别 1 → 6，每帧省 9.4% 字节。**原先选级别 1 的依据是"与级别 6 相差不到五分之一而非"，那是在旧几何下测的，几何一换这个数字就变了：240×180 索引色下实测，级别 1 每帧 13412 字节、级别 3 是 12905、级别 6 是 12147、级别 9 是 12141，而压缩耗时只从 0.4ms/帧涨到 0.9ms/帧。**这些字节直接就是帧率**：实测 420 秒，帧率中位由 9.1 升到 **11.9**，视频流量由 143 降到 121 kB/s，掉帧由 46 降到 **0**。教训是那句注释里的"不到五分之一而非"必须随几何重测，而不是当初测过一次就一直引用。

- 把视频包上限从 12288 提高到 16384、缓冲从 4 个减到 3 个，使一帧直播画面装进一个包。**瓶颈是每秒包数，不是字节数**——设备接收路径约 72 包/秒封顶，而 240×180 每帧约 13400 字节，超过原来 12288 的上限就要拆成两个包，12 帧下等于 24 个视频包加 50 个音频包，正好撞上上限。提高上限后同样 12 帧只需 12 个视频包。内存不变：3 × 16384 = 49152，与原 4 × 12288 完全相同，单块 16384 也在设备最大可分配块 36864 之内。这解释了此前一个反直觉的读数：**要求 16 帧反而比要求 12 帧更差**（83 kB/s 对 156 kB/s），因为多出来的包挤掉了音频，音频欠载把会话拖垮。修复后 16 帧请求能跑到 13.7 帧、音频满。

- 实测否决三项编码侧的尝试，记此以免重来：**PNG 过滤器**（sub/up/avg/paeth）全部更差，最好的 paeth 也让字节增加 19%——索引值本身已被量化，deflate 的 LZ77 直接利用了索引的重复，减法反而打乱；**锐化**（unsharp）不可用，MAE 变差 61% 到 165%，因为 3-3-2 栅格的蓝色只有四级，振铃和色带先于观感收益出现；**降低色深**（64 色）省 30% 字节但误差涨 66%，同一预算下把字节花在像素上始终优于花在颜色上。

- 320×240 原生在包上限提高后重测，仍然守不住：300 秒内 19 次会话中断，全部是音频欠载，最好时也只有 7 帧。它在离线误差表上是最清晰的一档（MAE 9.85 对 240×180 的 11.78），但实时通路容纳不下。240×180 是清晰度与稳定性的落点。

- 确认自适应优于固定帧率：同样 300 秒，自适应音频欠载 2 次、掉帧 9，固定 12 帧欠载 8 次、掉帧 33。自适应帧率中位低一帧，但守得住会话。

- 画面几何定为输入 240×180、设备端放大 4/3。整个几何族（20 的每个倍数，即条纹能整除 240 行的每个尺寸）先离线渲染——经设备自己的放大、按服务端的方式压缩——再挑有希望的刷机实测。**放大并不划算**：压缩后每像素字节数越小的画面越差（320×240 是 0.28，160×120 是 0.33，实测），所以少发列数省下的字节有一部分又还了回去，每秒上屏的像素随画面变小而减少。四个落点的实测：160×120 放大 2 倍跑 12 帧、200×150 放大 8/5 跑 12 帧、**240×180 放大 4/3 跑 11 帧**、320×240 原生只能跑 7 帧且音频每四十秒欠载。320×240 的每秒像素最多但守不住会话；240×180 在音频全满、零丢帧下守住 11 帧每秒、200 秒实测，是能稳住的配置里每秒像素最多的。开自适应时更好：200 秒零中断、丢帧 0、音频 499–503，中位 11 帧。因此默认改为自适应、起始 10 帧；另新增 `tools/geometry_sweep.py`，不接触设备即可比较全族。

- 修正此前两处关于链路容量的错误记述。`server/rate.py` 与 `server/usb_link.py` 各写了一个数字（227000 与 175000 字节/秒），两者都是从估算来的，而设备实测到过 243000 字节/秒且零丢帧、音频全满——自己的估算被当成了设备的极限，并据此写进了文档。现不再在任何地方声明一个常数容量：速率控制器按实测决策，同一台设备同一房间在不同会话里实测区间是 141 到 243 kB/s。

- 画面几何改为输入 200×150、由设备整数放大 8/5 铺满 320×240。上一版下发的是 320×240 整帧，实测在这条链路上只能支撑 6.5 帧/秒；而链路约 175 kB/s 是硬上限：需求加到 190 kB/s 会话就建不起来，156 kB/s 则能一直稳。总字节既然固定，可动的就只剩「一帧送多少像素」。8/5 是唯一同时压过已发布版的整数比例：屏幕上按源自身比例显示 200×112，对已发布版的 160×90 是**像素 1.56 倍**；实测 12 帧/秒下完成 117/120 帧（97%）、音频 500/500、零丢帧，**帧率 1.13 倍**。比例取整数而非任意值，是为了每个输出像素都恰好是某个输入像素的拷贝，既无插值也无舍入；条纹几何由比例推出而不是另行选定——屏幕一次取 16 行，画面供 10 行（16 × 5/8），150 行正好是十五个十行；10 行 × 200 像素 = 2000 索引字节，展开放大后恰好填满屏幕那条 10240 字节的条带，因此这项改动**不增加内存**。

- 修复设备因 CONFIG 校验失败而连上即断。设备端 `AV_STRIPE_ROWS` 有 16 处用途，其中 15 处指「屏幕一次取 16 行」，只有一处指「服务端把画面切成几行一条」。把画面改成 10 行一条时改了前者、漏了后者，于是服务端发 10、设备要 16，CONFIG 判为非法，每个会话连上即断、零媒体，一秒一次。从外部看不到「配置被拒」这件事，看到的是一台反复重连却什么都不发的设备，与链路故障、网络不稳完全同形；而这个症状仓库里已记过一次（`channels` 键冲突），本该认得出来。新增 `tools/check_config_agreement.py`：把服务端**实际会发**的 CONFIG 逐字段与固件**实际接受**的常量比对，两边都从真实源码读取（解析头文件、导入组包模块），不重建一份数值副本——那样只会自己和自己一致，什么也证明不了。已接入 `validate.sh --static`，以后每次校验都会跑。

- 新增 `docs/development/handoff-20260915.md`（双语），记录链路实测上限、各分辨率实测字节开销、新几何在真机上的实测结果、接收任务耗时分解，以及已实测否决的若干方案。

- 修复非方形像素的视频上下出现白边。调色板采样与画面映射用的不是同一套缩放几何：采样按满屏取色，映射却加了黑边，于是调色板里没有黑色，黑边被映射到最近的可用颜色也就是白色，整个面板看起来是亮的。现由同一处定义派生，两者不可能再不一致。

- 修复调色板第 256 项被 ffmpeg 占用的问题。`palettegen` 默认预留一项给透明色并写入纯绿，而设备用不到透明，这一项本可以从源画面里取一个真实颜色。现关闭预留，256 项全部来自源。

- 修复退出统计里「失败次数」时而多算时而少算。设备在鉴权之后断开时，两条代码路径都会发现，谁先发现决定了这次会话被记成正常结束还是故障——实测约十次错一次，而这个数字正是程序退出时给操作者看的唯一一行统计。分界改回它本来的位置：握手之前断开是观众改了主意，不计数；握手之后断开是真故障，如实计入。

- 修复 `install-actionlint.sh` 在 macOS 上必然失败。它用 `command -v sha256sum` 判断校验工具，而 macOS 的 `/sbin/sha256sum` 存在、也能被找到，却不接受任何选项，`--check` 直接打印用法就退出。现优先使用 `shasum`。

- 修复导入视频时每次漏一个文件描述符：只关闭了读取的管道，stderr 管道留着。单次命令行使用看不出来，长期运行的服务上是每个片段漏一个。

- 修复导入视频会写出「画面的图片」而不是画面本身。ffmpeg 的 `image2` 复用器按文件扩展名挑选编码器，于是一个 76800 字节的索引帧被写成 13287 字节的 PNG——既更大，又已经不是设备要读的索引。现改为逐帧读取原始字节，两端之间不再有编码器。

- 修复设备会把正在播放但一时不稳定的频道丢掉。原来的判断只数"连续几趟会话没出画面"，而"源抖了一下"和"源已死"在这笔账上长得一模一样：两次重连都没赶上出画面，频道就被当成死链跳过，而且跳走之后连观众的选择一同丢弃。现在区分二者的是"这个频道此前出过画面没有"——出过画面的频道无论失败多少次都留在原地重试，只有从始至终没出过画面的条目才会被跳过。既有的用意原样保留：死条目仍然会被跨过，否则观众会一直困在测试图上。判定规则抽成 `main/av_channel_policy.c`，可在主机上测试，`tests/test_av_channel_policy.c` 覆盖了 12 种情形，包括"看过 A 再去看 B、回到 A 时 A 仍受保护"这一类需要记住多个频道的场合。由用户报告：频道不稳定时设备自动往下跳。

- 修复自动跳台时把"这是观众选的"标记一并抹掉。该标记用于给观众主动选择的频道更宽的容忍度（4 次而不是 2 次），把它清掉会让下一个频道按"自动到达"对待，容忍度反而收紧，于是一个不稳定频道可能引起连续跳台、一格格往下滚。现在只在跳台时撤销标记，含义回归它原本的用途。

- 修复下载版一律无法建立 HTTPS 连接：播放列表加载不了、ffmpeg 也取不回来，两处都报 `unable to get local issuer certificate`，而同一个地址在浏览器里正常。原因是 Python 从编译时写死的路径读取根证书，而在一台机器上构建、下载到另一台机器运行的产物会继承构建机的路径，那个路径在用户的电脑上并不存在。新增 `tools/certs.py`，改用本机确实存在的证书文件，并以"实际装载了多少个根证书"为判据，而不是"文件是否存在"——后者正是最初写错的地方。验证方式：用一个自身没有证书文件的 Python 构建，再撤掉本机证书；修复前播放列表与 ffmpeg 下载双双失败，修复后都正常。构建检查里增加一问：撤掉本机证书后问产物"你还能校验 HTTPS 吗"，答不上则不允许发布。由用户在日常使用中第一个撞上并报告。

- 修复关掉程序后两个子进程活着不走的问题。关闭终端窗口或执行 `kill` 发送的是 SIGTERM，Python 默认直接结束进程，`finally` 里的清理代码不执行，于是媒体服务器与频道配置页留在自己的会话里继续运行，8096 和 8097 端口不释放。下一次启动会报"端口已被占用"，而屏幕上没有任何线索把它和用户认为已经关掉的程序联系起来。现在 SIGTERM 等信号与 Ctrl-C 走同一条退出路径；此外每个子进程会自行检查启动它的进程是否还在，覆盖信号无法覆盖的情况（进程被强杀）。打包版还有第二层后果：被留下的子进程仍在引用其父进程已经删除的临时目录，靠已加载的模块继续工作，直到要用某个尚未导入的模块时崩溃并报 `LookupError: unknown encoding: idna`——这句话描述的是症状，与真正的原因毫无关系。

- 退出提示不再把正常事件报成故障。握手阶段就断开的连接——换台、设备休眠、端口探测都会产生——原本计入失败次数，于是一次健康的运行会以"失败 3 次"结尾，而使用者无从知道这三次是什么。现单独计数且不再出现在提示里；通过鉴权之后才中断的会话仍然计为出错并如实报告。

- 逐条审读程序打印给运行者看的每一句提示。启动提示由十六行压到四行：删去正在监听的地址（那是这台电脑自己的号码，设备拿到的是主机名），只留下要填进设备的那一个地址，下面最多一行说明连不上时换成什么。五处仍是英文的提示改为中文，程序不再说到一半换语言；Ctrl-C 退出不再报告内部失败条数；端口被占用原本是二十行 Python 堆栈，末行写着 `OSError: [Errno 48] Address already in use`，现改为两句可读的话，并按 `errno.EADDRINUSE` 判别——这个编号在 macOS 是 48、在 Linux 是 98。`--help` 也已中文化，包括 argparse 自己拼出来的 `usage` 与 `options` 两个标题。

- Release 页面不再只列文件名，而是先说明该下哪一个：哪台电脑对应哪个文件、刷设备与跑服务是两件都要做的事、以及用户最先撞上的两个拦截（Windows 防火墙、未签名程序提示）。此前两次发布出来都是空正文，原因已查明：发布任务不检出仓库，只下载构建产物，指向仓库内文件的 `body_path` 自然找不到，动作便静默退回空正文。现改为在两个工作流里各写一份同样的正文——两份必须一模一样，后运行的那个会把 Release 整个改写。

- 服务端改为下载即用：新增三平台单文件可执行程序（`tv-server-*`），用户下载后双击即可，不必安装 Python。程序首次运行时自动获取 ffmpeg（约 21–31 MB，仅此一次；已装 ffmpeg 的机器完全不联网），获取前先说明体积并校验 sha256，不符则拒绝写入与执行。不内置 ffmpeg 的原因是这些构建带 `--enable-gpl`，随包再分发会产生提供源码的义务，而用户本机按需获取不构成再分发。可执行文件走 Release 分发，不进仓库。

- 服务端数据与代码位置分离：新增 `tools/datadir.py`，可写位置依次为 `TV_DATA_DIR` 环境变量、程序所在目录（实测可写才用）、平台用户目录；启动时打印实际路径。原先两者用同一个 `__file__` 推导的路径表示，从仓库运行时恰好重合，打包后会指向运行时就删除的临时目录，导致频道表保存丢失。子进程改用 `PYTHONPATH` 而非工作目录来找到 `server` 包，两者职责由此拆开。

- 修复首次保存频道表不触发媒体服务器重启：原判据要求比较两个时间戳，即只在文件已存在且发生变化时重启；而新数据目录首次运行为空，第一次保存恰好是从无到有。另修复重启时沿用旧频道名的问题——首次保存会用用户的表整体替换内置列表，旧名必然不在其中，服务器以 `--channel` 为必选并校验取值，随即退出且无人监听端口，用户看到的是"一保存就没画面"。现改为不存在时回退到新表首项。

- 构建自带的冒烟测试在 Windows 上读不懂程序的中文输出：`subprocess.run(text=True)` 用系统代码页解码，读取线程抛 `UnicodeDecodeError`，stdout 变成 `None`，随后比较时出错。程序本身一直是正确的，坏的是检查它的那段代码。现在仓库里每一处捕获子进程输出的地方都写明编码，并由一个 AST 扫描看守以免新增遗漏——该扫描还查出了第二处，在仓库检查工具里，中文路径同样会让它出错。

- 孤儿检测改为能在 Windows 上生效的做法。检查 `os.getppid()` 在 POSIX 上可行（子进程会被重新挂到 init 下），但 Windows 上父进程编号从不改变，检查永远不触发——于是 macOS 与 Linux 通过、Windows 失败，而问题正是 Windows 上报告的。现在启动器给每个子进程一个它从不写入的 stdin 管道，并在退出时关闭；启动器无论以何种方式结束——包括被直接强杀——子进程的读取都会返回文件结束，随即退出。管道是句柄而不是取值，不会过期，也不含任何平台差异。验证方式：用 `kill -9` 强杀启动器，修复前两个子进程存活并占着两个端口，修复后什么都不剩。

- 守护线程在解释器关闭期间读取 `sys.stdin.buffer` 是致命错误而非警告：Python 在持有该锁的情况下收尾，以 `_enter_buffered_busy` 中止，把一次干净的退出变成崩溃。现改用 `os.read` 读取原始文件描述符，不涉及这把锁。这个问题是实跑发现的，不是查文档查出来的，值得记下来：它只在退出路径上出现，而那是其他测试都碰不到的路径。

- 关闭终端窗口不再打印 Python 堆栈。窗口关闭会发出两次 SIGHUP——这是用伪终端实测的，不是推断——第二次在第一次的处理过程中到达，于是中断从"处理该中断的代码"内部抛出，无人接住，用户看到的最后一行是堆栈。退出本身一直是正确的，错的只是那几行文字；而这类错误会让人以为程序坏了。现在第二次停止请求被忽略；同样的保护也覆盖了子进程尚未启动的阶段（例如获取 ffmpeg，约需半分钟），做法是在启动器顶层捕获中断，而不只是围着运行子进程的那一段。验证方式：在伪终端下关闭窗口，堆栈消失，退出码由 1 变为 0，两个端口都释放。

- 修复"检测失效"把能播的频道判为失效。页面取的是 `c.ua`，而这个字段一直叫 `agent`——播放列表解析、频道表存储、保存写回，三处都是这个名字。于是每次探测都带着空的 User-Agent，而那些只应答特定播放器的源会直接拒绝：403、取不到帧、判定为"失效"，而该频道实际能播。由用户实测发现并报告——他自己试了一个，看着它播出来了，说页面不对，页面确实不对。用真实频道表做了双向实测：带上 agent，八个 CCTV 全部在半秒左右解出画面；不带，全部在零点一秒内失败，也就是页面此前一直显示的结果。新增 `tests/test_channel_config.py`，把页面读取的字段名与后端产生的字段名做比对，两边不再毫无关联。

- 启动提示里补上一句：关掉这个窗口，服务就停止了。此前没有任何地方说明这一点，而窗口看起来像个日志窗口——读完就顺手关掉——但关掉它，设备上的画面就没了。屏幕变黑和窗口被收走这两件事，从外面看不出任何联系，所以不说明的代价是一个画面停了、而使用者无法还原原因。这句话放在地址和网络提示之后，也只有在这个位置说，读者才还看得见。

- 烧录说明原本告诉读者：拔掉数据线，设备会自己重启。它不会，原因有两个，都对着硬件核实过。其一，设备走 ESP32-C3 的内置 USB 外设，而 esptool 的默认复位是拉低 RTS 线——那是外置 USB 转串口芯片的接法，USB 外设没有这根引脚可拉，于是 `loader.after()` 打印一句 "Hard resetting via RTS pin..." 却什么也没复位。其二，设备内置 520 mAh 电池，拔线只断开充电。两者叠加的结果，是芯片停在刷写状态、屏幕全黑——看着和刷失败一模一样。三处说明（烧录页、英文 README、中文 README）现在都写明要按住电源键关机再开机，页面也不再调用那个不可能生效的复位。新增测试让三处保持一致，并阻止"自动重启"这类说法回到刷固件那一节；配网流程不受此限，那里固件确实会在保存凭据后主动重启。

- 刷写日志现在会说明下一步做什么。此前它报完写入就结束了——不提重启，也不提电脑上还要装服务端。而那一刻用户正盯着这块日志，这里留白，正是周围那几步要改说明文字想解决的问题。新增两行：按住电源键关机再开机；然后去 Releases 页面下载服务端。按钮下方那一步也改成直接链到 Releases，因为日志里的文字点不动，"去 Releases 页面"这样一句从段落里读到的指示，读者是没法照做的。日志里"写入完成"原本出现两次（分列在已删除的复位调用两侧），读起来像写了两遍——由用户阅读自己的刷写日志时发现。

- 烧录页只留读者要做的事。删去：开头那段导语和"本页不会擦除设备"提示（说的是这个页面怎么工作，不是要读者做什么）；"按住某键再开机"进入刷写状态的说明（在这台设备上从未验证，改为"保持设备开机状态"）；以及整片擦除的警告（警告的是一个本页不提供的工具、一个本页造成不了的风险）。esptool 的输出也不再进日志——五十行 "Writing at 0x... (n%)" 和芯片识别信息原本被灌进读者正在看的框里，把那两行真正给他看的话埋在中间，而上方的进度条早就把同一件事说清楚了。校验值和写入范围同样从日志里删除，理由一样。删除后遗留的无用样式一并清掉。

- macOS 的说明改成与 macOS 15 上实际发生的情况一致。原文是"右键点这个文件，选打开"，而那个右键菜单里已经没有这一项了。双击未签名的程序会弹出一个两按钮对话框，右边那个是"移到废纸篓"，而绕过去的入口在"系统设置 → 隐私与安全性 → 仍要打开"。旧说法比没有更糟：被告知去右键菜单里找"打开"的人找不到，眼前唯一显眼的按钮却会把下载的程序删掉。中英 README 与两份 Release 正文均已修正，并新增测试让这四处保持一致——这段话写了四遍，而走样的方式正是改了一处、漏了另外三处。由用户实际撞上这个对话框后报告。
